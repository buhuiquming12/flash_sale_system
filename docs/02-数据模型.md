# 02 数据模型

MySQL 8.0，全部 InnoDB + utf8mb4。时间列统一 `DATETIME(3)`，避免时区问题；
金额统一 `DECIMAL(12,2)`，禁止用 float/double。

**建表脚本以 [`sql/V1__init.sql`](../sql/V1__init.sql) 为准**，本文档的 DDL 与它逐字对应。
那份脚本只含建表语句、不含 `CREATE DATABASE` / `USE`：Docker Compose 由
`MYSQL_DATABASE=flash_sale` 指定默认库，Testcontainers 由 `withDatabaseName` 指定，
两边共用同一份 DDL，避免测试与部署的表结构漂移。

> MySQL 容器必须显式加 `--default-time-zone=+08:00`。默认时区是 UTC，
> `NOW(3)` 与列 `DEFAULT CURRENT_TIMESTAMP(3)` 写入的时间会比 Java 侧写入的
> `LocalDateTime` 慢 8 小时。compose 与 Testcontainers 两处都加了，
> 并有 `DatabaseTimezoneTest` 防回归——原有用例抓不到它，因为断言的字段恰好都是
> Java 侧写入的。

## 1. 用户

```sql
CREATE TABLE t_user (
    id           BIGINT       NOT NULL AUTO_INCREMENT,
    username     VARCHAR(64)  NOT NULL              COMMENT '登录名',
    password     VARCHAR(100) NOT NULL              COMMENT 'BCrypt 摘要',
    phone        VARCHAR(20)  DEFAULT NULL          COMMENT '手机号',
    nickname     VARCHAR(64)  DEFAULT NULL,
    role         TINYINT      NOT NULL DEFAULT 0    COMMENT '0=普通用户 1=管理员',
    status       TINYINT      NOT NULL DEFAULT 1    COMMENT '0=禁用 1=正常 2=风控冻结',
    create_time  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    update_time  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uk_username (username),
    UNIQUE KEY uk_phone (phone)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户';
```

`password` 用 BCrypt（Spring Security `BCryptPasswordEncoder`，强度 10）。
`phone` 当前明文存储；若要加密又要支持按手机号登录，需存**确定性**加密值而非随机 IV
加密，否则无法建唯一索引。

## 4. 秒杀商品（核心热点表）

```sql
CREATE TABLE t_seckill_goods (
    id               BIGINT        NOT NULL AUTO_INCREMENT,
    activity_id      BIGINT        NOT NULL,
    sku_id           BIGINT        NOT NULL,
    seckill_price    DECIMAL(12,2) NOT NULL           COMMENT '秒杀价，服务端唯一价格来源',
    total_stock      INT           NOT NULL           COMMENT '活动总库存',
    available_stock  INT           NOT NULL           COMMENT '可售库存，扣减目标',
    locked_stock     INT           NOT NULL DEFAULT 0 COMMENT '已下单未支付占用（统计用）',
    sold_stock       INT           NOT NULL DEFAULT 0 COMMENT '已成交',
    released_stock   INT           NOT NULL DEFAULT 0 COMMENT '累计回补，用于对账',
    limit_per_user   INT           NOT NULL DEFAULT 1 COMMENT '每人限购',
    status           TINYINT       NOT NULL DEFAULT 1 COMMENT '0=停售 1=在售 2=售罄',
    version          INT           NOT NULL DEFAULT 0 COMMENT '预留乐观锁，主链路不用',
    create_time      DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    update_time      DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uk_activity_sku (activity_id, sku_id),
    KEY idx_sku (sku_id),
    CONSTRAINT ck_goods_stock     CHECK (available_stock >= 0),
    CONSTRAINT ck_goods_total     CHECK (total_stock >= 0),
    CONSTRAINT ck_goods_price     CHECK (seckill_price >= 0),
    CONSTRAINT ck_goods_limit     CHECK (limit_per_user >= 1)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='秒杀商品';
```

**`CHECK (available_stock >= 0)` 是最后一道防线，不是主要手段。**
主要手段是条件更新：

```sql
UPDATE t_seckill_goods
   SET available_stock = available_stock - #{qty},
       locked_stock    = locked_stock + #{qty}
 WHERE id = #{id}
   AND status <> 0
   AND available_stock >= #{qty};
-- 返回影响行数 0 → 库存不足，抛 BizException(STOCK_NOT_ENOUGH)
```

**库存三分口径**：`total_stock = available_stock + locked_stock + sold_stock` 恒成立。

| 动作 | 变化 |
| --- | --- |
| 下单 | `available → locked` |
| 支付成功 | `locked → sold` |
| 取消 / 超时关单 | `locked → available`，同时 `released_stock += qty` |
| 管理调整 | `total` 与 `available` 同步增减 |

下单时加的是 `locked_stock` 而**不是** `sold_stock`：此刻商品只是被占用，还没成交。
如果下单就加 `sold`，支付时的 `moveLockedToSold` 会把 `sold` 加第二次，
库存等式立刻不成立、对账任务马上报差异。这个等式在每个集成测试里都被断言。

**"排队中"的数量不进这条等式。** 它是"Redis 已预扣但还没落库"的量，
根本还没到 DB。把它加进来会让等式在有排队请求时恒为假，于是对账每轮都判"DB 漂移"、
自动修正永远不触发（它的前提正是这条等式成立），症状是"对账一直在报差异，
但库存其实是对的"。排队中的量出现在**另一条**等式里：
`redisStock == available_stock - 排队中数量`。三条等式各查一件事，见
[05 §9.2](05-消息与一致性.md)。

不用 `SELECT ... FOR UPDATE` 再更新（两次往返、持锁时间长），也不用
`version` 乐观锁（1000 并发下 CAS 重试率极高，退化成忙等）。条件更新一条语句
完成"判断 + 扣减"，行锁只在语句执行期间持有。

**为什么 CHECK 只是兜底**：MySQL 8.0.16+ 的 CHECK 违反会抛 3819 错误，
整个事务回滚，对用户表现为 500 而非"库存不足"。条件更新让我们能返回准确错误码。

## 5. 订单

```sql
CREATE TABLE t_order (
    id              BIGINT        NOT NULL AUTO_INCREMENT,
    order_no        VARCHAR(40)   NOT NULL           COMMENT '业务订单号',
    request_no      VARCHAR(40)   NOT NULL           COMMENT '秒杀请求号，幂等键',
    user_id         BIGINT        NOT NULL,
    activity_id     BIGINT        NOT NULL,
    sku_id          BIGINT        NOT NULL,
    status          TINYINT       NOT NULL DEFAULT 0
                    COMMENT '0=待支付 1=已支付 2=已取消 3=已完成 4=退款中 5=已退款',
    total_amount    DECIMAL(12,2) NOT NULL           COMMENT '原价合计',
    pay_amount      DECIMAL(12,2) NOT NULL           COMMENT '应付金额',
    quantity        INT           NOT NULL DEFAULT 1,
    stock_released  TINYINT       NOT NULL DEFAULT 0 COMMENT '0=未释放 1=已释放',
    expire_time     DATETIME(3)   NOT NULL           COMMENT '支付截止时间',
    pay_time        DATETIME(3)   DEFAULT NULL,
    cancel_time     DATETIME(3)   DEFAULT NULL,
    finish_time     DATETIME(3)   DEFAULT NULL,
    cancel_reason   VARCHAR(200)  DEFAULT NULL,
    create_time     DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    update_time     DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uk_order_no (order_no),
    UNIQUE KEY uk_request_no (request_no),
    UNIQUE KEY uk_activity_sku_user (activity_id, sku_id, user_id),
    KEY idx_user_create (user_id, create_time DESC),
    KEY idx_status_expire (status, expire_time),
    CONSTRAINT ck_order_amount CHECK (pay_amount >= 0 AND total_amount >= 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='秒杀订单';
```

三个唯一索引各自对应一类异常：

| 索引 | 拦截的场景 |
| --- | --- |
| `uk_request_no` | MQ 重复投递同一条消息、消费端重试 |
| `uk_activity_sku_user` | Redis 数据丢失后用户重抢、两个不同 request_no 同时到达 |
| `uk_order_no` | 订单号生成碰撞（理论上不该发生，兜底） |

`idx_status_expire` 支撑超时扫描：`WHERE status = 0 AND expire_time < now()`。

`idx_user_create` 用 `create_time DESC`（MySQL 8.0 支持降序索引），
匹配"我的订单"列表的默认排序，避免 filesort。

## 8. 秒杀请求记录

```sql
CREATE TABLE t_seckill_request (
    id           BIGINT       NOT NULL AUTO_INCREMENT,
    request_no   VARCHAR(40)  NOT NULL,
    user_id      BIGINT       NOT NULL,
    activity_id  BIGINT       NOT NULL,
    sku_id       BIGINT       NOT NULL,
    quantity     INT          NOT NULL DEFAULT 1,
    status       TINYINT      NOT NULL DEFAULT 0
                 COMMENT '0=排队中 1=成功 2=库存不足 3=重复购买 4=创建失败 5=已补偿',
    order_no     VARCHAR(40)  DEFAULT NULL,
    fail_reason  VARCHAR(200) DEFAULT NULL,
    trace_id     VARCHAR(64)  DEFAULT NULL,
    create_time  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    update_time  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uk_request_no (request_no),
    KEY idx_status_create (status, create_time),
    KEY idx_user_activity (user_id, activity_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='秒杀请求记录';
```

**成功路径上这张表不在主链路写。** 拿到资格的请求，其状态只写 Redis
（`seckill:req:{a:s}:R...`，`fss.seckill.result-ttl` 默认 30 分钟），本表由消费端在
创建订单时一并写入，用于对账和长期审计。Redis 中存在但本表没有的记录，
就是"排队中但消息丢失"的可疑请求，由资格对账捞出。

**被 Lua 直接拒绝的请求例外，同步写一条。** 它们根本没进 MQ，没有消费端会替它们
补记录；而用户可能在轮询，Redis 结果又只有 30 分钟。这一条 insert 的代价可以接受：
它发生在"已经确定失败"的路径上，此时请求已经不再争抢任何热点资源。
写失败只记日志——不能因为审计记录写不进去，就把"库存不足"换成"系统错误"。

## 10. 库存流水

```sql
CREATE TABLE t_stock_log (
    id           BIGINT       NOT NULL AUTO_INCREMENT,
    biz_no       VARCHAR(40)  NOT NULL           COMMENT '业务号：request_no 或 order_no',
    activity_id  BIGINT       NOT NULL,
    sku_id       BIGINT       NOT NULL,
    change_type  TINYINT      NOT NULL
                 COMMENT '1=预扣 2=确认扣减 3=取消回补 4=补偿回补 5=管理调整',
    quantity     INT          NOT NULL           COMMENT '正=增加 负=减少',
    before_stock INT          DEFAULT NULL,
    after_stock  INT          DEFAULT NULL,
    operator     VARCHAR(64)  DEFAULT NULL,
    remark       VARCHAR(200) DEFAULT NULL,
    create_time  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uk_biz_type (biz_no, change_type),
    KEY idx_activity_sku (activity_id, sku_id, create_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='库存流水';
```

**`uk_biz_type (biz_no, change_type)` 是库存幂等的关键。**
同一订单的"取消回补"只能记一条，重复的回补消息在 insert 时撞唯一键，
消费端捕获 `DuplicateKeyException` 后直接确认消息，不执行 UPDATE。

这比只依赖 `t_order.stock_released` 更强：`stock_released` 的读改写有并发窗口
（两个线程同时读到 0），而唯一键插入是数据库层的原子串行化。

实际实现两者都用：先条件更新 `stock_released` 拿到"我是唯一执行者"的许可，
再插流水。双保险。

## 13. 枚举定义（Java 侧）

全部落库的状态值都在 `fss-common/enums/` 下，统一实现 `CodeEnum` 接口：

```java
public interface CodeEnum {
    int code();
    static <E extends Enum<E> & CodeEnum> E of(Class<E> type, int code) { ... }
}
```

| 枚举 | 对应列 | 取值 |
| --- | --- | --- |
| `OrderStatus` | `t_order.status` | 0 待支付 / 1 已支付 / 2 已取消 / 3 已完成 / 4 退款中 / 5 已退款 |
| `SeckillRequestStatus` | `t_seckill_request.status` | 0 排队中 / 1 秒杀成功 / 2 库存不足 / 3 已参与过 / 4 创建订单失败 / 5 系统繁忙已退回 |
| `ActivityStatus` | `t_seckill_activity.status` | 0 待发布 / 1 待开始 / 2 进行中 / 3 已结束 / 4 已关闭 |
| `WarmupState` | `t_seckill_activity.warmup_state` | 0 未预热 / 1 预热中 / 2 预热完成 / 3 预热失败 |
| `PayStatus` | `t_payment.status` | 0 待支付 / 1 支付成功 / 2 支付失败 / 3 已退款 |
| `StockChangeType` | `t_stock_log.change_type` | 1 预扣 / 2 确认扣减 / 3 取消回补 / 4 补偿回补 / 5 管理调整 |
| `MqStatus` | `t_mq_message.status` | 0 待发送 / 1 已发送 / 2 已消费 / 3 发送失败 |
| `ReconcileTaskType` | `t_reconcile_task.task_type` | 1 资格对账 / 2 库存对账 / 3 支付对账 |
| `ReconcileTaskStatus` | `t_reconcile_task.status` | 0 待处理 / 1 自动修复成功 / 2 需人工处理 / 3 人工已处理 / 4 已忽略 |

```java
public enum SeckillRequestStatus implements CodeEnum {
    QUEUEING(0, "排队中"),
    SUCCESS(1, "秒杀成功"),
    STOCK_NOT_ENOUGH(2, "库存不足"),
    ALREADY_BOUGHT(3, "已参与过本次秒杀"),
    CREATE_FAILED(4, "创建订单失败"),
    COMPENSATED(5, "系统繁忙已退回");
}
```

**状态值一律用显式整数，禁止依赖 `ordinal()`**——枚举顺序调整会静默改变库中已有数据的
语义。`code()` 是唯一的落库表示，`CodeEnum.of(Type.class, code)` 是唯一的反向入口，
遇到未知编码直接抛 `IllegalArgumentException` 而不是返回 null。

**实体里的状态字段声明为 `Integer` 而不是枚举类型**，在 Service 层用 `of()` / `code()`
显式转换。理由是对账与故障排查经常要面对"库里存了一个当前代码不认识的值"——
枚举字段会在 MyBatis 映射阶段就抛异常，整条查询失败，连"这行到底是什么"都看不到；
`Integer` 能把它读出来再由业务代码决定怎么处理。
（`application.yml` 里仍配了 `MybatisEnumTypeHandler` 作为默认处理器，
供将来需要直接映射的字段使用。）

**每个枚举都带一个中文 `desc`**，接口响应里的 `statusDesc` 直接来自它。
让前端自己维护一份码值到文案的映射，等于同一份语义存在两处，改一处忘一处的成本
远大于多传一个字段。

## 14. 订单号与请求号生成

```
订单号:  O + yyyyMMddHHmmss + 3位机器号 + 6位序列
请求号:  R + yyyyMMddHHmmss + 3位机器号 + 6位序列
支付号:  P + yyyyMMddHHmmss + 3位机器号 + 6位序列
消息号:  M + yyyyMMddHHmmss + 3位机器号 + 6位序列
外部交易号: MOCK + T + ...（模拟渠道用）
链路号:  32 位十六进制
```

机器号从环境变量 `FSS_MACHINE_ID`（或系统属性 `fss.machine-id`）取，
缺省由主机名散列得到；Docker 部署时由启动脚本注入。
序列用进程内 `AtomicLong` 对 100 万取模，**起始值随机**——固定从 0 开始的话，
同一秒重启的两个实例会生成完全相同的一串号。

**尾段用递增序列而非随机数**：最初设计写的是"6 位随机"，但在 10000 QPS 下，
同一秒同一机器内 10000 个 6 位随机数发生碰撞的概率约 5%（生日问题），
碰撞会表现为请求号重复被拒或唯一键冲突——一种只在高并发下偶发、极难复现的故障。
改用进程内单调序列后，同机同秒内不可能重复，只有单机单秒超过 100 万请求才会绕回。

**不用纯自增 ID 做业务号**：暴露订单量，且分库后冲突。
**不用 UUID**：无序，作为二级索引会导致 B+ 树频繁页分裂。

## 附 限购数量大于 1 的扩展方案

当前 `limit_per_user = 1` 时，`uk_activity_sku_user` 直接表达一人一单。
若要支持限购 3 件（同一用户可下 3 张独立订单），唯一约束失效，需改为：

```sql
CREATE TABLE t_user_purchase_quota (
    id           BIGINT NOT NULL AUTO_INCREMENT,
    activity_id  BIGINT NOT NULL,
    sku_id       BIGINT NOT NULL,
    user_id      BIGINT NOT NULL,
    limit_qty    INT    NOT NULL,
    used_qty     INT    NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    UNIQUE KEY uk_asu (activity_id, sku_id, user_id),
    CONSTRAINT ck_quota CHECK (used_qty <= limit_qty AND used_qty >= 0)
) ENGINE=InnoDB;
```

消费端在同一事务内执行：

```sql
UPDATE t_user_purchase_quota SET used_qty = used_qty + #{qty}
 WHERE activity_id=? AND sku_id=? AND user_id=? AND used_qty + #{qty} <= limit_qty;
```

影响行数 0 → 超限。同时 `t_order` 的唯一键换成 `uk_request_no` 单键。
本项目第一版不做，`limit_per_user` 固定为 1，启动时校验。
