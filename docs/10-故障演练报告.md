# 10 故障演练报告

阶段五交付物。按 docs/08 §4 的 14 个场景逐个注入，辅助脚本
[`perf/drill.sh`](../perf/drill.sh)，证据在 `docs/drill-evidence/`。

环境：单进程 `web,consumer,job,dev`（**默认配置，不带 perf profile**），
MySQL / Redis / RocketMQ ×2 均为 Docker Desktop 容器，注入手段以 `docker pause` 为主。

## 0. 一句话结论

**14 个场景中 11 个实测通过、2 个被集成测试覆盖但演练侧无法注入、1 个注入方式受限。**
最有力的证据是终态：经历了 pause Redis、`FLUSHDB`、pause MySQL、pause broker、
重复投递 ×10、删除定时消息、三 job 实例并发对账之后，
**9 个活动的库存账目等式 `total = available + locked + sold` 全部成立，一份库存都没漏。**

```
activity  total  available  locked  sold  released  等式
   1       100      100       0      0       2      OK
   4      5000     5000       0      0     109      OK
   5     50000    50000       0      0    6747      OK
   7       100      100       0      0       8      OK
   9        10        9       1      0       0      OK
```

同时也**改正了 docs/08 对 F3 的预期**——那条预期与本地消息表的实际设计不符（见 §3）。

## 2. F1 + F8：一次注入验了两个场景

`docker pause` 的语义是**冻结进程**而不是断开连接——命令在 `unpause` 之后仍会执行，
但客户端早已超时。这恰好制造了真实的"不确定结果"，所以 F1 和 F8 是同一次注入的两面。

**注入**：`docker pause fss-redis`，持续 25s，期间 3 个不同用户各提交一次秒杀。

**观测**：

```
注入前   抢购成功，remain 99
暂停期间 用户101/102/103 全部返回 1005「系统繁忙，请稍后重试」
        活动详情 HTTP 200（允许匿名浏览，走缓存）
恢复后   抢购成功，remain 95        ← 注意：不是 98
```

`remain` 从 99 掉到 95，说明暂停期间那 3 个请求**实际扣了库存**——
`unpause` 后 Lua 照样执行完了，只是结果没能返回给客户端。

**这正是 F8 要测的处境**，而系统的处理完全正确：

```
fss_alarm_total{event="REDIS_UNCERTAIN",severity="P2"}  3.0     ← 3 次登记并告警
seckill:uncertain ZSet                                  空       ← 判定完即 ZREM

t_seckill_request（活动 7）
R...135029  status=1  O...135029111    ← 注入前那单
R...135033  status=1  O...135055118    ← 提交 13:50:33，订单 13:50:55 才建
R...135038  status=1  O...135055121
R...135044  status=1  O...135055123
R...135059  status=1  O...135059127
账目 100 = 95 + 5 + 0  等式成立
```

三条超时请求的订单号时间戳（`135055`）明显晚于请求号（`135033/135038/135044`），
**这就是 `checkUncertain` 在工作**：静置 5 秒后用 `EXISTS req key` 判定为"已扣库存"，
用**同一个 requestNo** 补发消息，订单照样建出来。

用户侧看到的是"系统繁忙请重试"，但他的单其实成了——这个体验不理想，
不过方向是对的：**宁可让他多等一轮轮询，也不能告诉他失败了然后又出一张单。**

**结论**：符合预期，且比预期更好——F1 的 fail-closed 和 F8 的事后判定串成了完整闭环，
5 个请求 5 张订单，零泄漏零超卖。

## 3. F3：文档的预期是错的，实际路径完全不同

这是本次演练最有价值的发现。

**docs/08 §4 原文预期**：「消费端重试，消息不丢；积压上升触发降级；恢复后全部落库」。

**实测**：

```
注入   docker pause fss-mysql，36s，期间 3 个用户提交
响应   全部 1005「系统繁忙，请稍后重试」    ← 不是"排队中"
指标   fss_seckill_request_total{result="mq_persist_failed"}  3.0
      fss_stock_rollback_total{type="compensate"}            4.0
日志   stage=SECKILL_SUBMIT ... result=MQ_PERSIST_FAILED 立即回补  ×3
恢复   5s 内积压清零（本来就没有积压）
账目   100 = 95 + 5 + 0  等式成立，库存未泄漏
```

**为什么**：本地消息表 `t_mq_message` **就在 MySQL 里**。MySQL 挂了，
`INSERT t_mq_message` 直接失败，请求根本走不到"投递"那一步——
触发的是 `SeckillServiceImpl` 里那条"连本地消息表都写不进去 → 必须就地回补"的分支：

> 走到这里说明连本地消息表都写不进去。投递意图彻底没能落盘，
> 没有任何后续机制会为这个用户建订单 → 必须就地回补，否则这一份库存永久泄漏。

所以「消费端重试」根本不会发生：**没有消息被创建**。
文档那条预期描述的是"消息已经发出去了，只是消费端落库失败"的情况，
而那需要 MySQL 在**投递时可用、消费时不可用**——单库部署下这两个时刻用的是同一个 MySQL，
不可能只坏一半。

**F3 与 F4 的对照恰好说明本地消息表的设计取舍**：

| | 消息表能否写入 | 接口返回 | 处置 |
| --- | --- | --- | --- |
| **F3** MySQL 挂 | **不能** | 1005 失败 | 投递意图没存下 → **必须立即回补** |
| **F4** broker 挂 | 能 | **0 排队中** | 意图已存 → 重发任务接手，**可以等** |

把本地消息表放在业务库里换来了"与业务操作同事务"，
代价就是**它与业务库共享可用性**。这不是缺陷，是决策 5 的固有属性，
但 docs/08 §4 的 F3 预期需要按上面这段改正。

**发现的问题**：`docs/08 §4` F3 行的预期与实现不符，已在本报告记录；
真要测"消费端重试"，正确的注入方式是**只停 consumer 实例**（消息已投递、无人消费），
或者把本地消息表放到独立库——后者会牺牲同事务性，不值得。

## 4. F2：Redis 全丢之后，DB 唯一键是最后一道防线

这一组最能回答"为什么有了 Redis 还要留 MySQL 约束"。

**注入**：`FLUSHDB`。

**观测（分四步）**：

```
① FLUSHDB 后立刻抢购            → 2005「活动未预热」        ← 拒绝而不是放行
② 人工 warmup 重建               → Redis stock=95，与 DB available 一致
                                   （setIfAbsent 按 DB 恢复，没有重置回 100）
③ bought 标记                    → HLEN=0，全丢了
④ 已抢过的用户重抢               → Redis **放行**了，remain 掉到 94
   4 秒后账目                    → 100 = 95 + 5 + 0，回到 95
   该活动订单数                  → 仍是 5，没有重复出单
```

第 ④ 步是关键：`bought` 标记丢了，Lua 的一人一单**失效**，Redis 放行了重抢并扣了库存。
但落库时撞上 `uk_activity_sku_user`，消费端判定为确定性失败 → 脚本 B 回补 →
库存回到 95。**Redis 失守，DB 兜住了。**

**发现的问题（文档未提）**：`FLUSHDB` 会连带清掉 `jwt:active:{jti}` 白名单，
于是**所有已登录用户的 token 立即失效**，全部返回 1002。
演练时这一点先把我拦住了——以为是限流或认证坏了。
真实故障中这意味着 Redis 数据丢失不只影响秒杀，还会让全站用户被强制登出。
这是 JWT 主动失效机制（阶段二）与 Redis 单点共享命运的必然结果，
生产上应当把白名单放独立 Redis 实例或独立 DB 编号，
让"秒杀数据丢失"与"全站登出"解耦。

## 5. F4：本地消息表按设计缓冲

**注入**：`docker pause fss-rmq-broker` 14s，期间 2 个用户提交。

**观测**：

```
暂停期间  两次提交都返回 code 0「排队中」，remain 96 → 95
         t_mq_message: status=0（待发送）2 条
恢复后    +50s 未消费数归零
账目      100 = 95 + 5 + 0，released=2
```

接口**没有失败**——这是与 F3 最大的差别，因为消息行已经落盘，
`ReliableMqProducer` 内部吞掉 send 异常、交给 `MqResendJob`。
50 秒的恢复时间来自重发任务 30 秒一轮 + 退避间隔，符合设计。

## 6. F5 + F11：重复投递

**注入**：从 `t_mq_message` 取一条已消费的 ORDER_CREATE 记录，
用 `mqadmin sendMessage` 原样重投 10 次（**确认 10/10 SEND_OK**，不是"以为发了"）。

**观测**：

```
重投前  订单 1 单，t_stock_log(change_type=2) 1 条
重投后  订单 1 单，t_stock_log(change_type=2) 1 条
账目    等式成立
```

幂等 L1（`selectByRequestNo`）命中即 ACK，10 次重投全部走这条路。
`uk_biz_type (biz_no, change_type)` 保证流水也只有一条。

**顺带发现一条真实的死信告警**：演练时为验证 `mqadmin` 可用，
我发了一条 `-k TESTKEY -p "{}"` 的消息。它解析不出 requestNo，
重试耗尽后进死信，`OrderCreateDlqListener` 正确地记录
`result=ROLLBACK_FAILED 转人工` 并发出 `MQ_DLQ` P2 告警。
这是死信兜底路径的一次意外真实验证——**一条格式错误的消息不会静默消失**。

## 7. F12：三实例并发，分布式锁生效

**注入**：额外启动 2 个 `--spring.profiles.active=job` 实例（:8091 / :8092），
与主进程的 job 组成 3 实例，等一轮完整的库存对账 cron（5 分钟）。

**观测**：

```
对账前  t_reconcile_task 2 条
对账后  t_reconcile_task 2 条
重复检查 SELECT task_type,biz_no,COUNT(*) ... HAVING COUNT(*)>1  → 空
```

若 `@DistributedLock` 失效，三个实例会各自扫一遍库存、各写一份差异记录。
任务数不变且无重复，说明每轮只有一个实例真正执行。

用**产出**而不是日志来验证是刻意的：日志格式可能变，
而"有没有重复的对账任务"是这把锁存在的唯一理由——正如 docs/05 里写的
「这里的锁保正确不只省资源」。

## 8. F13：拒绝正确，但告警没测到

**注入**：删掉 Redis 的 `seckill:goods` / `seckill:stock` 两个 key，
并把 `warmup_state` 置 3（预热失败）。

**观测**：

```
抢购        2005「活动未预热，请稍后再试」   ← 核心断言通过
DB 库存     available=49 / total=50，未被动过
WARMUP_FAILED 告警   未出现
```

**核心断言通过**：元数据缺失时**拒绝而不是放行**。放行意味着 Lua 读不到库存却让请求通过，
等于凭空造库存。

**告警没测到是注入方式的局限**，不是缺陷：我是直接 `UPDATE` 数据库把
`warmup_state` 改成 3，没有走 `WarmupService` 的代码路径，
而告警是在那里面发的。要真正验证告警需要 mock 预热抛异常——
`ScheduledJobTest` 里的 F13 用例正是这么做的（「未预热不进 RUNNING」）。

另外原计划的注入（发布活动但不预热，等它自动进 RUNNING）**没能成立**：
预热定时任务在 40 秒内自动跑完了，`warmup_state` 变成 2。
这本身是个好消息——自动预热在工作。

## 9. F14：时间判定的唯一权威是 Redis

**注入**：造一个 30 分钟后才开始的活动，预热后**只修改 Redis 元数据里的 `startTime`**，
不动数据库、不动系统时钟。

**观测**：

```
改之前   Redis TIME = 1787475008000
        goods.startTime = 1787476729000   （还没到）
        抢购 → 2002「活动未开始」

改之后   goods.startTime = 1787474949000  （改成 1 分钟前）
        抢购 → code 0，remain 9           ← 放行了
        而 DB 的 start_time 仍是 2026-08-23 17:18:49（30 分钟后）
```

DB 说没开始，Redis 说开始了，**系统按 Redis 走**。
这正面证明了 docs/03 脚本 A 那段注释的价值：时间判定放在 Lua 内、用 `redis.call('TIME')`，
所以任何一台 web 实例的时钟漂移都影响不了判定——
判定压根不看应用时钟。

反过来说，这也定义了运维边界：**Redis 的时钟成了业务时间的单点**。
它漂了就全漂，但那至少是**一致地漂**，不会出现"实例 A 放行、实例 B 拒绝"的分裂。
一致地错比不一致地错好排查得多，这是刻意的取舍。

## 10. 未演练的三项及其覆盖

| # | 为什么没演练 | 已有覆盖 |
| --- | --- | --- |
| F6 消费者处理中宕机 | 单进程部署，`kill -9` 会把 web 也带走，无法只杀消费端 | `MqReliabilityTest` M3「消费端晚到不丢」——先停消费再投递，重启后订单最终落库 |
| F7 消息发送失败 | 需要 mock `syncSend` 抛异常，容器层注入不了 | `MqReliabilityTest` M4（断开 MQ 堆积后重发）、M5（重发耗尽即回补） |
| F9 支付与取消并发 | 需要精确到毫秒的并发编排，脚本层做不出稳定的竞态 | `OrderLifecycleTest` C10 **×30 轮**、`UncertainAndRefundTest` F9（竞态→自动退款+幂等） |

这三项都是**集成测试比手工演练更可靠**的类型：它们要的是精确时序，
而 `docker pause` / `curl` 的粒度是秒级。写在这里而不是假装演练过。

## 11. 演练暴露的两个真问题

1. **`FLUSHDB` 会连带把全站用户登出**（§4）。JWT 白名单与秒杀数据共享同一个 Redis 实例
   和同一个 DB 编号，Redis 数据丢失的影响范围比"秒杀不可用"大得多。
   修法是把白名单挪到独立实例/独立 database，成本很低，
   但这属于阶段二的设计遗留，本次只记录不改。
2. **`docs/08 §4` 的 F3 预期与实现不符**（§3）。已在本报告改正，
   并给出了正确的注入方式（只停 consumer）。

## 12. 复现

```bash
docker compose --profile phase2 --profile phase3 --profile phase4 up -d
mvn -o clean package -DskipTests
java -jar fss-app/target/fss-app.jar \
  --spring.profiles.active=web,consumer,job,dev --server.port=8080 \
  --spring.datasource.url='jdbc:mysql://127.0.0.1:3307/flash_sale?...'

cd perf
USERS=200 ./run.sh prepare              # 演练要真实用户的 JWT
read A S <<< "$(./drill.sh new 100)"    # 造一个立刻可抢的活动
./drill.sh state $A $S                  # 注入前的基线，别省这一步

docker pause fss-redis                  # F1 + F8
./drill.sh buy $A $S 1
docker unpause fss-redis
./drill.sh state $A $S                  # 对比基线
```

> **每次注入前先 `./drill.sh state` 存一份基线。** 漏了这一步，
> 事后就说不清差异是注入造成的还是本来就有的——
> 本次演练开始时系统里已经有 2 条压测遗留的对账任务和 2 条 P1 告警，
> 没有基线的话它们会被误算到某个 F 用例头上。
