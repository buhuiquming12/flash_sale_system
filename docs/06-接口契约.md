# 06 接口契约

## 1. 统一响应体

```json
{ "code": 0, "message": "ok", "data": { }, "traceId": "a1b2c3d4e5f6" }
```

`code = 0` 表示成功，非 0 见错误码表。`traceId` 始终返回（由 `TraceIdResponseAdvice`
统一注入），便于用户报障时定位。

HTTP 状态码策略：业务失败一律返回 **200 + 非 0 code**，只有以下情况用非 200。
映射集中在 `GlobalExceptionHandler.HTTP_OVERRIDE`：

| HTTP | 错误码 | 场景 |
| --- | --- | --- |
| 401 | `UNAUTHORIZED` | 未登录 / token 失效 / 已登出 |
| 403 | `FORBIDDEN` | 权限不足（非管理员访问 `/api/admin/**`） |
| 429 | `RATE_LIMITED` | 限流拒绝（带 `Retry-After: 1` 头） |
| 503 | `SERVICE_DEGRADED` | 服务降级中 |

限流用 429 而非 200，是为了让 Nginx、网关、客户端 SDK 能按标准语义自动退避。

**"排队中"不是 202，而是 200 + `status = 0`。** 秒杀提交在协议层是成功的：
服务端确实受理并给了结论（资格已分配），只是订单还没落库。用 202 会让"已受理"
和"业务成功"共用一个状态码，客户端必须同时看 HTTP 状态和响应体两处才能判断，
而 `status` 字段本来就要看。

分段：1xxx 通用 / 2xxx 活动商品 / 3xxx 秒杀 / 4xxx 订单 / 5xxx 支付 / 9xxx 系统。

`isDeterministic()` 的划分（决定消费端失败后是重试还是补偿）：

```java
// 确定性失败：重试也不会成功 → 立即补偿回补并 ACK
private static final Set<ErrorCode> DETERMINISTIC = EnumSet.of(
        STOCK_NOT_ENOUGH, ALREADY_BOUGHT, GOODS_NOT_FOUND,
        ACTIVITY_ENDED, PARAM_INVALID);
// 其余（DB 连接失败、超时、未知异常）视为可恢复 → 抛出触发 MQ 重试
```

`REQUEST_DUPLICATED` **不在**这个集合里：它意味着同一 requestNo 被并发处理、
另一方已经建了单，消费端应当直接 ACK 而不是回补——回补会把赢家刚拿到的资格退掉。
处理在 `OrderCreateListener` 里单列一支。

## 3. 用户接口

### 3.1 注册

```
POST /api/user/register
{ "username": "alice", "password": "Passw0rd!", "phone": "13800001111",
  "nickname": "Alice" }
→ { "code": 0, "data": { "userId": 10086 } }
```

用户名 3~32 位，只允许字母、数字、下划线。密码 8~32 位且必须同时含大小写字母与数字
（正则 `^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).+$`）。服务端 BCrypt 加密存储。
`phone` 与 `nickname` 可选。

### 3.2 登录

```
POST /api/user/login
{ "username": "alice", "password": "Passw0rd!" }
→ { "code": 0, "data": { "token": "eyJ...", "expiresIn": 7200,
                         "userId": 10086, "username": "alice", "role": 0 } }
```

JWT payload 只含 `userId / role / exp / jti`，不含手机号等敏感信息。
`jti` 写入 Redis 白名单（`jwt:active:{jti}`）支持主动登出与踢下线。
`role` 一并返回，前端据此决定是否显示管理入口——**但这只是显示控制，
权限判定在服务端的 `AdminAuthFilter`**。

### 3.3 当前用户

```
GET /api/user/me                       Header: Authorization: Bearer <token>
→ { "code": 0, "data": { "userId": 10086, "username": "alice",
                         "nickname": "Alice", "role": 0, "status": 1 } }
```

### 3.4 登出

```
POST /api/user/logout                  Header: Authorization: Bearer <token>
→ { "code": 0 }
```

从请求头里的 token 解析 `jti` 并删除白名单 key，即刻生效。

**阶段一没有这个接口**：JWT 是无状态的，签发后在过期前天然无法撤销，没有白名单时
"登出"只能靠客户端自己丢掉 token。提供一个什么都不做的登出接口比不提供更糟——
调用方会以为会话真的结束了。

## 4. 活动与商品接口

### 4.1 活动列表

```
GET /api/activity/list?status=2&page=1&size=10
→ { "code": 0, "data": { "total": 3, "page": 1, "size": 10, "list": [
      { "activityId": 1001, "name": "iPhone 秒杀专场",
        "startTime": "2026-08-20 20:00:00", "endTime": "2026-08-20 20:30:00",
        "status": 2, "statusDesc": "进行中", "goodsCount": 2 } ] } }
```

`status` 可选，缺省返回全部；**草稿（`status = 0`）永不出现在这个列表里**——
它是运营还没发布的东西。`size` 服务端强制封顶 50，防止一次拉全表。
按 `start_time` 倒序。时间格式由 `spring.jackson.date-format` 统一成
`yyyy-MM-dd HH:mm:ss`（时区 `Asia/Shanghai`）。

### 4.2 活动详情

```
GET /api/activity/{activityId}
→ { "code": 0, "data": {
      "activityId": 1001, "name": "iPhone 秒杀专场",
      "startTime": "...", "endTime": "...", "status": 2, "statusDesc": "进行中",
      "serverTime": "2026-08-20 19:59:58",
      "goodsList": [
        { "skuId": 2001, "productTitle": "iPhone 16 Pro", "spec": "黑色/256G",
          "originPrice": 7999.00, "seckillPrice": 4999.00,
          "totalStock": 1000, "remainStock": 873, "stockLevel": "AVAILABLE",
          "limitPerUser": 1, "soldOut": false, "image": "https://..." } ] } }
```

**`serverTime` 必须返回**：客户端倒计时应基于服务端时间校准本地时钟偏差，
否则用户本地时间快 30 秒就会在活动未开始时疯狂提交，全部被拒。

**详情里的 `status` 由 `serverTime` 现算**（未开始 / 进行中 / 已结束），不直接用库里那个
由定时任务推进的值——状态推进是每分钟一轮的，而活动开始那一刻用户就在刷页面。
已被管理员关闭（`CLOSED`）的活动不参与现算。

`remainStock` 是近似值（读 Redis，无锁），仅用于展示。真实结论以秒杀接口为准。
读 Redis 失败时退回缓存里的 DB 快照，不让详情接口跟着挂。

`stockLevel` 是 `remainStock` 的分档：`AVAILABLE` / `LOW`（剩余 ≤ 20%）/ `SOLD_OUT`。
**降级 Level 1 起 `remainStock` 置 null、只下发 `AVAILABLE` / `SOLD_OUT`**：
这一档省掉的正是上面 per-SKU 的 Redis 读——一个活动 10 个 SKU 就是 10 次往返，
而详情接口是全站 QPS 最高的。降级期间"大概还有货"这个精度够用。

### 4.3 获取秒杀令牌

```
POST /api/seckill/token?activityId=1001&skuId=2001
→ { "code": 0, "data": { "token": "a3f9...", "path": "/api/seckill/a3f9.../do" } }
```

令牌绑定 `userId + activityId + skuId`，Redis 存 `seckill:token:{uid}:{aid}:{sid}`，
TTL 见 `fss.seckill.token-ttl`（默认 5 分钟），**`GETDEL` 一次性消费**。
同时返回动态路径，提高脚本直接刷固定 URL 的成本。

该接口与提交秒杀共用同一个用户级令牌桶（`fss.ratelimit.user-qps`），
因为"领令牌"和"提交"都属于抢购动作。

**令牌不是安全措施**，它只提高脚本作者的成本：真正的防线是限流与一人一单。

## 5. 秒杀接口

### 5.1 提交秒杀

```
POST /api/seckill/{token}/do              ← 动态路径，校验并消费令牌
POST /api/seckill/do                      ← 固定路径，不校验令牌；仅当
                                             fss.seckill.allow-tokenless-submit=true
                                             时可用（默认 false，dev/perf 打开），
                                             关闭时返回 403
Header: Authorization: Bearer <jwt>
{ "activityId": 1001, "skuId": 2001, "quantity": 1 }

→ 200 已受理（资格已分配，订单异步创建）
{ "code": 0, "data": { "requestNo": "R20260820200000001123456",
                       "status": 0, "statusDesc": "排队中",
                       "remainStock": 872,
                       "pollAfterMs": 300 } }

→ 200 库存不足
{ "code": 3001, "message": "库存不足", "traceId": "..." }

→ 200 重复购买
{ "code": 3002, "message": "您已参与过本次秒杀", "traceId": "..." }

→ 429 限流
{ "code": 1004, "message": "请求过于频繁" }        Header: Retry-After: 1

→ 503 降级
{ "code": 1006, "message": "服务降级中，请稍后再试" }
```

**固定路径为什么留着**：JMeter 脚本不必先取令牌再拼路径，否则压测测的一半是令牌
接口的性能。**生产环境应当在网关层只放开动态路径**，把这个入口挡在外面——
代码里保留而部署时屏蔽，比为了安全把压测入口删掉、然后每次压测再临时改代码要可靠。

**用户 ID 只从 JWT 取，请求体不接受 userId 字段。** 若请求体带了该字段，
直接返回 `PARAM_INVALID`，而非静默忽略——静默忽略会掩盖客户端 bug。

`quantity` 校验：必须为正整数且 ≤ `limit_per_user`。当前固定为 1，
传其他值返回 `PARAM_INVALID`。

`remainStock` 取自 Redis 而非 DB：Redis 才是资格分配的权威，而异步化之后
DB 的 `available_stock` 会滞后于真实可抢量，两者的差值正是"排队中"的量。

`pollAfterMs` 由降级开关下发（`fss.degrade.poll-interval-ms`，Level 2 起换成
`degraded-poll-interval-ms`）。服务端能在压力大时统一拉长客户端轮询间隔——
这是一个软限流手段，比只在服务端拒绝更友好，而且不用发版。

### 5.2 查询秒杀结果

```
GET /api/seckill/result?requestNo=R2026...&activityId=1001&skuId=2001

→ 排队中
{ "code": 0, "data": { "requestNo": "R...", "status": 0, "statusDesc": "排队中",
                       "pollAfterMs": 500 } }
→ 成功
{ "code": 0, "data": { "requestNo": "R...", "status": 1, "statusDesc": "秒杀成功",
                       "orderNo": "O20260820200001001", "pollAfterMs": 0 } }
→ 失败
{ "code": 0, "data": { "requestNo": "R...", "status": 2, "statusDesc": "库存不足",
                       "failReason": "库存不足", "pollAfterMs": 0 } }
→ 已补偿
{ "code": 0, "data": { "requestNo": "R...", "status": 5, "statusDesc": "系统繁忙已退回",
                       "failReason": "消息登记失败，已退回", "pollAfterMs": 0 } }
→ 请求号不存在，或不属于当前用户
{ "code": 3005, "message": "秒杀请求不存在" }
```

`pollAfterMs = 0` 表示已是终态，客户端应停止轮询。

`activityId` 与 `skuId` 是**可选**参数，但强烈建议带上：带了才能命中 Redis 里的
请求结果（key 含 `{activityId:skuId}` hash tag，无法从 `requestNo` 反推），
不带就得回查数据库。客户端刚提交过秒杀，这两个值它一定有。

**不属于自己的请求号返回 `REQUEST_NOT_FOUND` 而不是 `FORBIDDEN`**：
用两个不同的码区分"不存在"和"不属于你"，等于告诉攻击者哪些请求号是有效的。

服务端对结果查询接口单独限流（`fss.ratelimit.result-qps`，默认 5 QPS），
防止客户端轮询 bug 打成 DDoS。

## 6. 订单接口

### 6.1 我的订单列表

```
GET /api/order/list?status=0&page=1&size=10
→ { "code": 0, "data": { "total": 2, "page": 1, "size": 10, "list": [
      { "orderNo": "O2026...", "status": 0, "statusDesc": "待支付",
        "totalAmount": 7999.00, "payAmount": 4999.00, "quantity": 1,
        "expireTime": "2026-08-20 20:15:00", "createTime": "2026-08-20 20:00:00",
        "remainSeconds": 842,
        "items": [ { "skuId": 2001, "productTitle": "iPhone 16 Pro",
                     "spec": "黑色/256G", "unitPrice": 4999.00,
                     "quantity": 1, "image": "..." } ] } ] } }
```

`remainSeconds` 服务端计算，客户端不用自己算（避免时钟问题）。
`totalAmount` 是 SKU 原价合计、`payAmount` 是秒杀价合计，前端据此显示优惠金额。

### 6.2 订单详情

```
GET /api/order/{orderNo}
```

必须校验 `order.userId == currentUserId`，否则返回 `ORDER_NOT_OWNED`。
**不要返回 404**——用 404 区分"不存在"和"不属于你"会泄漏订单号是否有效。

### 6.3 取消订单

```
POST /api/order/{orderNo}/cancel
→ { "code": 0, "data": { "cancelled": true,
      "notice": "订单已取消，库存已释放给其他用户；本次活动您已不能再次参与" } }
→ { "code": 4002, "message": "订单状态不允许该操作" }
```

只有 `PENDING_PAY` 可取消。取消后库存回补，但**该用户不能再抢**（决策 1），
所以响应里带 `notice` 明确告知，避免用户反复尝试。

## 7. 支付接口（模拟）

### 7.1 创建支付

```
POST /api/pay/create
{ "orderNo": "O2026..." }
→ { "code": 0, "data": { "payNo": "P2026...", "amount": 4999.00,
                         "payUrl": "/mock-pay.html?payNo=P2026..." } }
```

重复调用返回同一个待支付流水（按 `order_no + status=0` 查询复用），
不产生多条流水。

### 7.2 支付回调（模拟渠道回调）

```
POST /api/pay/notify
{ "payNo": "P2026...", "outTradeNo": "MOCK_20260820...", "amount": 4999.00,
  "status": "SUCCESS", "timestamp": 1755691200000, "sign": "..." }
→ { "code": 0 }
```

签名算法：`HMAC-SHA256(按 key 升序拼接的 kv 串, fss.pay.notify-secret)`。
校验顺序：**先验签 → 再验时间戳（`fss.pay.notify-tolerance`，默认 5 分钟）→
再查流水 → 再比金额 → 最后改状态。** 验签失败直接 `PAY_SIGN_INVALID`，
不透露任何订单信息。

时间戳校验防重放。同一 `outTradeNo` 重复回调靠 `uk_out_trade_no` 幂等。

### 7.3 查询支付状态

```
GET /api/pay/status?orderNo=O2026...
→ { "code": 0, "data": { "orderNo": "...", "orderStatus": 1, "orderStatusDesc": "已支付",
                         "payStatus": 1, "payStatusDesc": "支付成功",
                         "payTime": "2026-08-20 20:03:11" } }
```

### 7.4 回调验签辅助（仅 dev）

```
GET /api/pay/mock-sign?payNo=P2026...&amount=4999.00&status=SUCCESS
→ { "code": 0, "data": { "payNo": "P2026...", "outTradeNo": "MOCK_...",
                         "amount": "4999.00", "status": "SUCCESS",
                         "timestamp": "1755691200000", "sign": "..." } }
```

返回的就是一份可直接 POST 给 `/api/pay/notify` 的完整报文（`outTradeNo` 不传则
自动生成）。演示前端与联调脚本靠它拿到合法签名，不必在客户端复制一份 HMAC 实现和密钥。

`@Profile("dev")` 标在**类**上而不是方法上——Spring 只在 Bean 定义层面处理
`@Profile`，写在方法上不生效，那样这个接口会在生产环境裸奔。

## 8. 管理接口

全部要求 `role = 1`（由 `AdminAuthFilter` 按 `/api/admin/` 前缀统一拦截），
变更类操作写 `t_admin_log`。

```
POST   /api/admin/product                  创建商品
POST   /api/admin/sku                      创建 SKU
GET    /api/admin/sku/list?productId=      查询某商品下的 SKU（配活动时选货用）
POST   /api/admin/activity                 创建活动（草稿，含秒杀商品列表）
POST   /api/admin/activity/{id}/publish    发布（DRAFT → READY，校验合法性）
POST   /api/admin/activity/{id}/close      关闭活动（任意状态 → CLOSED）
POST   /api/admin/activity/{id}/warmup     手动触发预热（幂等）
POST   /api/admin/goods/{id}/stock-adjust  库存调整（活动中改库存的唯一入口）
GET    /api/admin/degrade                  查看降级状态
POST   /api/admin/degrade                  人工设置降级等级
```

**秒杀商品随活动一次创建**（`ActivityCreateCmd` 内嵌 `SeckillGoodsCmd` 列表），
没有单独的"添加商品"接口：活动与其商品必须一起校验（库存不超 SKU、秒杀价不高于
日常价、时间段不冲突），分两次提交会产生"活动已建但没有商品"的中间状态，
而 `publish` 又必须拒绝这种活动。

**没有"修改活动"接口**。改时间等于改一场已经宣传出去的活动，正确做法是关闭重建。
留一个只在 DRAFT 下可用的修改接口，收益不足以抵掉"哪些字段在哪个状态可改"
这一整套状态×字段的判定。

### 降级开关

```
POST /api/admin/degrade
{ "level": 3, "reason": "大促前手动收紧" }
→ { "code": 0, "data": { "level": 3, "autoLevel": 0, "seckillEnabled": false,
                         "showExactStock": false, "browseEnabled": true,
                         "pollIntervalMs": 2000 } }
```

写的是 `degrade:level`（人工那一半，**无 TTL**），生效等级取人工与自动的最大值，
所以自动监控恢复到 0 也盖不过人的决定；解除需要显式再调一次并传 0。
`reason` 必填并写入审计——降级是会被复盘的操作，"谁在什么时候因为什么降的级"
必须查得出来。等级语义见 [07 §4](07-防护与可观测.md)。

### 发布校验

`publish` 只接受 `DRAFT` 状态，逐项校验后用条件更新推进到 `READY`：

```java
Assert.require(act.getStatus() == ActivityStatus.DRAFT.code(),
        ErrorCode.ACTIVITY_STATUS_ILLEGAL, "只有草稿状态的活动可以发布");
Assert.require(act.getEndTime().isAfter(act.getStartTime()),   "结束时间必须晚于开始时间");
Assert.require(act.getStartTime().isAfter(LocalDateTime.now()), "开始时间必须晚于当前时间");

List<SeckillGoods> goodsList = goodsMapper.selectByActivity(activityId);
Assert.require(!goodsList.isEmpty(),                            "活动必须包含商品");
for (SeckillGoods g : goodsList) {
    Assert.require(g.getSeckillPrice().signum() > 0,            "秒杀价必须大于 0");
    Assert.require(g.getTotalStock() > 0,                       "秒杀库存必须大于 0");
    Assert.require(g.getLimitPerUser() == 1,                    "当前版本限购必须为 1");
    Sku sku = productService.getSku(g.getSkuId());
    Assert.require(sku != null && sku.getStatus() == 1,
            ErrorCode.SKU_NOT_FOUND,                            "SKU 不存在或已下架");
    Assert.require(g.getTotalStock() <= sku.getStock(),          "秒杀库存不能超过 SKU 可用库存");
    Assert.require(g.getSeckillPrice().compareTo(sku.getPrice()) <= 0, "秒杀价不应高于日常价");
    // 同一 SKU 时间段冲突检测
    Assert.require(activityMapper.countOverlapping(g.getSkuId(),
            act.getStartTime(), act.getEndTime(), activityId) == 0,
            "该 SKU 在此时间段已参加其他活动");
}

// 状态推进也要条件更新：校验与更新之间可能有人并发关了这个活动
int rows = activityMapper.updateStatus(activityId,
        ActivityStatus.DRAFT.code(), ActivityStatus.READY.code());
if (rows == 0) {
    throw new BizException(ErrorCode.ACTIVITY_STATUS_ILLEGAL, "活动状态已变更，请刷新重试");
}
```

**发布不等于预热完成。** 阶段一这里会顺手 `markWarmupDone` 充当预热的替身，
因为定时任务推进到 `RUNNING` 的条件里有 `warmup_state = 2`。阶段二有了真正的预热
任务之后这个替身**必须移除**——留着它会让"未预热的活动不进入 RUNNING"
（故障用例 F13）这条保护彻底失效：活动到点开抢，而 Redis 里什么都没有，
全部请求返回 `GOODS_NOT_WARMED`。

时间段冲突检测的 SQL：

```sql
SELECT COUNT(1) FROM t_seckill_activity a
  JOIN t_seckill_goods g ON g.activity_id = a.id
 WHERE g.sku_id = #{skuId}
   AND a.id <> #{excludeId}
   AND a.status IN (1, 2)
   AND a.start_time < #{endTime}
   AND a.end_time   > #{startTime};
```

区间重叠的标准判定是 `a.start < b.end AND a.end > b.start`。
写成 `a.start BETWEEN b.start AND b.end` 会漏掉 b 完全包含在 a 内的情况。

### 库存调整

```
POST /api/admin/goods/{id}/stock-adjust
{ "delta": 200, "reason": "追加库存" }
```

同一事务内：

```java
@Transactional(rollbackFor = Exception.class)
public void adjustStock(long goodsId, int delta, String reason, long adminId) {
    Assert.require(delta != 0, "调整量不能为 0");

    // 管理操作低频，可以用行锁把"读当前值"和"改"串起来，拿到准确的 before/after
    SeckillGoods g = goodsMapper.selectByIdForUpdate(goodsId);
    Assert.requireFound(g, ErrorCode.GOODS_NOT_FOUND);
    Assert.require(g.getAvailableStock() + delta >= 0, "调整后可售库存不能为负");

    int rows = goodsMapper.adjustStock(goodsId, delta);
    //  UPDATE t_seckill_goods
    //     SET total_stock = total_stock + #{delta},
    //         available_stock = available_stock + #{delta},
    //         status = CASE WHEN status = 2 AND #{delta} > 0 THEN 1 ELSE status END
    //   WHERE id = #{id} AND available_stock + #{delta} >= 0
    Assert.require(rows == 1, "库存调整失败，请重试");

    stockLogMapper.insert(StockLog.of("ADJ-" + goodsId + "-" + System.nanoTime(),
            StockChangeType.MANUAL_ADJUST, delta, g.getActivityId(), g.getSkuId(),
            g.getAvailableStock(), g.getAvailableStock() + delta,
            "admin:" + adminId, reason));

    // Redis 加库存与详情缓存失效都放在提交之后
    adjustRedisStockAfterCommit(g.getActivityId(), g.getSkuId(), delta);
    evictDetailAfterCommit(g.getActivityId());

    audit.record(adminId, "STOCK_ADJUST", "SECKILL_GOODS", goodsId,
            String.valueOf(g.getAvailableStock()),
            String.valueOf(g.getAvailableStock() + delta));
}
```

`total_stock` 与 `available_stock` 同步调整，保证库存对账等式仍然成立。
只改 `available_stock` 会让对账任务立刻报差异。

**库存流水的 `biz_no` 用 `ADJ-{goodsId}-{纳秒}`**：`uk_biz_type (biz_no, change_type)`
对同一 `biz_no` 只允许一条同类型流水，而管理员可能对同一个商品多次追加库存。
业务号必须每次不同，否则第二次追加会撞唯一键。

**缓存失效放在提交之后**：提交前删缓存的话，删除与提交之间进来的读请求会回源读到
**旧**数据（事务还没提交，它看不到新值）并把旧值重新写进缓存——缓存里于是留下
一份永远不会自愈的脏数据，直到 TTL 到期。这个窗口只有几毫秒，
但在活动开抢前的管理操作上，几毫秒里可能有上万次读。

## 9. 参数校验

用 Jakarta Validation，在 DTO 上声明，`@Valid` 在 Controller 参数上生效。

```java
@Data
public class SeckillSubmitReq {
    @NotNull @Positive          private Long    activityId;
    @NotNull @Positive          private Long    skuId;
    @NotNull @Min(1) @Max(1)    private Integer quantity = 1;   // 当前版本仅支持 1
    @Null(message = "不允许指定 userId")
                                private Long    userId;         // 显式拒绝
    private String token;                                       // 动态路径下由路径变量覆盖
}
```

`@Null` 标注 `userId` 是一个防御设计：显式告诉调用方"这个字段由服务端决定"，
而不是悄悄忽略。静默忽略会掩盖客户端 bug——调用方以为自己在替别人下单，
实际被换成了 token 里的用户，等到出问题才发现。

全局异常处理把校验失败统一转成 `PARAM_INVALID` + 具体字段信息：

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public R<Void> handleValid(MethodArgumentNotValidException e) {
    return R.fail(ErrorCode.PARAM_INVALID, fieldErrors(e.getBindingResult().getFieldErrors()));
}

@ExceptionHandler(BindException.class)     // 查询参数绑定失败走这一支
public R<Void> handleBind(BindException e) {
    return R.fail(ErrorCode.PARAM_INVALID, fieldErrors(e.getBindingResult().getFieldErrors()));
}

private String fieldErrors(List<FieldError> errors) {
    return errors.stream()
            .map(f -> f.getField() + ": " + f.getDefaultMessage())
            .collect(Collectors.joining("; "));
}
```

`MethodArgumentNotValidException`（`@RequestBody`）与 `BindException`（查询参数）
是两个不同的异常，只处理前者会让 `@RequestParam` 上的校验失败直接冒成 500。
