# 06 接口契约

## 1. 统一响应体

```json
{ "code": 0, "message": "ok", "data": { }, "traceId": "a1b2c3d4e5f6" }
```

`code = 0` 表示成功，非 0 见错误码表。`traceId` 始终返回，便于用户报障时定位。

HTTP 状态码策略：业务失败一律返回 **200 + 非 0 code**，只有以下情况用非 200：

| HTTP | 场景 |
| --- | --- |
| 401 | 未登录 / token 失效 |
| 403 | 权限不足 |
| 429 | 限流拒绝（配 `Retry-After` 头） |
| 202 | 秒杀已受理（排队中） |
| 503 | 服务降级 / 熔断 |

限流用 429 而非 200，是为了让 Nginx、网关、客户端 SDK 能按标准语义自动退避。

```java
// 确定性失败：重试也不会成功 → 立即补偿回补

        STOCK_NOT_ENOUGH, ALREADY_BOUGHT, GOODS_NOT_FOUND,
        ACTIVITY_ENDED, PARAM_INVALID);
// 其余（DB 连接失败、超时、未知异常）视为可恢复 → 抛出触发 MQ 重试
```

## 3. 用户接口

### 3.1 注册

```
POST /api/user/register
{ "username": "alice", "password": "Passw0rd!", "phone": "13800001111" }
→ { "code": 0, "data": { "userId": 10086 } }
```

密码策略：8~32 位，含大小写与数字。服务端 BCrypt 加密。

### 3.2 登录

```
POST /api/user/login
{ "username": "alice", "password": "Passw0rd!" }
→ { "code": 0, "data": { "token": "eyJ...", "expiresIn": 7200, "userId": 10086 } }
```

JWT payload 只含 `userId / role / exp / jti`，不含手机号等敏感信息。
`jti` 写入 Redis（`jwt:active:{jti}`）支持主动登出与踢下线。

### 3.3 当前用户

```
GET /api/user/me                       Header: Authorization: Bearer <token>
→ { "code": 0, "data": { "userId": 10086, "username": "alice", "status": 1 } }
```

## 4. 活动与商品接口

### 4.1 活动列表

```
GET /api/activity/list?page=1&size=10&status=2
→ { "code": 0, "data": { "total": 3, "list": [
      { "activityId": 1001, "name": "iPhone 秒杀专场",
        "startTime": "2026-08-20T20:00:00", "endTime": "2026-08-20T20:30:00",
        "status": 2, "goodsCount": 2 } ] } }
```

缓存 5 分钟，允许轻微延迟。

### 4.2 活动详情

```
GET /api/activity/{activityId}
→ { "code": 0, "data": {
      "activityId": 1001, "name": "iPhone 秒杀专场",
      "startTime": "...", "endTime": "...", "status": 2,
      "serverTime": "2026-08-20T19:59:58.120",
      "goodsList": [
        { "skuId": 2001, "productTitle": "iPhone 16 Pro", "spec": "黑色/256G",
          "originPrice": "7999.00", "seckillPrice": "4999.00",
          "totalStock": 1000, "remainStock": 873, "limitPerUser": 1,
          "soldOut": false, "image": "https://..." } ] } }
```

**`serverTime` 必须返回**：客户端倒计时应基于服务端时间校准本地时钟偏差，
否则用户本地时间快 30 秒就会在活动未开始时疯狂提交，全部被拒。

`remainStock` 是近似值（读 Redis，无锁），仅用于展示。真实结论以秒杀接口为准。

### 4.3 获取秒杀令牌

```
POST /api/seckill/token
{ "activityId": 1001, "skuId": 2001 }
→ { "code": 0, "data": { "token": "a3f9...", "expiresIn": 300, "path": "/api/seckill/a3f9.../do" } }
```

令牌绑定 `userId + activityId + skuId`，Redis 存 `seckill:token:{uid}:{aid}:{sid}`，
TTL 5 分钟，**一次性消费**。同时返回动态路径，提高脚本直接刷固定 URL 的成本。

该接口本身也限流（单用户 1 QPS），并可挂验证码。

## 5. 秒杀接口

### 5.1 提交秒杀

```
POST /api/seckill/{token}/do
Header: Authorization: Bearer <jwt>
{ "activityId": 1001, "skuId": 2001, "quantity": 1 }

→ 202 Accepted
{ "code": 0, "data": { "requestNo": "R20260820200000001123456",
                       "status": 0, "statusDesc": "排队中",
                       "remainStock": 872,
                       "pollAfterMs": 300 } }

→ 200 库存不足
{ "code": 3001, "message": "库存不足", "traceId": "..." }

→ 200 重复购买
{ "code": 3002, "message": "您已参与过本次秒杀", "traceId": "..." }

→ 429 限流
{ "code": 1004, "message": "请求过于频繁" }        Header: Retry-After: 1
```

**用户 ID 只从 JWT 取，请求体不接受 userId 字段。** 若请求体带了该字段，
直接返回 `PARAM_INVALID`，而非静默忽略——静默忽略会掩盖客户端 bug。

`quantity` 校验：必须为正整数且 ≤ `limit_per_user`。当前固定为 1，
传其他值返回 `PARAM_INVALID`。

### 5.2 查询秒杀结果

```
GET /api/seckill/result?requestNo=R2026...&activityId=1001&skuId=2001

→ 排队中
{ "code": 0, "data": { "requestNo": "R...", "status": 0, "statusDesc": "排队中",
                       "pollAfterMs": 500 } }
→ 成功
{ "code": 0, "data": { "requestNo": "R...", "status": 1, "statusDesc": "秒杀成功",
                       "orderNo": "O20260820200001001", "expireTime": "2026-08-20T20:15:00" } }
→ 失败
{ "code": 0, "data": { "requestNo": "R...", "status": 2, "statusDesc": "库存不足",
                       "failReason": "库存不足" } }
→ 已补偿
{ "code": 0, "data": { "requestNo": "R...", "status": 5, "statusDesc": "系统繁忙已退回",
                       "failReason": "订单消息投递失败，已回补" } }
```

`pollAfterMs` 由服务端下发，让服务端能在压力大时统一拉长客户端轮询间隔——
这是一个软限流手段，比只在服务端拒绝更友好。

需要 `activityId` 和 `skuId` 是因为 Redis key 带 hash tag，无法从 `requestNo`
反推。也可以把它们编码进 `requestNo`，但会让请求号变长且泄漏活动 ID。

## 6. 订单接口

### 6.1 我的订单列表

```
GET /api/order/list?page=1&size=10&status=0
→ { "code": 0, "data": { "total": 2, "list": [
      { "orderNo": "O2026...", "status": 0, "statusDesc": "待支付",
        "payAmount": "4999.00", "expireTime": "2026-08-20T20:15:00",
        "remainSeconds": 842,
        "items": [ { "productTitle": "iPhone 16 Pro", "spec": "黑色/256G",
                     "unitPrice": "4999.00", "quantity": 1, "image": "..." } ] } ] } }
```

`remainSeconds` 服务端计算，客户端不用自己算（避免时钟问题）。

### 6.2 订单详情

```
GET /api/order/{orderNo}
```

必须校验 `order.userId == currentUserId`，否则返回 `ORDER_NOT_OWNED`。
**不要返回 404**——用 404 区分"不存在"和"不属于你"会泄漏订单号是否有效。

### 6.3 取消订单

```
POST /api/order/{orderNo}/cancel
→ { "code": 0, "data": { "cancelled": true } }
→ { "code": 4002, "message": "订单状态不允许取消" }
```

只有 `PENDING_PAY` 可取消。取消后库存回补，但**该用户不能再抢**（决策 1），
响应中应带提示文案：`"message": "订单已取消，库存已释放给其他用户"`。

## 7. 支付接口（模拟）

### 7.1 创建支付

```
POST /api/pay/create
{ "orderNo": "O2026..." }
→ { "code": 0, "data": { "payNo": "P2026...", "amount": "4999.00",
                         "payUrl": "/mock-pay.html?payNo=P2026..." } }
```

重复调用返回同一个待支付流水（按 `order_no + status=0` 查询复用），
不产生多条流水。

### 7.2 支付回调（模拟渠道回调）

```
POST /api/pay/notify
{ "payNo": "P2026...", "outTradeNo": "MOCK_20260820...", "amount": "4999.00",
  "status": "SUCCESS", "timestamp": 1755691200000, "sign": "..." }
→ { "code": 0 }
```

签名算法：`HMAC-SHA256(按 key 升序拼接的 kv 串, secret)`。
校验顺序：**先验签 → 再验时间戳（5 分钟内）→ 再查流水 → 再比金额 → 最后改状态。**
验签失败直接 `PAY_SIGN_INVALID`，不透露任何订单信息。

时间戳校验防重放。同一 `outTradeNo` 重复回调靠 `uk_out_trade_no` 幂等。

### 7.3 查询支付状态

```
GET /api/pay/status?orderNo=O2026...
→ { "code": 0, "data": { "orderNo": "...", "orderStatus": 1, "payStatus": 1,
                         "payTime": "2026-08-20T20:03:11" } }
```

### 发布校验

`publish` 时必须校验：

```java
require(act.getEndTime().isAfter(act.getStartTime()),          "结束时间必须晚于开始时间");
require(act.getStartTime().isAfter(LocalDateTime.now()),        "开始时间必须晚于当前时间");
require(!goodsList.isEmpty(),                                   "活动必须包含商品");
for (SeckillGoods g : goodsList) {
    require(g.getSeckillPrice().signum() > 0,                    "秒杀价必须大于 0");
    require(g.getTotalStock() > 0,                              "秒杀库存必须大于 0");
    require(g.getLimitPerUser() == 1,                           "当前版本限购必须为 1");
    Sku sku = skuMapper.selectById(g.getSkuId());
    require(sku != null && sku.getStatus() == 1,                 "SKU 不存在或已下架");
    require(g.getTotalStock() <= sku.getStock(),                 "秒杀库存不能超过 SKU 可用库存");
    require(g.getSeckillPrice().compareTo(sku.getPrice()) <= 0,  "秒杀价不应高于日常价");
    // 同一 SKU 时间段冲突检测
    require(activityMapper.countOverlapping(g.getSkuId(),
            act.getStartTime(), act.getEndTime(), act.getId()) == 0,
            "该 SKU 在此时间段已参加其他活动");
}
```

时间段冲突检测的 SQL：

```sql
SELECT COUNT(1) FROM t_seckill_activity a
  JOIN t_seckill_goods g ON g.activity_id = a.id
 WHERE g.sku_id = #{skuId}
   AND a.id <> #{excludeId}
   AND a.status IN (1, 2)
   AND a.start_time < #{endTime}
   AND a.end_time   > #{startTime};
```

区间重叠的标准判定是 `a.start < b.end AND a.end > b.start`。
写成 `a.start BETWEEN b.start AND b.end` 会漏掉 b 完全包含在 a 内的情况。

### 库存调整

```
POST /api/admin/goods/{id}/stock-adjust
{ "delta": 200, "reason": "追加库存" }
```

同一事务内：

```java
@Transactional
public void adjustStock(long goodsId, int delta, String reason, long adminId) {
    SeckillGoods g = goodsMapper.selectByIdForUpdate(goodsId);   // 管理操作低频，可用行锁
    require(g.getAvailableStock() + delta >= 0, "调整后库存不能为负");

    goodsMapper.adjustStock(goodsId, delta);
    //  UPDATE t_seckill_goods
    //     SET total_stock = total_stock + #{delta},
    //         available_stock = available_stock + #{delta},
    //         status = CASE WHEN status = 2 AND #{delta} > 0 THEN 1 ELSE status END
    //   WHERE id = #{id} AND available_stock + #{delta} >= 0

    stockLogMapper.insert(StockLog.manual(goodsId, delta, reason, adminId));
    adminLogMapper.insert(AdminLog.of(adminId, "STOCK_ADJUST", goodsId,
            String.valueOf(g.getAvailableStock()), String.valueOf(g.getAvailableStock() + delta)));

    registerAfterCommit(() -> {
        String tag = g.getActivityId() + ":" + g.getSkuId();
        redis.opsForValue().increment("seckill:stock:{" + tag + "}", delta);
        if (delta > 0) redis.opsForHash().put("seckill:goods:{" + tag + "}", "status", "1");
    });
}
```

`total_stock` 与 `available_stock` 同步调整，保证库存对账等式仍然成立。
只改 `available_stock` 会让对账任务立刻报差异。

## 9. 参数校验

用 Jakarta Validation，在 DTO 上声明，`@Validated` 在 Controller 生效。

```java
@Data
public class SeckillSubmitReq {
    @NotNull @Positive          private Long    activityId;
    @NotNull @Positive          private Long    skuId;
    @NotNull @Min(1) @Max(1)    private Integer quantity;   // 当前版本仅支持 1
    @Null(message = "不允许指定 userId")
                                private Long    userId;      // 显式拒绝
}
```

`@Null` 标注 `userId` 是一个防御设计：显式告诉调用方"这个字段由服务端决定"，
而不是悄悄忽略。

全局异常处理把校验失败统一转成 `PARAM_INVALID` + 具体字段信息：

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public R<Void> handleValid(MethodArgumentNotValidException e) {
    String msg = e.getBindingResult().getFieldErrors().stream()
            .map(f -> f.getField() + ": " + f.getDefaultMessage())
            .collect(Collectors.joining("; "));
    return R.fail(ErrorCode.PARAM_INVALID, msg);
}
```
