# 01 工程结构

## 1. Maven 模块划分

五个 Maven 模块，依赖单向向下，不允许反向或循环依赖。演示前端 `fss-web` 是独立的
npm 工程，**不在 Maven 聚合里**（见 §7）。

```
flash-sale-system                       (pom, 父工程，统一依赖版本)
├── fss-common                          (jar) 零业务依赖
│   ├── result/       统一响应体 R<T> / PageR<T>
│   ├── error/        ErrorCode（含 isDeterministic 判据）/ BizException / Assert
│   ├── web/          GlobalExceptionHandler / TraceIdResponseAdvice
│   ├── context/      UserContext（当前登录用户，ThreadLocal）
│   ├── trace/        TraceContext（traceId 的 MDC 读写）
│   ├── util/         IdGenerator / JsonUtil / IpUtil
│   └── enums/        CodeEnum 接口 + 9 个带显式编码的状态枚举
│
├── fss-infra                           (jar) 依赖 common
│   ├── config/       FssProperties / MybatisPlusConfig / RedissonConfig / SentinelConfig
│   ├── redis/        RedisKeys / RedisTemplateConfig
│   │                 LuaScriptConfig（脚本装载）+ EvalShaScriptExecutor（见 03 §7）
│   ├── cache/        CacheWrapper（防穿透 / 防雪崩）/ LogicalExpiryCache（逻辑过期）
│   ├── lock/         @DistributedLock + Aspect + LockService（Redisson）
│   ├── mq/           MqSender（只管发出去）/ MqTopics / MqBacklogMonitor
│   ├── ratelimit/    RateLimiter（Redis Lua 令牌桶）
│   ├── degrade/      DegradeSwitch（本地 volatile 等级，每秒刷新）
│   ├── metrics/      SeckillMetrics（Micrometer 埋点）
│   ├── alarm/        AlarmService（分级告警）
│   ├── tx/           TxSupport（afterCommit 回调，见 04 §2）
│   ├── trace/        TraceIdFilter + MDC
│   └── resources/lua/  seckill / rollback / release / write_result / token_bucket
│
├── fss-domain                          (jar) 依赖 common
│   ├── entity/       与 13 张表一一对应的实体
│   ├── mapper/       MyBatis-Plus Mapper 接口，SQL 写在注解里（无 XML，见下）
│   ├── dto/          内部传输对象（PaymentDiff）
│   └── message/      MQ 消息体：OrderCreate / OrderClose / StockRelease / StockRollback
│
├── fss-biz                             (jar) 依赖 domain + infra
│   ├── user/         用户与认证（JwtService、令牌吊销）
│   ├── product/      商品与 SKU
│   ├── activity/     活动管理与预热（WarmupService）
│   ├── seckill/      秒杀核心（高并发入口）
│   ├── order/        订单、状态机、库存释放
│   ├── payment/      模拟支付与退款
│   ├── reconcile/    资格 / 库存 / 支付三类对账 + PaymentFixer
│   ├── audit/        AdminAuditService（管理操作审计）
│   ├── mq/           ReliableMqProducer（本地消息表 + "发不出去怎么办"）
│   ├── consumer/     5 个 MQ 监听器（含 DLQ）
│   └── job/          7 个定时任务
│
└── fss-app                             (jar, 可执行) 依赖 biz
    ├── controller/   REST 接口层 6 个 + MockPayController（仅 dev）
    ├── config/       WebMvcConfig（拦截器注册）
    ├── filter/       JwtAuthFilter / AdminAuthFilter
    ├── interceptor/  RateLimitInterceptor（按 URI 前缀分档限流）
    ├── init/         DevDataInitializer（dev profile 造演示数据）
    └── FssApplication.java
```

**Mapper 不写 XML**：全部 SQL 用 `@Select` / `@Update` 注解写在接口上。热点语句
（条件扣减、状态条件更新）都是单表单语句，写在方法旁边比翻 XML 更容易看出
`WHERE` 里少了哪个条件——而少一个条件正是这类语句最典型的缺陷。

**`ReliableMqProducer` 为什么在 biz 而不是 infra**：它同时需要
`RocketMQTemplate`（基础设施）和 `MqMessageMapper`（数据模型），而 infra 只依赖
common。让 infra 依赖 domain 会把方向拧反。现在 `MqSender`（infra）只负责发出去，
`ReliableMqProducer`（biz）负责落本地消息表以及"发不出去该怎么办"——后者是业务
决策：订单消息必须回补库存，关单消息只需告警。

**为什么 domain 不依赖 infra**：实体与 Mapper 是纯数据契约，让 domain 独立可以在
单元测试中直接构造实体而不启动 Redis/MQ 上下文。

**为什么 biz 里按业务分包而非分模块**：七个业务域各自建 Maven 模块会产生 12 个
模块和大量跨模块接口下沉，对本项目规模是负收益。分包已足够表达边界；包之间
只允许通过 `XxxService` 接口调用，禁止跨包直接用别人的 Mapper。

## 2. fss-biz 内部包结构（以 seckill 为例）

```
com.fss.biz.seckill
├── service
│   ├── SeckillService.java             对外接口（submit / queryResult）
│   └── impl/SeckillServiceImpl.java    降级判定 → 令牌 → Lua → 投递
├── core
│   ├── SeckillExecutor.java            四段 Lua 的执行封装 + 结果读写
│   ├── SeckillOutcome.java             Lua 返回码到 ErrorCode 的翻译
│   ├── SeckillTokenService.java        秒杀令牌签发与一次性消费
│   ├── SeckillCompensateService.java   补偿回补（脚本 B）
│   └── UncertainRecorder.java          结果不确定的登记簿（ZSet，见 04 §5）
└── model
    ├── SeckillCmd.java                 入参命令对象
    ├── SeckillSubmitVO.java            提交出参（queueing / success 两个工厂方法）
    └── SeckillResultVO.java            轮询出参
```

同样结构复制到 order / activity / payment。`consumer` 与 `job` 包只做编排，
不写业务规则，规则都在各业务包的 Service 里——`OrderCreateListener` 全类
唯一的判断就是"抛异常触发重试"还是"回补并 ACK"。

**没有 converter 包**：VO 都是几个字段的手工装配，引入 MapStruct 要多一个注解
处理器、多一层生成代码，换来的只是省掉十几行 setter。

## 3. 三种运行角色

同一个 jar，用 Spring Profile 控制 Bean 装配。

```java
// fss-biz/consumer/OrderCreateListener.java
@Profile("consumer")
@RocketMQMessageListener(
        topic = MqTopics.ORDER_CREATE,
        consumerGroup = MqTopics.GID_ORDER_CREATE,
        consumeMode = ConsumeMode.CONCURRENTLY,
        consumeThreadNumber = 12,       // 与 Hikari 池对齐，见下
        maxReconsumeTimes = 5)
@Component
public class OrderCreateListener implements RocketMQListener<MessageExt> { ... }
```

```java
// fss-biz/job/ReconcileJob.java
@Profile("job")
@Component
public class ReconcileJob { ... }
```

```java
// fss-app/controller/SeckillController.java
@Profile("web")
@RestController
@RequestMapping("/api/seckill")
public class SeckillController { ... }
```

**Topic 与 Group 写成 `MqTopics` 常量而不是 `${...}` 占位符**：监听注解上的
占位符只在启动时解析，写错一个字符的表现是"消费者静默订阅了一个不存在的
Topic"——不报错、不告警，只是消息永远没人消费。常量能在编译期对齐生产者与消费者，
`MqTopicConsistencyTest` 再断言一遍两侧用的是同一个常量。

**`consumeThreadNumber = 12` 是被连接池反推出来的**：2 实例 × 12 = 24 个并发写
< 30 个连接，留 6 个给定时任务与监控查询。设成 20（2×20 = 40 > 30）会让消费线程
大量阻塞在获取连接上，症状是消费 TPS 上不去而 CPU 很闲，很容易被误判成 MQ 慢。

启动命令：

```bash
# Web 层，2 实例
java -jar fss-app.jar --spring.profiles.active=web,prod --server.port=8080
# 消费层，2 实例
java -jar fss-app.jar --spring.profiles.active=consumer,prod --server.port=8090
# 任务层，1 实例（或多实例 + Redisson 锁）
java -jar fss-app.jar --spring.profiles.active=job,prod --server.port=8099
```

本地开发默认 `web,job,dev`（见 `application.yml` 的 `spring.profiles.default`），
需要联调异步链路时加上 `consumer`。`dev` 额外启用 `DevDataInitializer` 造演示数据
与 `MockPayController` 的验签辅助接口。

**job 单实例的兜底**：即使部署成多实例，每个定时方法都套 `@DistributedLock`，
Redisson 抢不到锁直接返回，因此多实例只是浪费一次 Redis 请求，不会重复执行。

```java
@Scheduled(fixedDelayString = "${fss.job.mq-resend-delay-ms:30000}")
@DistributedLock(key = "mq-resend", leaseSeconds = 120)
public void resendPendingMessages() { ... }
```

**任务的时间参数一律走配置占位符**（`cron` 与 `fixedDelayString` 都支持），
默认值写在注解里。压测时要把对账频率调快十倍，改配置就行，不必重新编译。

## 4. 父 POM 依赖管理

```xml
<properties>
    <java.version>17</java.version>
    <maven.compiler.release>17</maven.compiler.release>
    <spring-boot.version>3.3.5</spring-boot.version>
    <lombok.version>1.18.34</lombok.version>
    <mybatis-plus.version>3.5.9</mybatis-plus.version>
    <jjwt.version>0.12.6</jjwt.version>
    <springdoc.version>2.6.0</springdoc.version>
    <testcontainers.version>1.20.3</testcontainers.version>
    <redisson.version>3.36.0</redisson.version>
    <sentinel.version>1.8.8</sentinel.version>
    <rocketmq-spring.version>2.3.1</rocketmq-spring.version>
</properties>
```

注意点：

- Spring Boot 3.x 的基线就是 JDK 17，本项目未使用虚拟线程等 21 特性，故按 17 落地。
- **`spring-boot.version` 等版本号必须在父 POM 里显式声明**：`spring-boot-dependencies`
  BOM 里的 property 不会被继承，只 import BOM 而在子模块引用 `${spring-boot.version}`
  会解析不到。
- **MyBatis-Plus 3.5.9 起把 JSqlParser 从核心包剥离**，`PaginationInnerInterceptor`
  依赖它，必须额外引入 `mybatis-plus-jsqlparser`，否则编译期就找不到类。
  同时需要 `mybatis-plus-spring-boot3-starter` 才能装配到 Spring Boot 3。
- RocketMQ 5.x broker 配合 `rocketmq-spring-boot-starter` 2.3.1 客户端，
  定时消息需 broker 开启 `timerWheelEnable=true`。
- Spring Boot 3.x 起 `javax.*` 全部换成 `jakarta.*`，JWT 库选 `jjwt 0.12.x`。

## 5. 核心配置项

`application.yml` 中与业务语义相关的自定义配置，全部集中在 `fss` 前缀下并绑定到
`@ConfigurationProperties(prefix = "fss")` 的 `FssProperties`，不散落在代码里——
超时时长与限流阈值需要在压测中反复调整，硬编码意味着每次都要重新编译。

```yaml
fss:
  order:
    pay-timeout: 15m              # 决策 3：关单时长，不受 MQ 延迟级别约束
    close-scan-delay: 2m          # 扫描比过期时刻晚这么久才处理
    close-scan-batch: 200
  seckill:
    result-ttl: 30m               # 秒杀请求结果在 Redis 的保留时长
    token-ttl: 5m                 # 秒杀令牌有效期
    warmup-ahead: 5m              # 活动开始前多久预热
    cache-ttl: 2h                 # 活动/商品缓存基础 TTL
    cache-ttl-jitter: 10m         # 随机抖动上限，防雪崩
    null-cache-ttl: 60s           # 空值缓存，防穿透
    cache-physical-buffer: 30m    # 物理 TTL 相对逻辑过期的缓冲，保证旧值可读
    key-ttl-after-end: 1h         # 活动结束后 Redis key 再留多久（供轮询与对账）
    released-ttl: 25h             # 已回补订单号 Set 的 TTL，须覆盖活动结束后的关单
    allow-repurchase-after-cancel: false   # 决策 1，启动时断言必须为 false
  ratelimit:
    enabled: true
    user-qps: 2                   # 单用户提交秒杀
    ip-qps: 20                    # 单 IP
    activity-qps: 5000            # 单活动放行上限
    global-qps: 12000
    result-qps: 5                 # 结果轮询单独一档，见下
    burst-factor: 2               # 桶容量 = qps × 该倍数，容纳正常的双击与刷新
  sentinel:
    enabled: true
    submit-qps: 6000              # 单实例阈值，3 个 web 实例总量是它的 3 倍
    result-qps: 8000
    activity-detail-qps: 3000
    lua-concurrency: 200          # 用并发线程数而非 QPS，见 SentinelConfig 注释
    slow-rt-ms: 200               # 压测实测该值偏紧，见 09 §2
    circuit-break-seconds: 10
  mq:
    topic:
      order-create: FSS_ORDER_CREATE
      order-close: FSS_ORDER_CLOSE
      stock-release: FSS_STOCK_RELEASE
      stock-rollback: FSS_STOCK_ROLLBACK
    group:                        # GID_ 前缀同名四组
      order-create: GID_FSS_ORDER_CREATE
      ...
    send-timeout: 2000
    max-resend: 5
    backlog-monitor-enabled: true # 启动 DefaultMQAdminExt 采集积压量
  degrade:
    seckill-enabled: true         # 人工总闸。与自动降级是"与"关系，自动只能收紧
    refresh-delay-ms: 1000        # 本地缓存刷新间隔，开关最多延迟这么久生效
    level-ttl-seconds: 300        # 自动降级值的 TTL；写入者崩溃时能自己过期
    poll-interval-ms: 300         # 下发给客户端的轮询间隔
    degraded-poll-interval-ms: 2000   # Level 2 起换成这个值，不用发版
    auto-enabled: true
    backlog-threshold: 50000      # 积压超阈值 → Level 3（暂停新资格分配）
    stalled-rounds: 4             # 消费端连续 4 轮无进展且仍有积压 → Level 3
    db-pending-threshold: 5       # 连接池等待线程超阈值 → Level 2
    recover-ratio: 0.5            # 恢复阈值 = 触发阈值 × 该比例（滞回，防抖动）
  reconcile:
    orphan-after: 5m              # 排队中超过这么久还没结论才算孤儿
    orphan-rounds-before-rollback: 3
    payment-diff-after: 5m        # 给正常的回调延迟留窗口
    batch-size: 500
    uncertain-retention: 10m      # 超期仍无法判定 → 转人工（不自动回补，方向未知）
    uncertain-settle: 5s          # 静置窗口：超时那一刻脚本可能正在执行
  jwt:
    secret: ${FSS_JWT_SECRET:...}     # 生产必须由环境变量注入
    ttl: 2h
    issuer: fss
  pay:
    notify-secret: ${FSS_PAY_SECRET:...}
    notify-tolerance: 5m          # 回调时间戳容忍窗口，防重放
  job:
    close-expired-cron: "0 */2 * * * ?"
    activity-state-cron: "0 * * * * ?"
    warmup-cron: "0 * * * * ?"
    mq-resend-delay-ms: 30000
    reconcile-qualification-cron: "0 * * * * ?"     # 用户正在等，最频繁
    reconcile-stock-cron: "0 */5 * * * ?"           # SCAN + 多次 DB，最贵
    reconcile-payment-cron: "0 */10 * * * ?"        # 最不急但最严重
    uncertain-check-delay-ms: 10000
    degrade-monitor-delay-ms: 15000  # 必须明显小于 degrade.level-ttl-seconds
```

`allow-repurchase-after-cancel` 保留为配置项但代码中断言必须为 `false`，
启动时校验，避免有人误开导致 [决策 1](00-设计总览.md#决策-1一人一单的最终归属与取消语义) 描述的死循环。

**限流为什么按接口分档**：单用户 2 QPS 是"提交秒杀"的额度。用户点一次抢购，
背后还有领令牌、活动详情、结果轮询等请求，共用一个桶会让第二次点击直接 429。
`RateLimitInterceptor` 按 URI 前缀分成提交（`user-qps`）、结果查询（`result-qps`）、
其他（不限）三档。

**`degrade-monitor-delay-ms` 必须小于 `level-ttl-seconds`**：自动降级值带 TTL
（写入者崩溃后能自己过期），刷新周期若大于 TTL，降级等级会在两轮之间过期抖动。

## 6. 数据源与连接池

```yaml
spring:
  datasource:
    type: com.zaxxer.hikari.HikariDataSource
    hikari:
      maximum-pool-size: 30       # 消费端 2×12 线程 + 定时任务 + 余量
      minimum-idle: 10
      connection-timeout: 3000    # 快速失败，不让请求堆在获取连接上
      max-lifetime: 1740000
  data:
    redis:
      timeout: 1000ms             # 秒杀链路必须快速失败
      connect-timeout: 1000ms
      lettuce:
        pool:
          max-active: 64          # Lettuce 是单连接多路复用，池子不必很大
          max-idle: 16
          min-idle: 8
          max-wait: 1000ms
  task:
    scheduling:
      pool:
        size: 4                   # 默认 1 会让慢任务饿死 DegradeSwitch 的刷新
```

**两个超时都给得很短，是为了压缩故障范围**：超时给到 5s 时，Redis 一慢，
Tomcat 线程会全部堆在等 Redis 上，表现是整个应用无响应，而不是"秒杀接口变慢"。
连接池的 `connection-timeout` 同理。

**`spring.task.scheduling.pool.size` 不能留默认的 1**：`DegradeSwitch` 每秒刷新一次
开关，它和"扫描关单"共用这个池——单线程下一轮扫了 3 分钟的关单任务会让降级开关
整整 3 分钟不更新，恰好是最需要它更新的时候。

Web 角色的 `maximum-pool-size` 可降到 10（只有本地消息表写入用 DB），
消费角色保持 30。通过 profile 覆盖：`application-web.yml` / `application-consumer.yml`。

## 7. 演示前端 fss-web

`fss-web/` 是独立的 npm 工程（Vue 3.5 + Vite 7 + TypeScript 5.9 + Element Plus 2.14），
不参与 Maven 构建，也不打进 `fss-app.jar`。

```
fss-web
├── src/api/          http.ts（axios 拦截器：注入 JWT、收集 traceId、401 回调外部注入）
│                     session.ts（token 的纯模块存储）/ index.ts / types.ts
├── src/stores/       auth.ts（登录态）/ trace.ts（最近若干请求的 traceId）
├── src/composables/  useSeckill.ts（提交 → 轮询 → 落单的客户端状态机）
├── src/components/   ActivityCard / SeckillFlow / admin/*
├── src/router/       history 模式路由
├── Dockerfile        多阶段构建：node 编译 → nginx 发静态
└── nginx.conf        发静态 + 反代 /api 与 /actuator 到 app:8080
```

**为什么不打成一个 jar**：前端改一行要重新跑一次 Maven 打包，而两者的发布节奏
本来就不同。分开之后开发期用 Vite proxy、部署期用 Nginx 反代，前端代码两种模式下
都不需要知道后端地址。

**前端镜像里的 Nginx 刻意不抄 `docker/nginx/nginx.conf` 的限流**：那份是四级限流的
第一级，保护的是应用集群；这份只是前端的门面。把限流写两遍会让"到底哪一层拦的"
变成一个查不清的问题。
