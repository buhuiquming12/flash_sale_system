# 11 技术选型与取舍

阶段五交付物，对应 docs/08 §6 第 6 条。这份文档回答的是**面试会追问的那些"为什么"**，
每一条都尽量给出「不这么做会怎样」，因为只有失败方向能说明取舍的价值。

前五节是 docs/08 点名的六个问题，后面是实现过程中真实做过的选择。

---

## 1. 为什么不直接操作 MySQL

阶段一**就是**纯 MySQL 实现，而且它是对的：

```sql
UPDATE t_seckill_goods SET available_stock = available_stock - 1, locked_stock = locked_stock + 1
WHERE activity_id = ? AND sku_id = ? AND available_stock >= 1
```

条件更新 + `uk_activity_sku_user` 唯一键，100 库存 × 500 并发实测恰好 100 单，
单用户 50 并发恰好 1 单。**防超卖不需要 Redis。**

问题不在正确性，在**这一行 UPDATE 是行级串行的**。10000 个请求争同一行，
InnoDB 行锁把它们排成一队，每个请求的持锁时间 ≈ 一次磁盘 fsync。
本机实测跨 WSL2 的单行 INSERT 约 50ms，即使同机房也是毫秒级——
把 10000 个请求串起来，最后一个要等几十秒。

而且**代价不对称**：库存只有 1000 件，其余 9000 个请求排了几十秒队，
只是为了听一句"卖完了"。让 9000 个注定失败的请求去争数据库的行锁，
是把最贵的资源花在最没价值的事情上。

所以阶段二做的不是"用 Redis 防超卖"，而是**把资格分配从 MySQL 挪到 Redis**：
Redis 决定谁有资格（O(1)、单线程无锁竞争），MySQL 只为那 1000 个赢家写订单。
条件更新一行没删，退化为兜底——F2 演练证明了它还得留着（§4）。

## 2. 为什么用 Redis

三个理由，重要性递减：

**① 单线程 + Lua = 无锁的原子判定。** 秒杀要在一次操作里做完
「活动状态、时间窗、一人一单、库存」四件事，任何两件之间有窗口就会出错。
数据库要用事务 + 行锁，Redis 天然串行——脚本 A 执行期间没有任何别的命令能插进来。
实测单次 Lua 65µs，而 MySQL 单行写是它的三个数量级。

**② `DECRBY` 返回扣减后的值。** 一次调用完成"写 + 读剩余量"，
不需要"先查再改"的两步（那中间又是一个窗口）。

**③ 内存态天然适合"用完即弃"的数据。** `bought` 标记、请求结果、
令牌桶计数在活动结束后毫无价值，让它们随 TTL 消失比在 MySQL 里堆着好。

**没选其他方案的原因**：本地缓存 + `synchronized` 在多实例下直接错（docs/08 §5 明确禁用）；
数据库乐观锁（`version` 字段）在高冲突下重试率接近 100%，
`t_seckill_goods.version` 字段留着但主链路不用就是这个原因。

## 3. 为什么用 MQ

阶段二已经能防超卖了，MQ 解决的是另一个问题：**接口 RT 与 MySQL 写入速度解耦**。

阶段二的秒杀接口 = Lua 判扣 + **同步落库**（4 张表、一个事务、热点行竞争）。
Lua 再快，接口 RT 也被 MySQL 的写入速度绑住了。
阶段三之后接口只做「Lua + 一次单行 INSERT + 一次 send」，
落库由消费端按自己的节奏做——10000 并发下 MySQL 只需要消化 1000 条消息。

**代价是用户拿不到即时结论**，而这不只是体验问题，它引入一整类新的失败模式：
消息丢了、消费端挂了、处理失败了，用户会永远停在"排队中"。
所以阶段三真正的工作量不在那个接口，而在
**本地消息表、幂等三层、死信处理、重发任务**这些"让排队中一定会有结论"的机制上。

如果只看代码行数，异步化让秒杀接口变简单了、让整个系统复杂了一个数量级。
**这个取舍只有在"接口 RT 是瓶颈"时才划算**，
而秒杀恰好是这种场景——峰值流量是日常的几百倍，且集中在几秒内。

选 RocketMQ 而不是 Kafka/RabbitMQ 的具体理由：**5.x 的任意时刻定时消息**
（`timerWheelEnable=true`）。关单需要"15 分钟后精确投递"，
Kafka 没有原生定时，RabbitMQ 的死信+TTL 方案只能做固定延迟队列，
而订单的 `expire_time` 各不相同。这是决策 3 的前提。

## 4. 为什么仍需 DB 约束

**因为 Redis 会丢数据，而唯一键不会。** 这不是理论——F2 演练实测过：

```
FLUSHDB 后重建，bought 标记全丢
→ 已抢过的用户重抢，Redis 放行了（一人一单失效），库存扣到 94
→ 落库撞 uk_activity_sku_user，消费端判定确定性失败
→ 脚本 B 回补，库存回到 95，订单仍是 5 单
```

Redis 的一人一单**失守了**，DB 唯一键兜住了。

三个唯一键各拦一类异常，缺一不可：

| 唯一键 | 拦什么 | 没有它会怎样 |
| --- | --- | --- |
| `uk_request_no` | MQ 重复投递、消费端重试 | 一条消息重投 10 次出 10 单 |
| `uk_activity_sku_user` | Redis 数据丢失后重抢 | 上面那个场景直接出 2 单 |
| `uk_order_no` | 订单号碰撞 | 静默覆盖，两个用户共享一张单 |

外加 `uk_biz_type (biz_no, change_type)` 保证库存流水幂等、
`CHECK available_stock >= 0` 作为最后的算术兜底。

**为什么不用物理外键**：秒杀写入是热点路径，外键检查要额外锁父表行
（`t_seckill_goods` 那一行正是最热的）。逻辑关系由应用维护，
一致性由唯一键 + 对账保证——ER 图上标了 12 张表的所有 UK，那就是幂等的物理载体。

## 5. 为什么最终一致

强一致要求"Redis 扣减"与"MySQL 建单"在一个事务里，而它们是两个不同的存储。
可选的路只有三条：

| 方案 | 为什么不选 |
| --- | --- |
| 分布式事务（XA / Seata） | Redis 不支持 XA。Seata AT 模式要全局锁，把好不容易去掉的锁竞争又加回来，而且引入 TC 单点 |
| TCC | 要为每个操作写 try/confirm/cancel 三份逻辑，而秒杀的"cancel"就是回补库存——TCC 框架能给的东西，本地消息表 + 补偿已经给了，只是不叫 TCC |
| **本地消息表 + 补偿（选定）** | 消息行与业务操作同事务 → 投递意图不会丢；剩下的不一致靠对账收敛 |

**关键在于把不一致的窗口和方向都定死**：

- 窗口：`req key` 的 TTL 是 30 分钟，资格对账每分钟一轮，正常情况下有 30 次机会发现
- 方向：**永远偏向少卖，绝不偏向超卖**。
  少卖能人工补货、能给用户发券；超卖要赔钱，而且赔的是商誉

这条原则贯穿全部代码，最典型的三处：

1. Redis 连不上时秒杀**一律拒绝**（fail-closed），不放行。F1 实测返回 1005 而不是 200
2. `checkUncertain` 判定不了时**只转人工，绝不自动回补**——
   处境恰好是"不知道扣没扣"，回补一份没扣过的库存就是凭空造库存
3. 库存对账发现 `redisStock > available` 时**P1 告警且绝不自动修**——
   Redis 比 DB 多意味着可能已经超卖，覆盖它会把证据也擦掉

反面的取舍也有一处：**限流器失败时放行**（docs/07 §1③）。
限流是保护措施而不是正确性措施，Redis 抖动时拒绝所有请求等于自己制造故障；
真正的正确性防线是 Lua 和唯一键，它们不会因为限流放行而失守。

## 6. 为什么模块化单体而不是微服务

五个模块 `common / domain / infra / biz / app`，**同一个 jar，靠 profile 切角色**：

```
web       只做 Lua + 投消息
consumer  订单在这里诞生
job       所有兜底机制
```

微服务化的收益在这个项目上几乎为零，成本却是实打实的：

- **收益为零**：这三类角色共享同一套领域模型和同一个数据库。
  拆成三个服务之后它们仍然要读写同一批表，只是把方法调用换成了 RPC——
  多了序列化、网络、超时、重试，少了编译期检查
- **成本明确**：`OrderCreateService.handle` 被 web（阶段一二）和 consumer（阶段三）
  共同调用，**落库逻辑三个阶段一行没改**。这是单体的直接好处：
  换调用方不用改被调用方，阶段一二的 55 个落库用例仍然覆盖着同一段代码

**边界在模块依赖上而不是在网络上**：`fss-infra` 只依赖 `fss-common`，
所以阶段三时 `ReliableMqProducer` 必须拆成两个类——它同时需要
`RocketMQTemplate`（infra）和 `MqMessageMapper`（domain），
让 infra 依赖 domain 会把方向拧反。这个约束是编译器强制的，
比"团队约定不要跨服务调用"可靠得多。

真要拆的时候，模块边界就是服务边界，而边界已经在这里画好并被编译器守着了。

## 7. 几个具体选型

### Lettuce 与 Redisson 并存

| 用途 | 客户端 | 理由 |
| --- | --- | --- |
| Lua、普通读写 | **Lettuce** | Spring Data Redis 的一等公民，`StringRedisTemplate` 直接可用 |
| 分布式锁 | **Redisson** | 看门狗自动续期。自己写"锁续期 + 可重入 + 安全释放"很容易写错，而写错的表现是偶发的双重执行 |

**不用 `redisson-spring-boot-starter`**：它会顶掉 Boot 自动装配的连接工厂，
于是 Lettuce 那一半也走 Redisson，白白引入一层。只引 `redisson` 核心包、手动配一个 `RedissonClient`。

### 为什么限流分四级

单一层限流挡不住不同形态的流量：

| 层 | 挡什么 | 挡不住什么 |
| --- | --- | --- |
| Nginx `limit_req` | 单 IP 洪水 | 分布式刷（每 IP 都不超阈值） |
| Sentinel 接口 QPS + 熔断 | 单实例过载、慢调用雪崩 | 单个用户的高频请求 |
| Redis 令牌桶（IP/用户/活动） | 单用户刷、单活动总量 | 已经进来的合法流量 |
| Lua 内售罄快速失败 | 售罄后的无效流量 | — |

最后一级最容易被忽略但收益最大：S3 实测**售罄路径在 200 并发下零熔断，
而正常路径 40 并发就熔断**——差 5 倍，因为售罄分支在脚本第二步就返回，
完全不碰 MySQL 和 MQ。

`user-qps` 必须**按接口分档**（提交 2 / 结果查询 5 / 其他不限）：
用户点一次"抢购"背后有领令牌、活动详情、订单列表几个请求，
共用一个 2 QPS 的桶会让第二次点击直接 429。

### 为什么 `maxmemory-policy` 必须是 `noeviction`

`seckill:stock` 和 `seckill:bought` **绝不能被淘汰**。
用 `allkeys-lru` 时内存压力下 Redis 可能淘汰库存 key，
后续请求读到 0 或读不到——业务直接错乱且没有任何报错。
`noeviction` 下写满会**报错**，而报错能被监控发现。
宁可写入失败，也不能静默丢数据。

配套的是 `bought` Hash 必须有 TTL（脚本 A 里补的那次 `EXPIRE`）：
不设的话购买标记永久驻留，一场十万人的活动约 3MB，活动做多了必然撑爆。

### 为什么时间判定在 Lua 内

F14 正面证明了它的价值：DB 里 `start_time` 是 30 分钟后，
只改 Redis 元数据就放行了——**判定压根不看应用时钟**。

如果放在 Java 侧，一台实例时钟快 5 分钟就会提前放行请求。
而且"应用层判时间、Redis 判库存"之间还有窗口，活动结束那一瞬间仍可能放行。
所以 `OrderCreateService` 里那份应用时钟的校验是**删掉**而不是留作双重保险——
两个时钟只要有一个错，留着的那个就是错的那个。

代价是 **Redis 时钟成了业务时间的单点**。它漂了就全漂，
但那至少是**一致地漂**，不会出现"实例 A 放行、实例 B 拒绝"的分裂。
一致地错比不一致地错好排查得多。

### 指标为什么用推送而不是回调采样

`Gauge.builder(name, () -> readRedis())` 在**每次抓取时执行**：
1 个活动 10 个 SKU × 4 个指标 = 一次抓取 40 次 Redis 查询，15 秒一轮就是稳定负载。
更糟的是失败模式：**Redis 变慢 → 抓取超时 → 整个端点失败 → 连"Redis 慢了"都看不到**，
因为报告它的曲线也断了。

改成对账任务顺手写内存（它本来就要读那四个值）、抓取只读内存，
代价是数据滞后一个对账周期。

## 8. 三个"事后才知道选错了"的地方

诚实记录，被追问时主动说比被追出来好。

### 本地消息表放业务库：收益与代价都比预期大

**收益**：消息行与业务操作同事务，"订单已创建"与"关单消息已登记"是原子的。

**代价（F3 演练才看清）**：它与业务库**共享可用性**。MySQL 挂了，
`INSERT t_mq_message` 就失败，请求走不到投递那一步——
只能就地回补并返回失败，而不是文档预期的"消息堆积、恢复后重试"。

这不是设计错误（放独立库会牺牲同事务性，更不值得），
但 docs/08 §4 对 F3 的预期需要按这个实际路径改正，本次已改。

### JWT 白名单与秒杀数据共享一个 Redis

F2 演练时 `FLUSHDB` 把 `jwt:active:{jti}` 也清了，**全站用户被强制登出**。
真实故障中这意味着"秒杀数据丢失"会连带"所有人重新登录"，影响面比预期大得多。

修法很简单——白名单挪到独立实例或独立 database 编号，
让两类数据的故障域解耦。属于阶段二的遗留，已记录未改。

### `slow-rt-ms: 200` 是拍出来的，不是压出来的

这个阈值按"专用机器、同机房"的假设定的。实测在本机：
**25 并发零错误（P99 225ms），40 并发就因慢调用比例超 50% 而熔断**。
放宽到 2000ms 后 100 并发零错误、176 TPS——**系统承得住，是熔断先动手**。

正确顺序是**先压出 P99 基线，再把阈值设成基线的 3–5 倍**。
反过来做（先定阈值再上线）就会出现现在这样：系统健康，熔断器认为它病了。

## 9. 一张表总结所有"失败方向"的选择

| 组件 | 失败时 | 选择 | 理由 |
| --- | --- | --- | --- |
| Redis 不可用 | 秒杀 | **拒绝**（1005） | 放行 = 超卖 |
| Redis 结果不确定 | 秒杀 | **拒绝 + 登记待确认** | 既不放行也不回补，事后用 `EXISTS req key` 判定 |
| `checkUncertain` 判不了 | 补偿 | **转人工，不自动回补** | 方向未知，回补可能凭空造库存 |
| 限流器不可用 | 限流 | **放行** | 限流是保护而非正确性，拒绝一切等于自制故障 |
| 消息表写不进 | 秒杀 | **立即回补 + 失败** | 投递意图没落盘，没人会建单 |
| `send` 失败 | 投递 | **吞掉，交重发任务** | 消息行已落盘，回补才是真丢单 |
| DB 回补失败 | 关单 | **整个事务回滚** | 否则订单已取消而库存没还 |
| Redis 回补失败 | 关单 | **重试 5 次 → 死信** | 它没法加入 DB 事务，所以必须可重试 |
| 对账发现 Redis > DB | 对账 | **P1，绝不自动修** | 可能已超卖，覆盖会擦掉证据 |
| 对账发现 DB 不自洽 | 对账 | **需人工** | 自动修的前提是"知道正确值是多少" |
| 支付成功 + 订单已取消 | 支付 | **退款 + P1** | CANCELLED 是终态，没有回头路 |
| 消息解析不了 | 消费 | **ACK + 告警** | 重试一万次也解析不了 |
| 未知消息版本 | 消费 | **抛出 → 死信** | 用旧代码解析新字段可能建出金额 0 的订单 |

这张表是整个系统的设计骨架：**每一个"失败时往哪边倒"的决定，
都是在"少卖"和"超卖"之间选了少卖**，唯一的例外是限流器——
因为它失败时放行不会导致超卖。
