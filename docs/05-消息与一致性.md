# 05 消息与一致性

## 1. Topic 规划

| Topic | Tag | 类型 | 生产者 | 消费者组 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `FSS_ORDER_CREATE` | - | 普通 | web | `GID_FSS_ORDER_CREATE` | 异步创建订单 |
| `FSS_ORDER_CLOSE` | - | 定时 | consumer | `GID_FSS_ORDER_CLOSE` | 到期关单 |
| `FSS_STOCK_RELEASE` | - | 普通 | consumer/web | `GID_FSS_STOCK_RELEASE` | 取消回补 |
| `FSS_STOCK_ROLLBACK` | - | 普通 | consumer/job | `GID_FSS_STOCK_ROLLBACK` | 补偿回补 |
| `%DLQ%GID_FSS_*` | - | 死信 | broker | `GID_FSS_DLQ_HANDLER` | 统一死信处理 |

队列数：`FSS_ORDER_CREATE` 设 16 个队列（消费端 2 实例 × 20 线程，队列数需 ≥ 实例数
才能均衡）。其余 Topic 4 个队列足够。

**不用顺序消息。** 秒杀订单之间没有顺序依赖，用顺序消息会把并发度锁死到队列数，
且单队列阻塞会拖垮整体。幂等设计已经让乱序无害。

## 2. 消息体定义

```java
@Data @Builder
public class OrderCreateMessage implements Serializable {
    private String        requestNo;      // 幂等键
    private Long          userId;
    private Long          activityId;
    private Long          skuId;
    private Integer       quantity;
    private LocalDateTime requestTime;
    private String        traceId;
    private Integer       version;        // 消息格式版本，便于灰度升级
}
```

`version` 字段的用途：消息格式变更时，新消费端能识别旧消息。消费端拿到
未知版本直接进死信并告警，而不是用错误的字段解析。

```java
@Data @AllArgsConstructor
public class OrderCloseMessage implements Serializable {
    private String orderNo;
    private Long   userId;
}

@Data @AllArgsConstructor
public class StockReleaseMessage implements Serializable {
    private String orderNo;
    private Long   activityId;
    private Long   skuId;
    private Integer quantity;
}

@Data @AllArgsConstructor
public class StockRollbackMessage implements Serializable {
    private String requestNo;
    private Long   userId;
    private Long   activityId;
    private Long   skuId;
    private Integer quantity;
    private String reason;
}
```

**所有消息体都不含金额。** 金额一律由消费端从 DB 读取（见
[04](04-核心流程.md#消息体中不带价格)）。

## 3. 幂等三层

每个消费者都必须具备这三层，缺一层就存在重复处理的窗口。

| 层 | 手段 | 拦截的场景 | 失效场景 |
| --- | --- | --- | --- |
| L1 前置查询 | `SELECT ... WHERE request_no = ?` | 绝大多数重复投递 | 两条重复消息并发进入，都查不到 |
| L2 唯一约束 | `uk_request_no` / `uk_biz_type` | L1 漏掉的并发情况 | 无（数据库层串行化） |
| L3 状态条件更新 | `WHERE status = ?` | 状态已推进的重复操作 | 无 |

L2 是唯一不可省的一层。L1 存在的意义是**避免绝大多数重复消息走到 insert 才失败**——
`DuplicateKeyException` 会让事务回滚，产生无用的 undo log 和错误日志噪音。
L3 用于状态变更类操作（关单、支付、释放库存），这些操作没有新行插入，无法靠唯一键。

### 捕获 DuplicateKeyException 的正确姿势

```java
try {
    orderMapper.insert(order);
} catch (DuplicateKeyException e) {
    // 必须区分是哪个唯一键冲突，处理方式完全不同
    String m = e.getMessage();
    if (m.contains("uk_request_no")) {
        // 同一请求重复消费 → 已有订单，ACK
        return;
    }
    if (m.contains("uk_activity_sku_user")) {
        // 该用户已有订单，但本次是不同 requestNo → 确定性失败，需补偿回补
        throw new BizException(ErrorCode.ALREADY_BOUGHT);
    }
    throw e;
}
```

靠字符串匹配索引名不优雅，但比"统一当成重复消息 ACK"安全得多：后者会让
`uk_activity_sku_user` 冲突的请求既没订单也不回补库存，库存永久泄漏。

更稳的做法是在 insert 前用 L1 的两次查询把两种情况分开（[04](04-核心流程.md#落库事务)
里的 `selectByRequestNo` + `selectByActivitySkuUser`），把 catch 分支退化为
纯粹的并发兜底。

## 4. 本地消息表

### 发送流程

```java
@Component
@RequiredArgsConstructor
public class ReliableMqProducer {

    private final RocketMQTemplate template;
    private final MqMessageMapper mapper;
    private final FssProperties props;

    /** 主链路调用：先落库再发送 */
    public void sendReliable(String topic, String bizKey, Object body, LocalDateTime deliverTime) {
        MqMessage rec = MqMessage.builder()
                .msgId(IdGenerator.msgId()).topic(topic).bizKey(bizKey)
                .body(JsonUtil.toJson(body)).deliverTime(deliverTime)
                .status(MqStatus.PENDING.code()).sendCount(0)
                .nextRetryAt(LocalDateTime.now().plusSeconds(30))
                .build();
        mapper.insert(rec);                       // 落盘：投递意图不会因崩溃丢失

        try {
            doSend(rec);
            mapper.markSent(rec.getMsgId());
        } catch (Exception e) {
            // 不抛出。落库已成功，重发任务会兜住
            log.warn("消息发送失败，转由重发任务处理 msgId={}", rec.getMsgId(), e);
        }
    }

    /** 事务内调用：提交后再发送 */
    public void registerAfterCommit(String topic, String bizKey, Object body,
                                    LocalDateTime deliverTime) {
        MqMessage rec = /* 同上构造 */;
        mapper.insert(rec);                       // 与业务同事务，一起提交或回滚
        TransactionSynchronizationManager.registerSynchronization(
                new TransactionSynchronization() {
                    @Override public void afterCommit() {
                        try { doSend(rec); mapper.markSent(rec.getMsgId()); }
                        catch (Exception e) { log.warn("延后发送失败 msgId={}", rec.getMsgId(), e); }
                    }
                });
    }

    private void doSend(MqMessage rec) {
        Message<String> m = MessageBuilder.withPayload(rec.getBody())
                .setHeader(RocketMQHeaders.KEYS, rec.getBizKey())
                .build();
        SendResult sr = rec.getDeliverTime() == null
                ? template.syncSend(rec.getTopic(), m, props.getMq().getSendTimeout())
                : template.syncSendDeliverTimeMills(rec.getTopic(), m,
                        toMillis(rec.getDeliverTime()));
        if (sr.getSendStatus() != SendStatus.SEND_OK) {
            throw new IllegalStateException("发送状态异常: " + sr.getSendStatus());
        }
    }
}
```

`registerAfterCommit` 是关键设计：消息记录与业务数据在同一事务里插入，因此
"订单创建成功"和"关单消息已登记"是原子的。事务提交后才真正 send，避免
"消息已投递但订单事务回滚"。

### 实现时拆成了两个类

上面的 `ReliableMqProducer` 同时依赖 `RocketMQTemplate`（技术设施）和
`MqMessageMapper`（数据模型），而按 [01-工程结构](01-工程结构.md) 的分层，
`fss-infra` 只依赖 `fss-common`。让 infra 依赖 domain 会把"技术设施"和"数据模型"
的方向拧反，以后 domain 想用 infra 的工具就成环。

实现切成两半：

| 类 | 模块 | 职责 |
| --- | --- | --- |
| `MqSender` | fss-infra | 只管把一条消息发出去：要不要定时、超时多少、SendStatus 校验 |
| `ReliableMqProducer` | fss-biz | 落库、退避重试的编排、失败了要不要回补库存 |

切点选在这里是因为"发送"是纯技术细节，而"发不出去该怎么办"是业务决策——
订单创建消息发不出去必须回补库存，关单消息发不出去只需要告警。

### `sendReliable` 抛异常意味着什么

`ReliableMqProducer` 内部**吞掉 send 失败**（转交重发任务），所以调用方
catch 到异常只有一种可能：**连本地消息表都写不进去**。那时投递意图彻底没能落盘，
没有任何后续机制会为这个用户建订单，必须就地回补。

主链路的 catch 块因此不是防御性代码，它覆盖的是一个真实且必须处理的分支：

```java
try {
    producer.sendReliable(TOPIC_ORDER_CREATE, requestNo, msg, null);
} catch (Exception e) {
    // 走到这里 = 消息行没落盘 = 没人会建这张订单
    compensateService.rollback(msg, ErrorCode.SYSTEM_BUSY, "消息登记失败，已退回");
    throw new BizException(ErrorCode.SYSTEM_BUSY);
}
```

### 关单定时消息的投递时刻取 `expire_time`

不用"现在 + 15 分钟"。两者在下单那一刻是同一个值，但 `expire_time` 是**写进 DB 的
那个值**，消费端也会读它。用同一个来源可以避免"消息在 14:59 触发而 DB 说 15:01
才过期"这种一秒级的错位——消费端会看到订单还没过期，于是什么都不做，
而这条定时消息已经消费掉了，订单只能等定时扫描来兜。

## 4.5 库存释放：DB 那半留在事务里，Redis 那半走消息

本文档前面把取消回补整个改成消息，实现只把 **Redis 那半**挪了出来，
DB 那半仍与关单同事务。两半的性质完全不同：

| | DB 回补 | Redis 回补 |
| --- | --- | --- |
| 能否与关单同事务 | **能** | 不能 |
| 所以 | 必须同事务 | 必须可重试 |
| 失败时 | 关单一起回滚，订单留在待支付由扫描重试 | 退避重试 5 次，再进死信 |

DB 那半拆成消息会引入一个新的失败模式：消费端永久失败时，订单已经是 CANCELLED
却永远拿不回库存，而"已取消"没法回滚成"待支付"。

Redis 那半不走消息则是阶段二的做法——提交后直接 `INCRBY`，失败只打日志等对账，
那期间 Redis 少一份库存，是实打实的少卖。登记成 `FSS_STOCK_RELEASE` 之后它才有了
重试与死信兜底。这才是这个 Topic 真正的用处。

顺序仍然是提交之后才投递。反了（事务内先投递、消费端抢先 `INCRBY`）会有一段时间：
Redis 库存已加回、别人已经能抢到这一份，而 DB 事务还没提交甚至可能回滚。

**消费端必须能区分"回补失败"与"早就回补过了"。** 脚本 C 对两者都返回非 0
（幂等命中返回 1，Redis 抛异常时封装层返回 false），分不开的话重复投递会被当成
失败无限重试，最后整批进死信——一个纯粹由"把幂等命中误判成失败"造出来的故障。
实现里多查一次 `SISMEMBER released orderNo` 把两者分开。

### 重发任务

```java
@Scheduled(fixedDelay = 30_000)
@DistributedLock(key = "job:mq-resend", waitTime = 0, leaseTime = 120)
public void resend() {
    List<MqMessage> list = mapper.selectPendingForRetry(LocalDateTime.now(), 200);
    for (MqMessage rec : list) {
        if (rec.getSendCount() >= props.getMq().getMaxResend()) {
            mapper.markFailed(rec.getMsgId(), "超过最大重发次数");
            onSendGiveUp(rec);          // 关键：放弃发送要触发补偿
            continue;
        }
        try {
            producer.doSend(rec);
            mapper.markSent(rec.getMsgId());
        } catch (Exception e) {
            // 指数退避：30s → 60s → 120s → 240s → 480s
            long backoff = 30L << rec.getSendCount();
            mapper.markRetry(rec.getMsgId(), backoff, e.getMessage());
        }
    }
}

private void onSendGiveUp(MqMessage rec) {
    if (TOPIC_ORDER_CREATE.equals(rec.getTopic())) {
        // 订单创建消息彻底发不出去 → 回补库存与资格（脚本 B）
        OrderCreateMessage m = JsonUtil.parse(rec.getBody(), OrderCreateMessage.class);
        compensateService.rollback(m, "订单消息投递失败，已回补");
        alarm.send("订单创建消息投递失败", rec.getBizKey());
    } else {
        alarm.send("消息投递最终失败，需人工处理", rec.getTopic() + "/" + rec.getBizKey());
    }
}
```

`onSendGiveUp` 是原设计缺失的一环：投递彻底失败必须回补，否则库存被永久占用。

### 捞待重发记录时必须带 `send_count < max` 条件

上面的写法是"捞出来再判断次数，超了就 `markFailed` 并 `continue`"。照这样实现有个
在量小时完全看不出来的缺陷：`markFailed` 之后记录状态变成 3，不会再被捞到——
**只要 markFailed 成功**。而它和 `selectPendingForRetry` 的 `status = 0` 条件之间
存在窗口：任何一次 `markFailed` 失败（DB 抖动、连接超时），这条记录就会永远留在
`status = 0` 里，每 30 秒被捞出来一次、判断一次、跳过一次。

积累几万条之后，每轮 200 条的配额全被它们占满，真正需要重发的新消息一条也捞不到。
这是典型的队头阻塞，而症状是"重发任务在跑、日志也没报错、但消息就是发不出去"。

实现拆成两次查询：

```sql
-- 该重试的
WHERE status = 0 AND next_retry_at <= now AND send_count < #{maxSendCount}
-- 该放弃的
WHERE status = 0 AND send_count >= #{maxSendCount}
```

两条都走 `idx_status_retry`，成本与一次查询相当，而配额不会被污染。

### `markFailed` 要在回补之前

顺序反了的话，回补成功而 `markFailed` 失败时，下一轮又会把同一条记录捞出来再回补
一次。虽然脚本 B 的状态机幂等挡得住，但那意味着每 30 秒重复一次无用功，
还会不断刷 P1 日志。先置终态则至多多回补一次，而那一次本来就该重试。

## 5. 已消费状态回写

消费端处理成功后，异步把 `t_mq_message.status` 更新为"已消费"（状态 2）。
这不影响正确性，只是让本地消息表能被安全归档：状态 2 的记录 7 天后可删。
用异步单线程批量更新，不占消费主链路时间。

**消费端只拿得到 RocketMQ 的 `KEYS`（= bizKey），拿不到我们的 `msg_id`**，
所以回写要按 `(biz_key, topic)` 定位。两个条件都要：同一个 `requestNo` 会在多个
Topic 下各有一条消息（`ORDER_CREATE` 与后续可能的 `STOCK_ROLLBACK`），
只按 bizKey 更新会把另一条也标成已消费。

而且只能从"已发送(1)"推进到"已消费(2)"。允许从 0 推进的话，一条尚未发出的
同 bizKey 消息会被标成已消费，重发任务再也不会碰它——投递意图就这么丢了。

## 6. 死信处理

```java
@Profile("consumer")
@RocketMQMessageListener(
        topic = "%DLQ%GID_FSS_ORDER_CREATE",
        consumerGroup = "GID_FSS_DLQ_HANDLER")
@Component
public class DlqListener implements RocketMQListener<MessageExt> {

    @Override
    public void onMessage(MessageExt ext) {
        String body = new String(ext.getBody(), StandardCharsets.UTF_8);
        log.error("死信消息 topic={} keys={} reconsume={} body={}",
                  ext.getTopic(), ext.getKeys(), ext.getReconsumeTimes(), body);

        // 记录成对账任务，人工可见
        reconcileMapper.insert(ReconcileTask.builder()
                .taskType(TaskType.QUALIFICATION.code())
                .bizNo(ext.getKeys())
                .detail(body)
                .status(TaskStatus.NEED_MANUAL.code())
                .build());

        // 订单创建类死信：自动回补，不等人工
        try {
            OrderCreateMessage m = JsonUtil.parse(body, OrderCreateMessage.class);
            compensateService.rollback(m, "消息进入死信队列，已自动回补");
        } catch (Exception e) {
            log.error("死信自动回补失败，转人工 keys={}", ext.getKeys(), e);
        }
        alarm.send("死信消息", ext.getTopic() + "/" + ext.getKeys());
    }
}
```

死信队列必须有消费者。没有消费者的死信队列等于数据静默丢失——消息堆在那里，
没人知道有 300 个用户扣了库存却没订单。

**死信处理器绝不能抛异常。** 死信的死信没有归宿：抛出去只会让同一条消息在死信
Topic 里反复投递、反复插对账任务。处理不了就记 P1 日志。

顺序也有讲究：**先落对账任务，再自动回补**。自动回补万一也失败了，至少还有一条
记录说明"这个 requestNo 需要人看一眼"。反过来则可能两件事都没做成而只剩一行日志。

## 7. 消费端限速与积压保护

```yaml
rocketmq:
  consumer:
    pull-batch-size: 16
```

消费并发由 `consumeThreadNumber = 20` 控制。MySQL 侧的约束是：
2 实例 × 20 线程 = 40 并发写，Hikari 池 30 → 会有等待。

调整为 `consumeThreadNumber = 12`，2 实例 = 24 并发 < 30 连接，留 6 个给定时任务
和监控查询。这个数字必须与连接池大小对齐，否则消费线程会大量阻塞在获取连接上，
表现为消费 TPS 上不去但 CPU 很闲。

### 积压保护

```java
@Scheduled(fixedDelay = 15_000)
public void checkBacklog() {
    long lag = mqAdmin.计算积压量(TOPIC_ORDER_CREATE, GID_ORDER_CREATE);
    metrics.gauge("mq.backlog", lag);

    if (lag > props.getDegrade().getBacklogThreshold()) {
        degradeSwitch.pauseSeckill("消息积压 " + lag);   // 写 Redis 开关，web 层读
        alarm.send("消息积压超阈值，已暂停秒杀资格分配", String.valueOf(lag));
    } else if (lag < props.getDegrade().getBacklogThreshold() / 2) {
        degradeSwitch.resumeSeckill();                  // 半阈值恢复，避免抖动
    }
}
```

积压量 = `maxOffset - consumerOffset` 之和，通过 `DefaultMQAdminExt` 或
RocketMQ Dashboard 的 API 获取。恢复阈值取暂停阈值的一半（滞回），
避免在阈值附近反复开关。

暂停开关写在 Redis（`degrade:seckill:enabled`），web 实例每 1 秒本地缓存刷新一次，
不为每个请求查 Redis。

## 8. 异常场景与处理对照表

| # | 场景 | 后果 | 处理 | 兜底 |
| --- | --- | --- | --- | --- |
| 1 | Redis 预扣成功，进程崩溃在发消息前 | 库存占用无订单 | 本地消息表已落盘 → 重发任务发出 | 重发耗尽 → 脚本 B 回补 |
| 2 | Redis 预扣成功，消息表也写了，send 一直失败 | 同上 | 指数退避重发 5 次 | `onSendGiveUp` → 脚本 B 回补 |
| 3 | Redis 脚本调用超时，结果未知 | 未知 | `EXISTS req key` 判定真实结果，存在则补发消息 | 不存在 = 未执行，无需处理 |
| 4 | 消息发送成功，HTTP 响应超时，用户重试 | 可能双份资格 | 新请求被 Lua 的 `bought` 检查拦截，返回"重复购买" | `uk_activity_sku_user` |
| 5 | 订单创建成功，ACK 失败，消息重投 | 可能双订单 | L1 `selectByRequestNo` 命中 → 直接 ACK | `uk_request_no` |
| 6 | 消费端扣 DB 库存后崩溃，订单未插入 | 事务回滚，DB 库存未变 | 消息重投重新处理 | — |
| 7 | 消费端确定性失败（DB 库存真不足） | Redis 与 DB 库存不一致 | 立即脚本 B 回补 + 请求置 COMPENSATED | 库存对账 |
| 8 | Redis 宕机 | 秒杀入口不可用 | Sentinel 熔断 → 返回"活动太火爆"；不把流量转给 MySQL | 主从哨兵 + AOF everysec |
| 9 | Redis 数据丢失（主从切换未持久化） | 库存/资格丢失 | 活动置 CLOSED，人工按 DB 重建后重开 | `uk_activity_sku_user` 保证不会因此超卖出订单 |
| 10 | MySQL 宕机 | 消费端全失败 | 消息在队列堆积 → 积压保护暂停资格分配 | 恢复后自然消费完 |
| 11 | 定时关单消息丢失 | 订单永久待支付 | 定时扫描 `status=0 AND expire_time < now` | 对账 |
| 12 | 重复关单/重复释放库存 | 库存多加 | `stock_released` 条件更新 + `uk_biz_type` + Redis Set | 三层 |
| 13 | 支付与关单并发 | 收钱无订单 | 行锁竞争，输者走退款流程 + 告警 | 支付对账 |
| 14 | 消息格式升级，旧消费端收到新消息 | 解析错误 | `version` 校验，未知版本进死信 + 告警 | 死信处理器 |
| 15 | 活动到点但预热失败 | 全部请求返回未预热 | 预热未完成不推进到 RUNNING，用户看到"即将开始" | 预热失败告警 |

## 9. 对账任务

### 9.1 资格对账（每分钟）

找"Redis 说排队中，但 DB 没有订单"的请求。

```java
public void reconcileQualification() {
    // 只扫描 5 分钟前仍为排队中的记录，给正常异步处理留足时间
    LocalDateTime before = LocalDateTime.now().minusMinutes(5);
    for (Long activityId : activityMapper.selectRunningOrRecentEnded()) {
        for (Long skuId : goodsMapper.selectSkuIds(activityId)) {
            String tag = activityId + ":" + skuId;
            // SCAN 而非 KEYS，避免阻塞 Redis
            try (Cursor<String> c = redis.scan(ScanOptions.scanOptions()
                    .match("seckill:req:{" + tag + "}:*").count(200).build())) {
                while (c.hasNext()) {
                    String key = c.next();
                    Map<Object,Object> h = redis.opsForHash().entries(key);
                    if (!"0".equals(h.get("status"))) continue;
                    if (toTime(h.get("ts")).isAfter(before)) continue;

                    String requestNo = key.substring(key.lastIndexOf(':') + 1);
                    if (orderMapper.selectByRequestNo(requestNo) != null) {
                        // 订单其实已建，只是 Redis 回写失败 → 修正 Redis
                        resultService.markSuccess(activityId, skuId, requestNo,
                                orderMapper.selectByRequestNo(requestNo).getOrderNo());
                        continue;
                    }
                    handleOrphanQualification(activityId, skuId, requestNo, h);
                }
            }
        }
    }
}

private void handleOrphanQualification(long activityId, long skuId,
                                       String requestNo, Map<Object,Object> h) {
    MqMessage rec = mqMapper.selectByBizKey(requestNo);
    if (rec == null) {
        // 连消息记录都没有 → 主链路在落库前就崩了 → 直接回补
        compensateService.rollback(build(activityId, skuId, requestNo, h), "无消息记录，回补");
    } else if (rec.getStatus() == MqStatus.PENDING.code()) {
        // 等重发任务处理，本次不动
        log.info("消息待重发，跳过 requestNo={}", requestNo);
    } else if (rec.getStatus() == MqStatus.SENT.code()) {
        // 已发送但没结果 → 消费端可能丢了，重发一次；连续 3 轮仍无结果则回补
        int rounds = orphanCounter.incrementAndGet(requestNo);
        if (rounds >= 3) {
            compensateService.rollback(build(...), "消息已发送但长期无结果，回补");
        } else {
            producer.doSend(rec);
        }
    }
}
```

`orphanCounter` 存 Redis（`reconcile:orphan:count`，TTL 1h），
避免每轮都重发导致消息风暴。

### 9.2 库存对账（每 5 分钟）

校验等式：

```
total_stock == available_stock + 排队中占用 + 有效订单占用
```

其中：
- `available_stock` 取 DB（权威）
- 排队中占用 = Redis 中 `status=0` 的请求数 × quantity
- 有效订单占用 = `SELECT SUM(quantity) FROM t_order WHERE activity_id=? AND sku_id=? AND status IN (0,1,3,4,5)`
  （即除 CANCELLED 外的全部状态；已取消的已经通过 `released_stock` 回到 available）

同时校验 Redis 与 DB 的差值：

```
redisStock - dbAvailableStock == -(排队中占用)
```

即 Redis 一定小于或等于 DB（Redis 先扣，DB 后扣）。**Redis 大于 DB 一定是 bug**，
直接告警到 P1。

```java
public void reconcileStock() {
    for (SeckillGoods g : goodsMapper.selectActiveGoods()) {
        String tag = g.getActivityId() + ":" + g.getSkuId();
        long redisStock = Long.parseLong(
                Optional.ofNullable(redis.opsForValue().get("seckill:stock:{" + tag + "}"))
                        .orElse("-1"));
        if (redisStock < 0) continue;                       // 未预热或已清理

        int queueing = countQueueing(tag);
        int occupied = orderMapper.sumEffectiveQuantity(g.getActivityId(), g.getSkuId());
        int expected = g.getTotalStock() - occupied - queueing;

        boolean dbOk    = g.getAvailableStock() + occupied + queueing == g.getTotalStock();
        boolean redisOk = redisStock == expected;

        if (redisStock > g.getAvailableStock()) {
            record(TaskType.STOCK, g, "REDIS_GT_DB", redisStock, g.getAvailableStock());
            alarm.p1("Redis 库存大于 DB 库存，存在超卖风险", tag);
        } else if (!dbOk || !redisOk) {
            record(TaskType.STOCK, g, dbOk ? "REDIS_DRIFT" : "DB_DRIFT", redisStock, expected);
            // 只有 Redis 漂移且无排队中请求时，才允许自动修正
            if (dbOk && queueing == 0) {
                redis.opsForValue().set("seckill:stock:{" + tag + "}",
                        String.valueOf(g.getAvailableStock()));
                log.warn("自动修正 Redis 库存 tag={} {} → {}", tag, redisStock, g.getAvailableStock());
            } else {
                alarm.send("库存对账差异需人工", tag);
            }
        }
    }
}
```

**自动修正的前提条件必须严格**：只在 DB 自洽（`dbOk`）且没有排队中请求
（`queueing == 0`）时才覆盖 Redis。有排队中请求时，Redis 与 DB 的差值是**正常的**，
覆盖会造成超卖。这是库存对账最容易写错的地方。

### 9.3 支付对账（每 10 分钟）

四类差异：

```sql
-- A. 支付成功但订单未支付
SELECT p.pay_no, p.order_no FROM t_payment p
  JOIN t_order o ON o.order_no = p.order_no
 WHERE p.status = 1 AND o.status NOT IN (1,3,4,5)
   AND p.finish_time < NOW() - INTERVAL 5 MINUTE;

-- B. 订单已支付但无成功流水
SELECT o.order_no FROM t_order o
 WHERE o.status = 1
   AND NOT EXISTS (SELECT 1 FROM t_payment p
                    WHERE p.order_no = o.order_no AND p.status = 1);

-- C. 金额不一致
SELECT p.pay_no FROM t_payment p JOIN t_order o ON o.order_no = p.order_no
 WHERE p.status = 1 AND p.amount <> o.pay_amount;

-- D. 已取消订单出现支付成功
SELECT p.pay_no FROM t_payment p JOIN t_order o ON o.order_no = p.order_no
 WHERE p.status = 1 AND o.status = 2;
```

A 类可自动修复（补推订单状态）；B、C、D 一律人工，且 C、D 直接 P1 告警——
它们意味着资金与业务不一致。

## 10. 一致性总结

系统的正确性不依赖任何单一组件，而是靠：

```
Lua 原子性       →  资格分配不会部分成功
本地消息表       →  投递意图不会因崩溃丢失
唯一约束         →  重复处理不会产生重复数据
条件更新         →  并发状态变更只有一个赢家
状态机           →  非法流转被显式拒绝
补偿回补         →  失败路径不泄漏库存
对账任务         →  上述全部失效时仍能发现并修复
告警             →  对账无法自动修复时人能介入
```

八层里任意一层单点失效，都有下一层接住。这是"最终一致"在工程上的具体含义——
不是"最后总会对的"，而是"每一种不一致都有明确的检测手段和收敛路径"。
