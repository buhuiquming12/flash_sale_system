# 08 实施与验收

## 1. 五阶段路线图

每阶段结束都是一个可演示、可回归的状态。不允许"三个阶段一起做最后一起调"。

### 阶段一：基础业务闭环（约 5 天）

不涉及 Redis、不涉及 MQ。纯 MySQL 同步链路，先把业务规则做对。

交付：

- 工程骨架（五模块 + Docker Compose 起 MySQL）
- 全部建表 SQL + Flyway 迁移脚本
- 用户注册、登录、JWT 认证
- 商品与 SKU 管理
- 活动创建、发布、状态推进
- **同步**秒杀：直接 `UPDATE t_seckill_goods ... WHERE available_stock >= 1` + 建订单
- 模拟支付、支付回调
- 定时扫描关闭超时订单
- 取消订单回补库存

验收：

```
单元测试：订单状态机全部合法/非法迁移
集成测试：100 库存 × 200 并发同步下单 → 恰好 100 单，库存 0，无负数
集成测试：同一用户并发 20 次下单 → 恰好 1 单
```

这一阶段的并发测试用 `CountDownLatch` + 线程池即可，重点验证条件更新和唯一约束
真的拦住了超卖和重复下单。**如果这一步都拦不住，后面加 Redis 只是把 bug 藏得更深。**

### 阶段二：缓存与高并发入口（约 4 天）

交付：

- Redis 接入 + 序列化配置
- 活动预热任务（`setIfAbsent` 幂等）
- 活动详情缓存（逻辑过期 + 单飞重建 + 空值缓存 + TTL 抖动）
- `seckill.lua` 原子判扣
- 一人一单 Redis 拦截
- 秒杀结果 Redis 读写 + 查询接口
- 四级限流（Nginx + Sentinel + 令牌桶）
- 秒杀令牌与动态路径

此阶段秒杀仍是同步落库（Lua 通过后直接调阶段一的下单逻辑），暂不引入 MQ。
这样能单独验证 Lua 的正确性，不被 MQ 的异步性干扰。

验收：

```
1000 库存 × 10000 并发 → Redis 剩余 0，DB 订单恰好 1000
重复预热 → Redis 库存不被重置
活动结束瞬间的请求 → 全部被 Lua 时间校验拒绝
限流：单用户 100 QPS 压测 → 大部分返回 429
```

### 阶段三：异步化（约 4 天）

交付：

- RocketMQ 接入 + Topic 创建
- 本地消息表 + `ReliableMqProducer`
- `OrderCreateListener` 异步落库
- 消费幂等三层
- 定时消息关单 + 定时扫描兜底
- 库存释放消费者
- 死信队列消费者
- 消息重发任务

验收：

```
1000 库存 × 10000 并发 → 秒杀接口 P99 < 100ms，3s 内全部订单落库
手动重复投递同一条消息 10 次 → 仍然 1 单
杀掉消费端进程再重启 → 消息不丢，订单最终落库
断开 MQ 后压测 → 本地消息表堆积，恢复后全部发出
```

### 阶段四：可靠性与补偿（约 4 天）

交付：

- 补偿回补（脚本 B）+ 确定性失败判定
- 三类对账任务
- 不确定结果处理（`checkUncertain`）
- 支付与关单竞态处理 + 退款流程
- 降级开关 + 自动降级
- 全量监控指标 + Grafana 看板 + 告警规则

验收：见 §4 故障测试全部通过。

### 阶段五：展示物料（约 3 天）

交付：

- 架构图、核心时序图、数据模型 ER 图（PlantUML 源文件 + 导出 PNG）
- JMeter 压测脚本 + 压测报告（含 P99、TPS、错误率曲线）
- 故障演练报告（每个场景的注入方式、观测结果、恢复过程）
- Docker Compose 一键启动 + README 快速开始
- 技术选型与取舍说明文档
- 简单的前端演示页（活动列表、秒杀按钮、结果轮询、订单列表、模拟支付）

前端不必精美，但**必须有**：面试演示时能点击秒杀、看到排队、看到结果、完成支付，
比看代码有说服力得多。

### 并发测试写法

```java
@SpringBootTest
@Testcontainers
class SeckillConcurrencyTest {

    @Container static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0");
    @Container static GenericContainer<?> redis =
            new GenericContainer<>("redis:7.2-alpine").withExposedPorts(6379);

    @Test
    void 库存100并发10000_订单恰好100() throws Exception {
        long activityId = fixture.createRunningActivity(100);
        int threads = 10000;
        var start = new CountDownLatch(1);
        var done  = new CountDownLatch(threads);
        var ok    = new AtomicInteger();

        try (var pool = Executors.newFixedThreadPool(200)) {
            for (int i = 0; i < threads; i++) {
                long uid = 100000 + i;
                pool.submit(() -> {
                    try {
                        start.await();
                        seckillService.submit(cmd(activityId, 2001L, 1), uid);
                        ok.incrementAndGet();
                    } catch (BizException ignored) {
                    } catch (Exception e) {
                        fail("非业务异常: " + e);
                    } finally {
                        done.countDown();
                    }
                });
            }
            start.countDown();
            assertThat(done.await(60, SECONDS)).isTrue();
        }
        awaitConsumed(Duration.ofSeconds(30));            // 等异步落库完成

        assertThat(ok.get()).isEqualTo(100);
        assertThat(orderMapper.countByActivity(activityId)).isEqualTo(100);
        assertThat(goodsMapper.select(activityId, 2001L).getAvailableStock()).isZero();
        assertThat(redisStock(activityId, 2001L)).isZero();
    }
}
```

`awaitConsumed` 用轮询等待而非固定 sleep：`while (queueing > 0 && !timeout) sleep(200)`。
固定 sleep 在 CI 上会随机失败。

Testcontainers 起真实 MySQL 和 Redis，不用 H2 或嵌入式 Redis——Lua 脚本行为、
`CHECK` 约束、行锁语义在替代品上都不一样，测过了不代表真环境对。

## 3. 性能测试

### 场景与目标

| 场景 | 并发 | 时长 | 目标 |
| --- | --- | --- | --- |
| S1 活动详情读 | 5000 | 3 min | P99 < 50ms，错误率 0，Redis 命中率 > 99% |
| S2 秒杀提交（有库存） | 10000 | 30 s | P99 < 100ms，无超卖 |
| S3 秒杀提交（已售罄） | 10000 | 1 min | P99 < 30ms（走 status=2 快速失败） |
| S4 结果轮询 | 8000 | 2 min | P99 < 50ms |
| S5 混合场景 | 详情 5000 + 秒杀 3000 + 轮询 2000 | 5 min | 全部达标，无降级触发 |
| S6 消费端吞吐 | 预置 50000 消息 | — | ≥ 500 TPS/实例 |

S3 单独测是为了验证售罄快速失败的效果：售罄后 P99 应显著低于 S2，
如果没有明显差异，说明 `status=2` 的短路没生效。

### 需要记录的数据

```
请求总量 / 峰值 QPS / 平均 RT / P50 / P95 / P99 / P999 / 最大 RT
成功率 / 业务失败率 / 限流率(429) / 系统错误率(5xx)
Redis: QPS、命中率、内存、连接数、Lua P99
MySQL: QPS、活跃连接、pending 连接、慢查询数、行锁等待
MQ: 生产 TPS、消费 TPS、积压峰值、最老消息滞留时长
JVM: GC 次数与暂停时间、堆使用、活跃线程数
```

### 调优检查清单

压测不达标时按顺序检查，不要乱调：

1. **Redis Lua P99 是否 > 5ms** → 脚本操作数太多，或有大 key。检查 `bought` Hash
   是否膨胀（5 万用户的 Hash 约 3MB，`HGET` 仍是 O(1)，但 `HGETALL` 会阻塞，
   确认代码里没有 `HGETALL`）。
2. **Hikari `pending` 是否 > 0** → 连接池不足或消费线程数与池大小不匹配，
   见 [05](05-消息与一致性.md#7-消费端限速与积压保护)。
3. **Tomcat 线程是否打满** → `max-threads` 不足，或有阻塞调用。秒杀链路上不应有
   任何同步 HTTP 调用。
4. **GC 暂停是否 > 100ms** → 检查是否在请求路径上创建大对象（如日志里拼大字符串）。
   用 G1，堆 2G，`-XX:MaxGCPauseMillis=100`。
5. **网络是否是瓶颈** → 单机压测时 JMeter 和应用抢 CPU 与端口，
   压测机应独立部署。

## 4. 故障测试

每个场景都要有明确的注入方式与可观测的预期结果。

| # | 场景 | 注入方式 | 预期 |
| --- | --- | --- | --- |
| F1 | Redis 短暂不可用 | `docker pause redis` 10s | 秒杀返回 1005/1006，无 500；不产生订单；恢复后正常；无超卖 |
| F2 | Redis 数据全丢 | `FLUSHDB` | 秒杀返回 2005；活动可人工关闭重建；`uk_activity_sku_user` 保证不重复出单 |
| F3 | MySQL 短暂不可用 | `docker pause mysql` 20s | 消费端重试，消息不丢；积压上升触发降级；恢复后全部落库 |
| F4 | MQ 不可用 | `docker pause rocketmq` 30s | 本地消息表堆积；恢复后重发任务发出全部消息；无库存泄漏 |
| F5 | 消息重复投递 | 用 Admin 工具重发 | 无重复订单，无重复扣减 |
| F6 | 消费者处理中宕机 | 落库后 `kill -9` 消费端 | 消息重投，L1 幂等命中，ACK |
| F7 | 消息发送失败 | Mock `syncSend` 抛异常 | 记录待发送，重发任务处理；耗尽后回补 |
| F8 | Redis 调用超时 | `tc` 注入 800ms 延迟 | 记入 uncertain，`checkUncertain` 正确判定 |
| F9 | 支付与取消并发 | 并发脚本 ×100 轮 | 无双终态；竞态时自动退款 + 告警 |
| F10 | 定时消息丢失 | 直接删除定时消息 | 定时扫描在 2 分钟内关单 |
| F11 | 补偿重复执行 | 重投 STOCK_ROLLBACK ×10 | 库存只 +1（脚本 B 状态机幂等） |
| F12 | job 多实例 | 起 3 个 job 实例 | 每个任务只执行一次（Redisson 锁） |
| F13 | 预热失败 | Mock 预热抛异常 | 活动不进入 RUNNING，用户看到"即将开始"，收到告警 |
| F14 | 时钟漂移 | 调快一台 web 实例时钟 5 分钟 | 活动时间判定不受影响（Lua 用 Redis `TIME`） |

F14 是容易被忽略的一项：如果时间判定放在 Java 侧，一台实例时钟快 5 分钟就会
提前放行请求。把时间校验放进 Lua、用 Redis 自己的时钟，从设计上消除了这个问题。
测试要能证明这一点。

### 故障报告模板

```markdown
## F3 MySQL 短暂不可用

**注入**：`docker pause fss-mysql`，持续 20s，期间维持 2000 QPS 秒杀压力

**观测**：
- 秒杀接口成功率保持 99.8%（Redis 层不依赖 MySQL）
- 消费端错误率 100%，消息重试
- `fss_mq_backlog` 从 0 升至 38000（未触及 50000 阈值，未自动降级）

**结论**：符合预期。MySQL 故障不影响入口可用性，消息队列成功承担缓冲。

**发现的问题**：消费端重试日志刷屏（每条消息 5 次 × 38000），
建议对同类连接异常做日志采样（1/100）。已修复。
```

"发现的问题"这一栏是报告的价值所在——只写"符合预期"的故障报告说明测得不够深。

### 两个关键配置

**Redis `maxmemory-policy noeviction`**：秒杀库存和用户购买标记**绝不能被淘汰**。
如果用 `allkeys-lru`，内存压力下 Redis 可能淘汰 `seckill:stock` key，
后续请求读到 0 或读不到 key，直接导致业务错乱。宁可写入失败（noeviction 下
写满会报错，能被监控发现），也不能静默丢数据。

**Redis `appendfsync everysec`**：主从切换或宕机最多丢 1 秒数据。
配合 `uk_activity_sku_user` 兜底，1 秒的资格丢失不会造成超卖，只会有极少数
用户需要重抢。用 `appendfsync no` 会丢更多，用 `always` 性能损失过大。

**RocketMQ broker 必须开定时消息**：

```properties
# broker.conf
brokerClusterName = DefaultCluster
brokerName = broker-a
brokerId = 0
brokerRole = ASYNC_MASTER
flushDiskType = ASYNC_FLUSH
timerWheelEnable = true          # 5.x 任意时刻定时消息（决策 3 的前提）
messageDelayLevel = 1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
autoCreateTopicEnable = false    # 生产环境关闭，Topic 显式创建
```

`autoCreateTopicEnable = false` 后需手动建 Topic：

```bash
sh mqadmin updateTopic -n namesrv:9876 -c DefaultCluster -t FSS_ORDER_CREATE  -r 16 -w 16
sh mqadmin updateTopic -n namesrv:9876 -c DefaultCluster -t FSS_ORDER_CLOSE   -r 4  -w 4
sh mqadmin updateTopic -n namesrv:9876 -c DefaultCluster -t FSS_STOCK_RELEASE -r 4  -w 4
sh mqadmin updateTopic -n namesrv:9876 -c DefaultCluster -t FSS_STOCK_ROLLBACK -r 4 -w 4
```

### 多实例部署的约束

因为是多实例，以下东西**绝不能用**：

| 禁用 | 替代 |
| --- | --- |
| `synchronized` / `ReentrantLock` 保护业务临界区 | Redis Lua 原子操作 或 Redisson 分布式锁 |
| 本地 `HashMap` 缓存业务数据 | Redis（本地缓存只用于降级开关等最终一致的配置） |
| 本地 `AtomicLong` 生成业务序列 | Redis `INCR` 或雪花算法（带机器号） |
| 单机 `@Scheduled` 直接执行 | `@Scheduled` + `@DistributedLock` |
| `LocalDateTime.now()` 做业务时间判定 | Redis `TIME`（Lua 内）或统一时钟源 |

最后一条是 F14 测试要验证的。

| 库存回补后别人能抢到吗 | 能。回补是 `INCRBY` Redis 库存，原用户资格已消耗（[决策 1](00-设计总览.md#决策-1一人一单的最终归属与取消语义)） |

| 多实例时钟不一致怎么办 | Lua 内用 Redis `TIME`（[03 脚本 A](03-缓存与Lua.md#2-脚本-a秒杀资格判定与预扣)），[F14](#4-故障测试) 验证 |

## 8. 已知限制

诚实列出，被问到时主动说明，比被追出来好：

1. **限购固定为 1**。大于 1 需要 `t_user_purchase_quota`，见
   [02 附录](02-数据模型.md#附-限购数量大于-1-的扩展方案)。
2. **取消后不允许重抢**。这是产品取舍而非技术限制，原因见决策 1。
3. **单库单表**。1000 库存 × 若干活动的订单量，单表完全够。分库分表需要引入
   ShardingSphere 与全局 ID，超出本项目范围。
4. **Redis 单点**（演示环境）。生产需哨兵或 Cluster；Key 已带 hash tag，
   上 Cluster 无需改代码。
5. **模拟支付**。无真实渠道对接，但状态机、验签、幂等、对账逻辑完整。
6. **无库存分桶**。极端热点（单 SKU 10 万 QPS）下 Redis 单 key 会成瓶颈，
   届时可把库存拆成 N 个子 key 随机路由。当前量级（10000 QPS）单 key 足够，
   过早分桶会让库存查询和对账复杂度上升。
7. **对账用 SCAN 遍历 Redis**。活动数与 SKU 数很多时成本上升，
   可改为从 `t_seckill_request` 反向查（但那需要主链路同步写库，是另一个取舍）。
