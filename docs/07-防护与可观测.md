# 07 防护与可观测

## 1. 四级限流

从外到内逐层收窄，每一层拦下的请求都不消耗内层资源。

```
① Nginx limit_req          全局 + 单 IP        → 拦掉爬虫与明显洪峰
② Sentinel 接口级 QPS       单接口 + 熔断降级    → 保护应用线程池
③ Redis 令牌桶              单用户 / 单 IP / 单活动 → 业务级公平性
④ Lua 内部快速失败           售罄标记 status=2   → 降低 Redis 自身开销
```

### ① Nginx

```nginx
# 单 IP 20 r/s，突发 40
limit_req_zone $binary_remote_addr zone=perip:20m rate=20r/s;
# 全局 12000 r/s
limit_req_zone $server_name        zone=perserver:10m rate=12000r/s;
limit_req_status 429;

upstream fss_web {
    server fss-web-1:8080 max_fails=2 fail_timeout=10s;
    server fss-web-2:8080 max_fails=2 fail_timeout=10s;
    keepalive 128;
}

location /api/seckill/ {
    limit_req zone=perip     burst=40   nodelay;
    limit_req zone=perserver burst=2000 nodelay;

    proxy_pass http://fss_web;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header X-Real-IP        $remote_addr;
    proxy_set_header X-Forwarded-For  $proxy_add_x_forwarded_for;
    proxy_connect_timeout 1s;
    proxy_read_timeout    3s;          # 秒杀接口必须快，超时即失败
}

location /api/activity/ {
    limit_req zone=perip burst=100 nodelay;
    proxy_cache activity_cache;         # 活动详情可在 Nginx 缓存 3s
    proxy_cache_valid 200 3s;
    proxy_cache_key "$uri$is_args$args";
    proxy_pass http://fss_web;
}
```

`nodelay` 让突发请求立即处理而非排队，超出直接 429。秒杀场景要的是快速失败，
不是排队——排队会占满连接。

活动详情页在 Nginx 缓存 3 秒，能把详情接口的 QPS 降一到两个数量级。库存展示
有 3 秒延迟完全可接受。

### ② Sentinel

```java
@SentinelResource(
        value = "seckill:submit",
        blockHandler  = "onBlock",       // 限流/熔断触发
        fallback      = "onFallback")    // 业务异常之外的异常触发
public SeckillSubmitVO submit(SeckillCmd cmd, long userId) { ... }

public SeckillSubmitVO onBlock(SeckillCmd cmd, long userId, BlockException e) {
    metrics.countBlocked();
    throw new BizException(ErrorCode.RATE_LIMITED, "活动太火爆，请稍后再试");
}

public SeckillSubmitVO onFallback(SeckillCmd cmd, long userId, Throwable t) {
    if (t instanceof BizException be) throw be;      // 业务异常原样抛出，不吞
    log.error("秒杀降级 activityId={}", cmd.getActivityId(), t);
    throw new BizException(ErrorCode.SYSTEM_BUSY);
}
```

`fallback` 里必须把 `BizException` 原样抛出。否则"库存不足"会被降级逻辑吞掉，
变成"系统繁忙"，用户一直重试，反而放大流量。这是 Sentinel 集成最常见的坑。

更彻底的做法是同时加 `exceptionsToIgnore = BizException.class`：不写它的话，
"库存不足"还会被计入**异常比例**，几秒钟就把熔断器打开——活动一售罄整个接口就熔断了。
业务失败不是故障，不能进故障统计。两者都加：注解负责不进统计，`fallback` 里的
显式抛出负责万一注解失效时也不吞码。

规则用代码加载而不是接控制台：控制台推送的规则是运行时状态，重启即丢，而且
"线上阈值到底是多少"变成一个要去控制台查的问题。写在配置里的规则能随代码一起
review、一起回滚。加载时机放在 `ApplicationReadyEvent` 而不是 `@PostConstruct`——
限流规则加载不上是可降级的问题，不该拖着整个应用起不来。

规则：

| 资源 | 阈值 | 熔断规则 |
| --- | --- | --- |
| `seckill:submit` | QPS 6000/实例 | 慢调用比例 > 50%（RT > 200ms）持续 5s → 熔断 10s |
| `seckill:result` | QPS 8000/实例 | — |
| `activity:detail` | QPS 3000/实例 | 异常比例 > 30% → 熔断 10s |
| `redis-seckill-script` | 并发线程数 200 | 熔断保护 Redis |

`redis-seckill-script` 用**并发线程数**而非 QPS 限流：Redis 慢下来时，
线程会堆积在等待响应上，线程数阈值能直接感知这一点，QPS 阈值感知不到。

### ③ Redis 令牌桶

```java
@Component
@RequiredArgsConstructor
public class RateLimitInterceptor implements HandlerInterceptor {

    private final StringRedisTemplate redis;
    private final RedisScript<Long> tokenBucket;
    private final FssProperties props;

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object h) {
        Long userId = UserContext.getUserId();
        String ip   = IpUtil.realIp(req);
        Long aid    = extractActivityId(req);

        var rl = props.getRatelimit();
        if (!pass("rate:ip:" + ip, rl.getIpQps() * 2, rl.getIpQps())) {
            return reject(resp, "IP 请求过于频繁");
        }
        if (userId != null && !pass("rate:user:" + userId + ":" + aid,
                                    rl.getUserQps() * 2, rl.getUserQps())) {
            return reject(resp, "操作过于频繁，请稍候");
        }
        if (aid != null && !pass("rate:activity:" + aid,
                                 rl.getActivityQps() * 2, rl.getActivityQps())) {
            return reject(resp, "活动太火爆，请稍后再试");
        }
        return true;
    }

    private boolean pass(String key, int capacity, int rate) {
        try {
            return Long.valueOf(1L).equals(redis.execute(tokenBucket, List.of(key),
                    String.valueOf(capacity), String.valueOf(rate), "1"));
        } catch (Exception e) {
            log.warn("限流检查失败，放行 key={}", key, e);
            return true;      // fail-open：限流组件故障不应阻断业务
        }
    }

    private boolean reject(HttpServletResponse resp, String msg) throws IOException {
        resp.setStatus(429);
        resp.setHeader("Retry-After", "1");
        resp.setContentType("application/json;charset=UTF-8");
        resp.getWriter().write(JsonUtil.toJson(R.fail(ErrorCode.RATE_LIMITED, msg)));
        return false;
    }
}
```

**限流 fail-open，库存 fail-closed。** 限流 Redis 挂了就放行（后面还有 Sentinel
和 Lua 兜着）；但库存判定的 Redis 挂了绝不能放行（会超卖）。两者的失败方向必须相反，
这是这套设计里一个容易搞反的取舍。

顺序上先查 IP 再查用户：IP 桶的 key 数量远少于用户桶，命中拒绝时能省一次 Redis 调用。

### 用户桶的速率必须按接口分档

上面的代码对所有路径用同一个 `userQps`，实现时发现这是错的。单用户 2 QPS 是给
**提交秒杀**定的（一个人一秒点两次已经不正常），但用户点一次"抢购"背后还有领令牌、
活动列表、活动详情、订单列表几个读请求——共用一个 2 QPS 的桶，点一次就把配额吃光，
第二次点击直接 429。

实现按 URI 前缀分档：

| 路径 | 单用户档位 |
| --- | --- |
| `/api/seckill/result` | `result-qps`（5） |
| `/api/seckill/**` 其余（提交、动态路径、领令牌） | `user-qps`（2） |
| 其他 | 不做用户级限流，交给 IP 桶与 Sentinel |

默认"不限"而不是默认"最严"：新加的接口漏配最多是防护不足，配错档位则是直接的
功能故障，而后者不会有任何报错。

另外两条边界：
- **支付渠道回调 `/api/pay/notify` 必须排除在限流之外**。它来自渠道方固定的几个 IP、
  量大且集中，按 IP 限流一定误杀，而拦掉一次成功回调意味着用户付了钱订单没变。
- **拦截器要自己写 429 的响应体**。它跑在 `DispatcherServlet` 之前，
  `@RestControllerAdvice` 根本看不到它；不写的话客户端收到的是容器默认的 HTML 错误页，
  前端的 JSON 解析会直接抛异常。

### ④ IP 提取的注意点

```java
public static String realIp(HttpServletRequest req) {
    String xff = req.getHeader("X-Forwarded-For");
    if (StringUtils.hasText(xff)) {
        // XFF 可被客户端伪造，只信任最右侧由我们自己的 Nginx 追加的那一段
        String[] parts = xff.split(",");
        return parts[parts.length - 1].trim();
    }
    return req.getRemoteAddr();
}
```

取 XFF 最左侧是常见错误——那一段完全由客户端控制，攻击者可以每次请求换一个
伪造 IP 从而绕过 IP 限流。信任链只能从右往左数，跳过自己已知的代理层数。

## 2. 秒杀令牌与动态路径

```java
public String issue(long userId, long activityId, long skuId) {
    String token = sha256Hex(userId + ":" + activityId + ":" + skuId + ":"
            + IdGenerator.nonce() + ":" + System.nanoTime());
    redis.opsForValue().set("seckill:token:" + userId + ":" + activityId + ":" + skuId,
            token, props.getSeckill().getTokenTtl());
    return token;
}

public void verifyAndConsume(String token, long userId, long activityId, long skuId) {
    String key = "seckill:token:" + userId + ":" + activityId + ":" + skuId;
    // GETDEL 原子取出并删除，保证一次性
    String stored = redis.opsForValue().getAndDelete(key);
    // 定长比较，不用 String.equals —— String.equals 在首个不同字节处提前返回，
    // 比对耗时随匹配前缀长度变化，可被用来逐字节爆破令牌
    if (stored == null || !MessageDigest.isEqual(
            stored.getBytes(StandardCharsets.UTF_8), token.getBytes(StandardCharsets.UTF_8))) {
        throw new BizException(ErrorCode.SECKILL_TOKEN_INVALID);
    }
}
```

`getAndDelete`（Redis 6.2+ `GETDEL`）保证令牌只能用一次，防止一个令牌被脚本
并发复用。用 `get` 再 `delete` 会有并发窗口。

**令牌的作用与局限**：它提高了脚本作者的成本（必须先调 token 接口、必须解析
动态路径），但对方拿到 token 后仍能高频提交。真正的防线是限流和一人一单，
令牌只是抬高门槛。文档里写清这一点，避免误以为有了令牌就安全。

## 3. 风控规则

规则引擎不需要复杂，用 Redis 计数 + 阈值判断即可。

| 规则 | 判定 | 动作 |
| --- | --- | --- |
| 同 IP 关联账号数 | 5 分钟内 > 20 个不同 userId | 该 IP 要求验证码 |
| 单账号请求频率 | 10 秒内 > 30 次秒杀请求 | 账号冻结 5 分钟 |
| 同设备指纹多账号 | 同 `deviceId` > 10 个 userId | 设备加入观察名单 |
| 令牌获取频率异常 | 1 分钟内 > 20 次 token 请求 | 强制验证码 |
| 验证码连续失败 | 5 次 | 账号锁定 15 分钟 |
| 登录地突变 | IP 归属地跨省且间隔 < 10 分钟 | 二次验证 |
| 抢购成功率异常 | 某账号连续 5 场活动全部抢中 | 加入人工审查名单 |

```java
// 同 IP 关联账号数
String key = "risk:ip:users:" + ip;
redis.opsForSet().add(key, String.valueOf(userId));
redis.expire(key, Duration.ofMinutes(5));
Long distinct = redis.opsForSet().size(key);
if (distinct != null && distinct > 20) {
    riskService.requireCaptcha(ip);
}
```

**IP 规则必须留白名单**：学校、公司、运营商 NAT 出口会有大量真实用户共享一个 IP。
把已知的教育网、大企业出口段加入白名单，或对这些段放宽阈值 10 倍。
只靠 IP 封禁会误伤大批正常用户。

## 4. 降级

### 分级策略

```
Level 0 正常（活动详情下发精确 remainStock + 三档 stockLevel）
Level 1 关闭非核心：remainStock 置空，只下发"有货/无货"两档
Level 2 拉长客户端轮询间隔（pollAfterMs 300 → 2000）
Level 3 暂停新资格分配（秒杀入口返回 1006 SERVICE_DEGRADED + HTTP 503），
        已排队的继续处理完
Level 4 只保留订单查询与支付，商品浏览也关
```

保住的优先级：**支付 > 订单查询 > 已排队订单落库 > 新资格分配 > 商品浏览**。

支付排第一是因为它涉及资金，中断会产生真实的资损与客诉。
"已排队订单落库"排在"新资格分配"之前，是 Level 3 停入口而不是停消费的原因。

**Level 1 省掉的是每次请求的 per-SKU Redis 读**：一个活动 10 个 SKU 就是 10 次往返，
而活动详情是全站 QPS 最高的接口。降级后用缓存里的 DB 快照判"有没有货"，
它可能滞后，但降级期间这个精度足够。

**Level 3 返回 `SERVICE_DEGRADED`（1006）而不是"活动已结束"**：后者是谎话，
用户会放弃而不是稍后重试，而降级往往只持续几分钟。用 HTTP 503 也让网关和客户端
SDK 能按标准语义退避。

### 开关实现

```java
@Component
public class DegradeSwitch {
    private volatile int level = 0;

    @Scheduled(fixedDelayString = "${fss.degrade.refresh-delay-ms:1000}")
    public void refresh() {
        try {
            String v = redis.opsForValue().get("degrade:level");
            level = v == null ? 0 : Integer.parseInt(v);
        } catch (Exception ignored) { /* 保持上次值 */ }
    }

    public boolean seckillEnabled() { return level < 3; }
    public boolean showExactStock() { return level < 1; }
    public boolean browseEnabled()  { return level < 4; }
    public int pollIntervalMs()     { return level >= 2 ? d.getDegradedPollIntervalMs()
                                                        : d.getPollIntervalMs(); }
}
```

本地 volatile 变量 + 每秒刷新，请求路径上零 Redis 调用。Redis 挂了保持上次值，
不会因为读不到开关就全部降级（那会把 Redis 故障放大成全站故障）。

> **实现里拆成了两个 key，生效等级取最大值。** 上面的写法只有一个
> `degrade:level`，而自动监控每 15 秒会重算一次目标等级——于是运维手动降到
> Level 4 之后，下一轮自动计算就把它抹回 0，而做这个决定的人正在处理别的事故，
> 根本不知道开关自己弹回去了。
>
> | key | 写入方 | TTL | 理由 |
> | --- | --- | --- | --- |
> | `degrade:level` | 管理接口 | **无** | 人做的决定不该悄悄失效，必须显式解除 |
> | `degrade:level:auto` | 监控任务 | 300s | 写入 Level 3 的 job 实例崩溃后没人负责删它，TTL 让最坏情况变成"几分钟后自动恢复" |
>
> 生效等级 = `max(manual, auto)`，于是**自动机制只能收紧，永远盖不过人的决定**。
> 同理 `fss.degrade.seckill-enabled` 这个配置项也是"与"关系。
>
> 代价是自动监控必须拿 `autoLevel` 而不是生效等级去做"有没有变"的判断：
> 用生效等级时，人工降到 4 而自动算出 0 会让它每轮都认为"变了"，
> 每 15 秒写一次 Redis、发一条"4 → 0"的告警，而实际上什么都没变。

自动触发条件（由 job 角色监控后写 Redis）：

| 条件 | 目标 Level |
| --- | --- |
| 消息积压 > 50000 | 3 |
| 秒杀接口错误率 > 20% 持续 30s | 2 |
| Redis 连接失败率 > 10% | 3 |
| MySQL 连接池使用率 > 90% 持续 30s | 2 |
| 消费端 TPS 跌至 0 持续 60s | 3 |

自动降级必须能自动恢复，且恢复阈值低于触发阈值（滞回），否则会在阈值附近震荡。

> **目标等级 = 各条件的最大值，不是"最后一个触发的条件"。** 逐条件顺序判断、
> 后面覆盖前面的话会出现：积压超阈值判定 Level 3，接着"连接池正常"这一条把它写回 0
> ——秒杀在积压 8 万条的情况下重新开闸。取最大值天然满足"任何一个条件要求收紧就收紧"，
> 而且顺带解决了自动恢复：每轮从 0 重算，所有条件退回时结果自然是 0，
> 不需要额外记"是谁触发的、什么时候能解除"。无状态的算法在多实例、重启、切主之后
> 都还是对的。
>
> **采不到数据时必须让这一条不参与计算，而不是当成 0。** broker 挂了正是最该降级的
> 时候，判 0 会解除降级把流量全放进来。实现里返回 `null` 表示"这一条没有意见"，
> 保持当前等级。
>
> **实现只接了积压与连接池等待两条**，另外三条没接：错误率与"消费端 TPS 跌零"
> 需要在应用内维护 30~60 秒的滑动窗口，而这件事 Sentinel 的慢调用比例熔断
> （`seckill:submit`）和 Prometheus 侧的 `SeckillErrorRateHigh` 规则已经各做了一遍。
> 在第三个地方再实现一次同样的窗口统计，只会多一处可能与另两处不一致的判断。
> 这里只接**别处没有的信号**。消费端停滞用"积压 > 0 且与上一轮没有减少"来判，
> 不用采样 TPS——积压本身的变化量已经蕴含了这个信息，且不受生产侧速率干扰。

## 5. 安全

| 项 | 措施 |
| --- | --- |
| 传输 | 演示部署为明文 HTTP（两个 nginx 均 `listen 80`，未配 TLS/HSTS）；生产需在网关层终止 TLS |
| 密码 | BCrypt 强度 10，不可逆；登录失败不区分"用户不存在"与"密码错误" |
| 会话 | JWT 2 小时过期；`jti` 存 Redis 支持主动失效；不使用 refresh token（项目规模不需要） |
| 权限 | 自研 `AdminAuthFilter` 按 `/api/admin/` 前缀统一拦截并校验 `role == 1`；该前缀同时便于网关层隔离。未引入 `spring-boot-starter-security`，无方法级注解鉴权 |
| 越权 | 所有按 ID 查询的资源都校验归属；订单/支付一律带 `userId` 条件查询而非查完再判断 |
| 价格 | 秒杀价只从 `t_seckill_goods` 读取；消息体、请求体中的任何金额字段都不采信 |
| 支付 | 回调验签 + 时间戳防重放 + 金额比对 + `uk_out_trade_no` 幂等 |
| 注入 | 全部用 MyBatis `#{}` 参数绑定；无接收排序字段的接口，`ORDER BY` 均为 SQL 字面量，不存在拼接 |
| XSS | 服务端未做 HTML 转义与富文本过滤。当前风险低是因为响应全为 JSON、前端 Vue 默认转义；若引入富文本或服务端渲染需补白名单过滤 |
| 日志脱敏 | 密码、token、签名一律不落日志；手机号不参与任何日志输出（未实现掩码函数） |
| 越界枚举 | 状态值从请求进来时校验在合法枚举内，不直接存 |

### 越权查询的正确写法

```java
// 错：先查后判，存在信息泄漏与时序差异
Order o = orderMapper.selectByOrderNo(orderNo);
if (!o.getUserId().equals(currentUserId)) throw ...;

// 对：条件带进 SQL，查不到就是查不到
Order o = orderMapper.selectByOrderNoAndUser(orderNo, currentUserId);
if (o == null) throw new BizException(ErrorCode.ORDER_NOT_FOUND);
```

后者对"订单不存在"和"订单不属于你"返回完全一致的结果与耗时，不泄漏订单号有效性。

### 动态排序白名单

```java
private static final Set<String> SORTABLE = Set.of("create_time", "pay_amount");

if (!SORTABLE.contains(req.getSortBy())) {
    throw new BizException(ErrorCode.PARAM_INVALID, "不支持的排序字段");
}
```

## 6. 监控指标

### 业务指标（Micrometer Counter / Gauge）

```java
// 计数器
fss_seckill_request_total{activity, sku, result}     // result: qualified/stock_out/dup/blocked/error
fss_seckill_qualified_total{activity, sku}
fss_order_created_total{activity, sku}
fss_order_create_failed_total{activity, sku, reason}
fss_order_paid_total{activity, sku}
fss_order_cancelled_total{activity, sku, reason}     // reason: timeout/user/system
fss_stock_rollback_total{activity, sku, type}        // type: release/compensate
fss_reconcile_diff_total{type}                        // type: qualification/stock/payment
fss_mq_resend_total{topic}
fss_dlq_total{topic}

// 仪表
fss_stock_remain{activity, sku}                       // Redis 剩余库存

```

`fss_stock_remain` 与 `fss_stock_db_available` 同时上报，Grafana 里画在同一张图上，
两条线的差值就是排队中的量。差值持续扩大意味着消费端跟不上，一眼可见。

### 技术指标

Spring Boot Actuator + Micrometer 自带的加上：

```
http_server_requests_seconds{uri, status}             // QPS / RT / P95 / P99
jvm_memory_used_bytes, jvm_gc_pause_seconds
jvm_threads_live_threads
hikaricp_connections_active / _pending / _timeout_total
lettuce_command_completion_seconds                    // Redis 命令耗时
rocketmq_consumer_lag

```

`fss_lua_execution_seconds` 单独埋点：Lua 脚本是整个系统的串行瓶颈，
它的 P99 直接决定秒杀接口的 P99。

### 埋点位置

```java
@Aspect @Component
public class SeckillMetricsAspect {
    @Around("@annotation(com.fss.common.annotation.Metered)")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        Timer.Sample s = Timer.start(registry);
        String result = "success";
        try {
            return pjp.proceed();
        } catch (BizException e) {
            result = e.getErrorCode().name().toLowerCase();
            throw e;
        } catch (Throwable t) {
            result = "error";
            throw t;
        } finally {
            s.stop(registry.timer("fss_seckill_duration", "result", result));
            registry.counter("fss_seckill_request_total", "result", result).increment();
        }
    }
}
```

用 `result` 标签区分失败原因，而不是为每种失败建一个 Counter——标签维度可以在
Grafana 里任意聚合，独立 Counter 不行。

注意标签基数：`activity` 和 `sku` 作为标签是可以的（活动数量有限），
但**绝不能把 `userId` 或 `requestNo` 作为标签**，那会让 Prometheus 时间序列爆炸。

### 指标名不能带 Prometheus 的保留后缀

实现时踩到的坑，而且**单元测试抓不到**：Micrometer 里注册的名字和导出到
`/actuator/prometheus` 的名字不是同一个东西。prometheus-metrics-core 1.x 会剥掉
保留后缀（`_total` / `_created` / `_sum` / `_count` / `_bucket` / `_info`），
Counter 再自己补一个 `_total` 回去：

```
fss_order_created_total  →  剥 _total → fss_order_created → 剥 _created → fss_order → fss_order_total
fss_stock_total（Gauge） →  剥 _total → fss_stock（Gauge 不补回去）
```

而 `registry.find("fss_order_created_total")` 在**注册侧**照样找得到——所以断言指标
存在的那些用例全绿，告警规则和看板却在查一个不存在的序列。**Prometheus 对
"查不到序列"的表达式既不报错也不告警**，规则就这么静默失效了。

上表中的两个名字因此改成 `fss_order_create_total` 与 `fss_stock_capacity`，
并且加了一个直接断言**导出文本**的用例（`MetricsExportTest`），
把 `alert-rules.yml` 与看板 JSON 里引用的每个 `fss_` 指标名都与导出内容对一遍。

### Timer 要用 `publishPercentileHistogram` 而不是 `publishPercentiles`

两个方法名字很像，导出的东西完全不同：

| | 导出内容 | 能否跨实例聚合 |
| --- | --- | --- |
| `publishPercentiles(0.99)` | `{quantile="0.99"}`，应用内算好 | **不能**（分位数不可求平均） |
| `publishPercentileHistogram()` | `_bucket` 系列 | 能（桶是可加的） |

告警规则 `LuaSlow` 与看板都用
`histogram_quantile(... rate(fss_lua_execution_seconds_bucket[5m]))`，
配成前者时那个查询**返回空**——同样是静默失效。

### 库存仪表用推送而不是回调采样

`Gauge.builder(name, () -> readRedis())` 形式的仪表在**每次抓取时**执行。
1 个活动 10 个 SKU、4 个库存指标，一次抓取就是 40 次 Redis/DB 查询；
抓取间隔 15 秒的话，监控本身成了一个稳定的负载源。

更糟的是失败模式：Redis 变慢 → 抓取超时 → **整个 `/actuator/prometheus` 端点失败**
→ 连"Redis 慢了"这件事都看不到了，因为报告它的那条曲线也断了。

实现改成推送：对账任务本来就要读这四个值（它就是干这个的），顺手写进内存；
抓取只是读内存。代价是数值最多滞后一个对账周期（5 分钟），
对"库存是否漂移"这种问题完全够——它本来就不是秒级指标。

用 `MultiGauge` 而不是自己维护一个 Map：活动会不断新增，结束的活动如果不清理，
时间序列只增不减。`MultiGauge.register` 会整体替换，这一轮没有的行自动消失，
正好对上"活动结束就不再上报"的语义。

## 7. 告警规则

Prometheus alert rules，按严重程度分级。

```yaml
groups:
- name: fss-critical
  rules:
  - alert: RedisStockNegative
    expr: fss_stock_remain < 0
    for: 0m
    labels: { severity: P1 }
    annotations: { summary: "Redis 库存为负，存在超卖" }

  - alert: RedisStockGreaterThanDb
    expr: fss_stock_remain > fss_stock_db_available
    for: 1m
    labels: { severity: P1 }
    annotations: { summary: "Redis 库存大于 DB，库存视图错乱" }

  - alert: OrderExceedsTotalStock
    expr: sum by (activity, sku) (fss_order_created_total) > on (activity, sku) fss_stock_total
    for: 0m
    labels: { severity: P1 }
    annotations: { summary: "订单数超过总库存，已超卖" }

  - alert: PaymentReconcileDiff
    expr: increase(fss_reconcile_diff_total{type="payment"}[10m]) > 0
    for: 0m
    labels: { severity: P1 }
    annotations: { summary: "支付对账出现差异，可能资损" }

- name: fss-warning
  rules:
  - alert: MqBacklogHigh
    expr: fss_mq_backlog{topic="FSS_ORDER_CREATE"} > 20000
    for: 2m
    labels: { severity: P2 }

  - alert: SeckillErrorRateHigh
    expr: |
      sum(rate(fss_seckill_request_total{result="error"}[1m]))
      / sum(rate(fss_seckill_request_total[1m])) > 0.05
    for: 2m
    labels: { severity: P2 }

  - alert: HikariPoolExhausted
    expr: hikaricp_connections_pending > 5
    for: 1m
    labels: { severity: P2 }

  - alert: LongQueueingRequests
    expr: fss_stock_queueing > 500
    for: 5m
    labels: { severity: P2 }
    annotations: { summary: "大量请求长期排队，消费端可能卡住" }

  - alert: DlqNotEmpty
    expr: increase(fss_dlq_total[5m]) > 0
    for: 0m
    labels: { severity: P2 }

  - alert: ReconcileJobFailing
    expr: increase(fss_job_error_total{job=~"reconcile.*"}[15m]) >= 3
    for: 0m
    labels: { severity: P2 }
```

P1 触发即刻通知（短信/电话），P2 进工作时间群通知。
`for: 0m` 用于"发生即异常"的不变量违反，`for: 2m` 用于需要持续观察的比率类指标。

### 告警从一个统一出口发出

阶段一到三的代码里"需要人介入"的场合写的是 `log.error("...需人工处理")`，
那意味着告警的触发条件散落在几十处日志文本里，真接告警系统时没人能回答
"我们一共会发多少种告警"。实现补了一个 `AlarmService`，做三件事：

1. **固定日志格式** `stage=ALARM severity=P1 event=... key=...`，Loki 一条查询就能
   拉出全部告警
2. **同时打指标** `fss_alarm_total{severity, event}`。日志告警依赖日志管道，
   而日志管道本身也会挂；指标这条路是独立的，还能做"5 分钟内 P1 增量 > 0"这类规则
3. **吞掉自身异常**。告警发不出去绝不能把业务链路带崩——最需要告警的时刻
   往往正是依赖不稳的时刻

`event` 必须是**有限的常量集合**（它进了 Prometheus 标签），高基数的 `key`
（orderNo / requestNo）只进日志。

**不做重复抑制。** 同一事件每秒触发一千次就打一千条，看起来像缺陷，但抑制需要状态
（内存里的话多实例各抑制一份、重启即丢；Redis 里的话告警链路又多一个依赖，
而 Redis 挂掉正是要告警的场景）。收敛留给告警系统做——Prometheus 的 `for:` 与
Alertmanager 的 `group_interval` 就是干这个的，应用侧硬做一遍只会让
"为什么这条告警没发出来"多一个排查层。

本项目没有真实的短信/电话通道（`P1` 只是日志与指标里的一个标签）。
这是演示环境的取舍，但触发点、分级、事件名都是真的，接通道只需要加一个 HTTP 调用。

### 定时任务线程池必须调大

阶段四之前只有几个互不重叠的 cron 任务，Spring Boot 默认的
`spring.task.scheduling.pool.size = 1` 够用。现在多了 `DegradeSwitch` 每秒刷新一次
开关，而它和"扫描关单"共用这个池——单线程下一轮扫了 3 分钟的关单任务会让降级开关
整整 3 分钟不更新，**恰好是最需要它更新的时候**。给 4 个线程让快慢任务互不阻塞。

## 8. 链路追踪

### TraceId 贯穿

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class TraceIdFilter implements Filter {
    public static final String TRACE_ID = "traceId";
    public static final String HEADER   = "X-Trace-Id";

    @Override
    public void doFilter(ServletRequest req, ServletResponse resp, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest r = (HttpServletRequest) req;
        String traceId = Optional.ofNullable(r.getHeader(HEADER))
                .filter(StringUtils::hasText)
                .orElseGet(() -> IdGenerator.traceId());
        MDC.put(TRACE_ID, traceId);
        ((HttpServletResponse) resp).setHeader(HEADER, traceId);
        try {
            chain.doFilter(req, resp);
        } finally {
            MDC.clear();
        }
    }
}
```

跨 MQ 传递：消息体带 `traceId` 字段，消费端 `onMessage` 开头
`MDC.put(TRACE_ID, msg.getTraceId())`，`finally` 里 `MDC.clear()`。

跨线程传递：定时任务、`@Async`、缓存重建线程池都要包装 Runnable：

```java
public static Runnable wrap(Runnable task) {
    Map<String, String> ctx = MDC.getCopyOfContextMap();
    return () -> {
        if (ctx != null) MDC.setContextMap(ctx);
        try { task.run(); } finally { MDC.clear(); }
    };
}
```

不 wrap 的话，异步执行的日志会丢 traceId，恰好这些异步路径（缓存重建、
提交后回调）是最需要追踪的地方。

### 日志格式

```
%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level [%X{traceId}] %logger{36} - %msg%n
```

关键节点的结构化日志，字段固定便于 Loki 检索：

```java
log.info("stage=SECKILL_LUA requestNo={} userId={} activityId={} skuId={} code={} remain={} cost={}ms",
         requestNo, userId, activityId, skuId, out.code(), out.remainStock(), cost);
log.info("stage=MQ_SEND requestNo={} msgId={} topic={} status={}", ...);
log.info("stage=ORDER_CREATE requestNo={} orderNo={} result={} cost={}ms", ...);
log.info("stage=STOCK_DEDUCT_DB goodsId={} qty={} rows={}", ...);
log.info("stage=ORDER_CLOSE orderNo={} from={} to={} rows={}", ...);
log.info("stage=STOCK_RELEASE orderNo={} qty={} idempotent={}", ...);
```

`stage=` 前缀让 Loki 查询变成 `{app="fss"} |= "stage=ORDER_CREATE" | logfmt`，
能直接把日志当结构化数据用，不需要额外的 JSON 编码开销。

### 排查"用户有资格但没订单"

```
1. Loki 按 requestNo 检索全部日志
   {app="fss"} |= "R20260820200000001123456"
2. 看到 stage=SECKILL_LUA code=0  → Redis 预扣成功
3. 有无 stage=MQ_SEND status=OK   → 判断消息是否发出
4. 有无 stage=ORDER_CREATE        → 判断消费端是否处理
5. 查 t_mq_message WHERE biz_key = 'R...' → 看投递状态与重试次数
6. 查 t_reconcile_task WHERE biz_no = 'R...' → 看对账是否已识别
```

这条排查路径能在一分钟内定位问题环节，是设计"每个阶段都打一条结构化日志"的
直接收益。
