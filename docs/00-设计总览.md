# 00 设计总览

## 1. 八个关键决策

业务设计中未定论、但直接决定代码怎么写的点，在此固化。后续所有文档以本表为准。
决策 1~6 在开工前定下，7~8 是阶段四实现降级与补偿时补上的——它们同样属于
"文档没说、但不定就写不下去"的那一类。

### 决策 1：一人一单的最终归属与取消语义

- 唯一约束建在 `t_order (activity_id, sku_id, user_id)`。
- **订单取消后不允许该用户重新抢购。** 资格视为已消耗，库存回池给其他用户。

理由：允许重抢会让 Redis 与 MySQL 的判定规则不一致。Redis 侧删除用户标记后用户可
再次通过，但 MySQL 侧已取消订单的行仍然存在并占用唯一约束，消费端必然插入失败，
请求进入"创建失败 → 补偿"的死循环。要允许重抢，唯一约束必须改为
"仅对未取消订单生效"，MySQL 无法用普通唯一索引表达该语义（需要软删或状态列参与，
均引入新的并发窗口）。实习项目取"不允许重抢"，并在活动规则中明示。

> 若业务必须允许重抢：把唯一键改为 `(activity_id, sku_id, user_id, attempt_seq)`，
> 并新增 `t_user_purchase_quota` 表用条件更新维护"有效持有数"，见 [02-数据模型](02-数据模型.md#附-限购数量大于-1-的扩展方案)。

### 决策 2：库存回补拆成两种语义

原设计把"取消订单恢复库存"和"预扣成功但下单失败恢复库存"混为一件事，二者对
用户购买标记的处理必须相反：

| 语义 | 触发场景 | Redis 库存 | Redis 用户标记 | 幂等依据 |
| --- | --- | --- | --- | --- |
| **取消回补** `RELEASE` | 订单超时关闭、用户主动取消、支付失败 | `+qty` | **保留**（决策 1） | `t_order.stock_released` + `seckill:released:{k}` Set |
| **补偿回补** `ROLLBACK` | Redis 预扣成功但消息投递失败 / 消费端确定性失败 | `+qty` | **扣减并删除** | `seckill:req` 状态机（仅 `QUEUEING` 可回补） |

补偿回补时用户从未拿到订单，必须归还其购买资格，否则用户既没买到也不能再抢。
取消回补时用户已经拿到过订单，资格已消耗。

### 决策 3：延迟关单用 RocketMQ 5.x 定时消息

RocketMQ 4.x 只有 18 个固定延迟级别（1s/5s/10s/30s/1m/2m/3m/4m/5m/6m/7m/8m/9m/10m
/20m/30m/1h/2h），**没有 15 分钟**。要么把关单时长改成 10m 或 20m 去凑级别，要么
用 5.x 的任意时刻定时消息。选后者：`message.setDeliveryTimestamp(expireTime)`，
关单时长由配置项 `fss.order.pay-timeout` 决定，业务不被中间件级别绑架。

定时消息仍可能丢失，因此保留定时扫描兜底（见 [05](05-消息与一致性.md)）。

### 决策 4：Redis Key 统一 hash tag，保证 Lua 多 key 同 slot

秒杀 Lua 单次要读写 4 个 key（活动元数据、库存、用户标记、请求记录）。Redis
Cluster 要求同一脚本的所有 key 落在同一 slot，否则报 `CROSSSLOT`。所有秒杀相关
key 统一带 hash tag `{活动ID:SKU ID}`：

```
seckill:goods:{1001:2001}
seckill:stock:{1001:2001}
seckill:bought:{1001:2001}
seckill:req:{1001:2001}:R2026...
```

单机 Redis 不受影响，但从第一天就带上 tag，后续上 Cluster 零改造。

### 决策 5：消息可靠投递用本地消息表

原设计 §16.1 的"Redis 扣减成功但消息发送失败"，靠"重试 + 定时扫描排队中请求"
处理。问题是：应用在"Redis 扣减成功"和"消息发送成功"之间宕机，进程内重试逻辑
一起消失，只能等扫描任务发现，而扫描任务需要遍历 Redis 请求记录，成本高且不可靠。

改为：Redis 预扣成功后，**同一次 HTTP 请求内先写 `t_mq_message` 表（状态=待发送），
再发消息，发送成功后更新为已发送**。定时任务扫 `t_mq_message` 中超过 30s 仍为
待发送的记录重发；重发超过阈值则触发补偿回补（决策 2）。数据库落盘保证了崩溃
不丢投递意图。

代价是秒杀主链路多一次 DB 写。该写入是单行 insert、无行锁竞争、无热点，
与"扣库存"的热点行 UPDATE 完全不同量级；且可通过批量刷盘线程异步化（见 [05](05-消息与一致性.md#4-本地消息表)）。

### 决策 6：五模块模块化单体，单 jar 用 profile 分角色

不拆微服务。一个 `fss-app` jar，用 `--spring.profiles.active=web|consumer|job`
决定启用哪些 Bean。部署时同一镜像起三组容器，互不干扰：

- `web`：只开 Controller + Redis + 消息生产者
- `consumer`：只开 MQ Listener + MySQL
- `job`：只开定时任务，且必须单实例或加分布式锁

好处：Web 层被打爆时不影响订单消费；消费端可独立扩容；代码只有一份。

演示前端 `fss-web` 是第六个交付物但**不是第六个 Maven 模块**：它是独立的 npm 工程，
产物由 Nginx 发布，与 jar 的发布节奏无关。见 [01 §7](01-工程结构.md)。

### 决策 7：结果不确定时不猜，登记后事后判定

Redis 调用超时（`QueryTimeoutException`）时，脚本可能已执行、也可能没执行。
两个方向都不能猜：

| 猜法 | 猜错的后果 |
| --- | --- |
| 当成功 | 库存没扣却告诉用户排队中，最终没订单也没结论 |
| 当失败并回补 | 脚本其实执行了，回补凭空增加一份库存 → **超卖** |

所以：把整条消息记入 `seckill:uncertain`（ZSet，score = 登记时刻），返回
`SYSTEM_BUSY` 让用户用新 `requestNo` 重试（一人一单的 `bought` 标记会拦住重复中签）。
定时任务过一个**静置窗口**（`fss.reconcile.uncertain-settle`，默认 5s）后用
`EXISTS seckill:req:{a:s}:<requestNo>` 判定：存在就补发消息，不存在就什么都不做。

这条决策成立的前提是 Lua 的原子性——"预扣库存"和"写 req key"要么都发生要么都不发生，
因此 `req key` 存在 ⟺ 库存已扣。判不出来的（超过 `uncertain-retention`）转人工，
**绝不自动回补**：少卖一份可以人工修，超卖要赔钱。详见 [04 §5](04-核心流程.md)。

### 决策 8：降级等级人工与自动各一份，生效值取最大

降级不是一个布尔开关，而是 0~4 五个等级（见 [07 §4](07-防护与可观测.md)）：

```
Level 0  正常
Level 1  关闭非核心：活动详情不再展示精确库存，只给"有货/无货"
Level 2  拉长客户端轮询间隔 300ms → 2000ms
Level 3  暂停新资格分配（秒杀入口拒绝），已排队的继续处理完
Level 4  只保留订单查询与支付，商品浏览也关
```

状态存两个 Redis key：

| key | 写入者 | TTL | 理由 |
| --- | --- | --- | --- |
| `degrade:level` | 人工（管理接口） | **无** | 人的决定不该悄悄失效 |
| `degrade:level:auto` | `DegradeMonitorJob`（15s 一轮） | 有（`level-ttl-seconds`） | 写入者崩溃后没人负责删它 |

**生效等级 = max(人工, 自动)**，自动只能收紧不能放松。
只用一个 key 的话，运维手动降到 Level 4，下一轮自动计算就把它抹回 0——
而做这个决定的人正在处理别的事故，根本不知道开关自己弹回去了。

自动那一半的目标等级同样是**各条件的最大值**，不是"最后一个触发的条件"。
逐条件顺序覆盖会出现：积压超阈值判 Level 3，接着"连接池正常"把它写回 0，
于是秒杀在积压 8 万条的情况下重新开闸。取最大值顺带解决了自动恢复——每轮从 0 重算，
所有条件退回时结果自然是 0，不需要记"是谁触发的"。采不到数据时让那一条
**不参与计算**而不是当成 0：broker 挂了正是最该降级的时候。

等级本身读的是**本地 volatile 变量，每秒从 Redis 刷一次**，秒杀最热的那条路径上
零网络往返。刷新失败时保留上一个值而不是默认 0：Redis 挂掉前如果已经降到 3，
重连期间不该悄悄恢复放行。

**两层 Nginx 是刻意的**：前端镜像里那层只发静态、反代 API，是前端的门面；

本地 `docker compose --profile all` 起的是单容器 `web,consumer,job,dev` 一把全开，
上面这个三角色拆分是生产拓扑（见 [08 §5](08-实施与验收.md)）。

## 3. 容量假设与目标

| 指标 | 设计目标 |
| --- | --- |
| 注册用户 | 100 万 |
| 日活 | 10 万 |
| 单场活动参与用户 | 5 万 |
| 秒杀库存 | 1,000 件 |
| 峰值请求 | 10,000 QPS |
| 通过 Redis 拿到资格的请求 | ≤ 1,000 |
| 秒杀接口 P99 | ≤ 100 ms（返回 成功/失败/排队中） |
| 订单落库延迟 | P99 ≤ 3 s |
| 消费端处理能力 | ≥ 500 TPS/实例 |

核心比例：**10,000 : 1,000 = 10:1 的请求库存比**。设计重点是让 9,000 次注定失败的
请求在 Redis 层就结束，绝不触达 MySQL。

单实例线程配置按此推导：Tomcat `max-threads=400`，秒杀接口的工作量是"一段 Lua +
一次单行 INSERT + 一次 send"，不含建订单那 4 张表的写入与热点行竞争。

**这一节是目标，不是结论。** 实测见 [09 压测报告](09-压测报告.md)，与目标的差距和原因
都在那份报告里，此处只记两条对设计有反馈的：

- 读路径达标且有余量：活动详情 200 并发 → 12588 TPS / P99 35ms / 缓存命中率 99.991%。
- **写路径的天花板是熔断阈值而不是资源**：默认 `slow-rt-ms: 200` 下 25 并发零错误、
  40 并发即熔断；放宽到 2000ms 后 100 并发零错误。也就是说 `slow-rt-ms` 这个值
  当初是拍出来的，正确顺序是先压出 P99 基线再定阈值。
- 消费端吞吐（≥ 500 TPS/实例）**没测**，因为压测机与被测系统同机、跨 WSL2 的
  4 表事务上限远低于 500，测出来只反映环境。没测就不写数字。

## 4. 一致性边界

整体最终一致，但以下五条为**强保证**，任何异常路径都不得破坏：

| 不变量 | 保证手段 |
| --- | --- |
| 库存不超卖 | Redis Lua 原子判扣 + MySQL `WHERE available_stock >= qty` 条件更新 + `CHECK(available_stock >= 0)` |
| 一人一单 | Redis `seckill:bought` Hash 前置拦截 + `uk_activity_sku_user` 唯一索引兜底 |
| 订单不重复创建 | `uk_request_no` 唯一索引 + 消费端前置查询 |
| 库存不重复释放 | `t_order.stock_released` 条件更新 + `t_stock_log` 唯一键 + Redis `released` Set |
| 支付不重复入账 | `uk_pay_no` / `uk_out_trade_no` 唯一索引 + 状态机条件更新 `WHERE status = PENDING_PAY` |

库存账目的三条等式由对账任务每 5 分钟验证一次，每条只回答一个问题
（[05 §9](05-消息与一致性.md)）：

```
① total_stock == available_stock + locked_stock + sold_stock
      商品表自身是否自洽（恒等式，破了必然是某段 UPDATE 写错）
② locked_stock + sold_stock == Σ 未取消订单.quantity
      商品表与订单表是否吻合
③ redisStock == available_stock - 排队中数量
      Redis 与 DB 的差值是否正好是"已预扣未落库"的那部分
```

三条必须**相互独立**：把"排队中"塞进第一条会让它在有排队请求时恒为假，
于是每轮都判"DB 漂移"、自动修正永远不触发，症状是"对账一直在报差异，
但库存其实是对的"。故障演练的终态证据是 **9 个活动的账目等式全部成立**
（[10 §0](10-故障演练报告.md)）——经历了 pause Redis、`FLUSHDB`、pause MySQL、
pause broker、重投消息 ×10、删定时消息、三实例并发对账。

允许的不一致窗口：

- 页面展示库存与真实库存存在秒级偏差（可接受，最终以资格判定为准）。
- Redis 剩余库存与 MySQL `available_stock` 在"已预扣未落库"期间存在差值，
  差值上限 = 排队中请求数，由对账任务收敛。
- 降级 Level 1 起库存展示退化为"有货/无货"，精度是主动放弃的。

**所有失败方向上都选"少卖"而不是"超卖"**：判不出来就不自动修（决策 7）、
回补失败就让事务回滚（订单留在待支付由扫描重试）、`locked_stock` 不足就报错而不是
把库存凭空加回去。少卖一份可以人工修，超卖要赔钱。这条取向的完整清单见
[11 技术选型与取舍](11-技术选型与取舍.md)。

## 5. 与业务设计的差异说明

| 业务设计条目 | 本方案调整 | 原因 |
| --- | --- | --- |
| §15 取消后恢复库存并"删除或修改用户购买资格标记" | 只恢复库存，保留用户标记 | 决策 1、2，避免与 DB 唯一约束冲突 |
| §14.1 延迟消息 15 分钟 | 时长可配置，用 5.x 定时消息实现 | 决策 3，4.x 无 15m 级别 |
| §16.1 消息发送失败靠内存重试 | 前置本地消息表 | 决策 5，覆盖进程崩溃 |
| §5 七个业务模块 | 合并为五个 Maven 模块，业务模块作为 `fss-biz` 内的包 | 决策 6，避免模块数膨胀 |
| §6.5 秒杀商品含"数据版本" | 保留 `version` 但不用于秒杀主链路 | 主链路用条件更新而非 CAS 重试，CAS 在高竞争下重试率过高 |

实现过程中反过来发现设计文档需要修正的地方（共 25 条，含库存三分口径、
对账判据、降级双 key、指标命名等），逐条记在
[README「与设计文档的偏差」](../README.md#与设计文档的偏差)，
相应的文档段落都已改过。
