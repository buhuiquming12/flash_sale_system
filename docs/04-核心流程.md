# 04 核心流程

## 1. 提交秒杀请求（主链路）

### 时序

```
Client        Nginx       Web实例          Redis          MySQL         RocketMQ
  │             │            │               │              │              │
  ├─POST /seckill──────────► │               │              │              │
  │             ├─limit_req──►               │              │              │
  │             │            ├─JWT 解析       │              │              │
  │             │            ├─令牌桶(user/ip/activity)►     │              │
  │             │            ├─秒杀令牌校验──►│              │              │
  │             │            ├─生成 requestNo │              │              │
  │             │            ├─EVALSHA seckill.lua ─────────►│              │
  │             │            │   活动/时间/一人一单/库存      │              │
  │             │            │◄─ {0, remain} ─│              │              │
  │             │            ├─INSERT t_mq_message(待发送)──►│              │
  │             │            ├─syncSend ORDER_CREATE ──────────────────────►│
  │             │            ├─UPDATE t_mq_message(已发送)─►│              │
  │◄─202 {requestNo, QUEUEING}                │              │              │
```

### 代码骨架

```java
@Service
@RequiredArgsConstructor
public class SeckillServiceImpl implements SeckillService {

    private final SeckillExecutor executor;
    private final ReliableMqProducer producer;
    private final SeckillTokenService tokenService;
    private final SeckillResultService resultService;
    private final FssProperties props;

    @Override
    public SeckillSubmitVO submit(SeckillCmd cmd, long userId) {
        // 1. 降级开关
        if (!props.getDegrade().isSeckillEnabled()) {
            throw new BizException(ErrorCode.SERVICE_DEGRADED);
        }
        // 2. 秒杀令牌（绑定 user+activity+sku，一次性）
        tokenService.verifyAndConsume(cmd.getToken(), userId, cmd.getActivityId(), cmd.getSkuId());

        // 3. 请求号 + 链路号
        String requestNo = IdGenerator.requestNo();
        String traceId   = MDC.get(TraceIdFilter.TRACE_ID);

        // 4. Redis 原子判定
        SeckillOutcome out;
        try {
            out = executor.trySeckill(cmd.getActivityId(), cmd.getSkuId(),
                                      userId, cmd.getQuantity(), requestNo, traceId);
        } catch (Exception e) {
            // 结果不确定，见 §5
            log.error("Redis 秒杀脚本异常 requestNo={}", requestNo, e);
            uncertainRecorder.record(requestNo, cmd, userId);
            throw new BizException(ErrorCode.SYSTEM_BUSY);
        }

        if (!out.success()) {
            metrics.countReject(out.code());
            throw new BizException(out.toErrorCode());     // 库存不足/重复购买/活动已结束…
        }

        // 5. 可靠投递：先落本地消息表，再发消息（决策 5）
        OrderCreateMessage msg = OrderCreateMessage.builder()
                .requestNo(requestNo).userId(userId)
                .activityId(cmd.getActivityId()).skuId(cmd.getSkuId())
                .quantity(cmd.getQuantity()).traceId(traceId)
                .requestTime(LocalDateTime.now()).version(1)
                .build();

        producer.sendReliable(props.getMq().getTopic().getOrderCreate(),
                              requestNo, msg, null);

        // 6. 立即返回排队中
        metrics.countQualified();
        return new SeckillSubmitVO(requestNo, SeckillRequestStatus.QUEUEING, out.remainStock());
    }
}
```

### 消息体中不带价格

`OrderCreateMessage` 只有 `activityId / skuId / quantity`，**没有 price**。
消费端从 `t_seckill_goods.seckill_price` 读取。原因：消息体一旦包含金额，
就成了客户端到订单金额之间的一条可篡改路径（消息可被伪造重放）。价格必须由
服务端在落库时刻从权威数据源读取。

## 2. 异步创建订单（消费端）

```java
@Profile("consumer")
@Component
@RocketMQMessageListener(
        topic = "${fss.mq.topic.order-create}",
        consumerGroup = "${fss.mq.group.order-create}",
        consumeThreadNumber = 20,
        maxReconsumeTimes = 5)
public class OrderCreateListener implements RocketMQListener<OrderCreateMessage> {

    @Override
    public void onMessage(OrderCreateMessage msg) {
        MDC.put(TraceIdFilter.TRACE_ID, msg.getTraceId());
        try {
            orderCreateService.handle(msg);
        } catch (BizException e) {
            if (e.getErrorCode().isDeterministic()) {
                // 确定性失败（库存真的没了、限购超了）→ 不重试，走补偿
                compensateService.rollback(msg, e.getMessage());
                return;                       // 正常返回 = ACK
            }
            throw e;                          // 非确定性 → 抛出触发 RocketMQ 重试
        } finally {
            MDC.clear();
        }
    }
}
```

**RocketMQ 的重试语义**：`onMessage` 正常返回即 ACK；抛异常则 `RECONSUME_LATER`，
按 `maxReconsumeTimes` 重试后进 `%DLQ%GID_xxx`。因此"确定性失败"必须
自己处理完并正常返回，否则会白重试 5 次再进死信。

### 落库事务

```java
@Service
@RequiredArgsConstructor
public class OrderCreateService {

    @Transactional(rollbackFor = Exception.class)
    public void handle(OrderCreateMessage msg) {
        // 幂等层 1：请求号已处理？
        Order exist = orderMapper.selectByRequestNo(msg.getRequestNo());
        if (exist != null) {
            log.info("消息重复，订单已存在 requestNo={} orderNo={}",
                     msg.getRequestNo(), exist.getOrderNo());
            return;                          // 直接 ACK，不做任何写操作
        }
        // 幂等层 2：该用户在该活动该 SKU 上已有订单？（Redis 失效后的兜底）
        Order dup = orderMapper.selectByActivitySkuUser(
                msg.getActivityId(), msg.getSkuId(), msg.getUserId());
        if (dup != null) {
            throw new BizException(ErrorCode.ALREADY_BOUGHT);   // 确定性失败 → 补偿
        }

        SeckillGoods goods = goodsMapper.selectByActivitySku(msg.getActivityId(), msg.getSkuId());
        require(goods != null, ErrorCode.GOODS_NOT_FOUND);

        // 3. 条件扣减，一条语句完成判断+扣减
        int rows = goodsMapper.deductStock(goods.getId(), msg.getQuantity());
        if (rows == 0) {
            throw new BizException(ErrorCode.STOCK_NOT_ENOUGH);  // 确定性失败 → 补偿
        }

        // 4. 建订单（价格来自 DB，不信消息）
        BigDecimal unitPrice = goods.getSeckillPrice();
        BigDecimal payAmount = unitPrice.multiply(BigDecimal.valueOf(msg.getQuantity()));
        LocalDateTime expireTime = LocalDateTime.now().plus(props.getOrder().getPayTimeout());

        Order order = Order.builder()
                .orderNo(IdGenerator.orderNo()).requestNo(msg.getRequestNo())
                .userId(msg.getUserId()).activityId(msg.getActivityId()).skuId(msg.getSkuId())
                .status(OrderStatus.PENDING_PAY.code())
                .totalAmount(payAmount).payAmount(payAmount)
                .quantity(msg.getQuantity()).stockReleased(0)
                .expireTime(expireTime).build();
        orderMapper.insert(order);            // uk_request_no / uk_activity_sku_user 兜底

        // 5. 明细快照
        Sku sku = skuMapper.selectById(msg.getSkuId());
        Product p = productMapper.selectById(sku.getProductId());
        orderItemMapper.insert(OrderItem.builder()
                .orderNo(order.getOrderNo()).skuId(sku.getId()).productId(p.getId())
                .productTitle(p.getTitle()).specSnapshot(sku.getSpec())
                .imageSnapshot(p.getMainImage()).unitPrice(unitPrice)
                .quantity(msg.getQuantity()).build());

        // 6. 库存流水（uk_biz_type 保证幂等）
        stockLogMapper.insert(StockLog.of(msg.getRequestNo(), StockChangeType.CONFIRM_DEDUCT,
                -msg.getQuantity(), goods));

        // 7. 请求记录落库
        requestMapper.insertOrUpdateSuccess(msg, order.getOrderNo());

        // 8. 定时关单消息，同样走本地消息表
        producer.registerAfterCommit(props.getMq().getTopic().getOrderClose(),
                order.getOrderNo(),
                new OrderCloseMessage(order.getOrderNo(), order.getUserId()),
                expireTime);

        // 9. 回写 Redis 结果（事务提交后执行，见下）
        registerAfterCommit(() -> resultService.markSuccess(
                msg.getActivityId(), msg.getSkuId(), msg.getRequestNo(), order.getOrderNo()));
    }
}
```

### 为什么 Redis 回写要放在事务提交之后

如果在事务内就把 Redis 请求状态改成 SUCCESS，而事务随后回滚，客户端会查到
"成功 + 订单号"，但订单并不存在。用 `TransactionSynchronizationManager` 注册
提交后回调：

```java
private void registerAfterCommit(Runnable action) {
    if (TransactionSynchronizationManager.isSynchronizationActive()) {
        TransactionSynchronizationManager.registerSynchronization(
                new TransactionSynchronization() {
                    @Override public void afterCommit() { action.run(); }
                });
    } else {
        action.run();
    }
}
```

提交后回写失败（Redis 抖动）不影响正确性：客户端查不到结果会继续轮询，
`SeckillResultService.query()` 在 Redis 未命中时**回查数据库** `t_order` +
`t_seckill_request`，能拿到真实结论。

## 3. 查询秒杀结果

```java
public SeckillResultVO query(String requestNo, long userId) {
    // 1. 先查 Redis（活动 tag 从 requestNo 无法反推，故客户端需带 activityId/skuId）
    SeckillResultVO r = resultService.queryFromRedis(activityId, skuId, requestNo);
    if (r != null && r.getStatus() != QUEUEING) {
        return r;
    }
    // 2. Redis 无结果或仍排队 → 回查 DB（Redis 结果可能已过期，或回写失败）
    Order order = orderMapper.selectByRequestNo(requestNo);
    if (order != null) {
        assertOwner(order.getUserId(), userId);
        return SeckillResultVO.success(requestNo, order.getOrderNo());
    }
    SeckillRequest req = requestMapper.selectByRequestNo(requestNo);
    if (req != null) {
        return SeckillResultVO.of(req);
    }
    // 3. 都没有：Redis 说排队中就返回排队中，否则视为不存在
    return r != null ? r : SeckillResultVO.notFound(requestNo);
}
```

客户端轮询策略（退避）：

```
第 1 次   300 ms
第 2 次   500 ms
第 3 次   800 ms
第 4 次  1300 ms
第 5 次  2000 ms
之后固定 2000 ms，累计 20 s 未出结论 → 提示"请稍后在订单列表查看"
```

服务端对结果查询接口也限流（单用户 5 QPS），防止客户端 bug 打成 DDoS。

## 4. 订单状态机

```text
                    ┌──────────────┐
                    │  PENDING_PAY │ 0
                    └──┬────────┬──┘
             支付成功   │        │  超时/用户取消
                       ▼        ▼
                  ┌────────┐  ┌───────────┐
                  │  PAID  │1 │ CANCELLED │2
                  └───┬─┬──┘  └───────────┘
            发货完成   │ │  申请退款
                      ▼ ▼
        ┌──────────┐  ┌───────────┐
        │ FINISHED │3 │ REFUNDING │4
        └──────────┘  └─────┬─────┘
                            ▼
                      ┌──────────┐
                      │ REFUNDED │5
                      └──────────┘
```

允许的迁移，集中定义并在每次变更前断言：

```java
public final class OrderStateMachine {

    private static final Map<OrderStatus, Set<OrderStatus>> ALLOWED = Map.of(
            PENDING_PAY, EnumSet.of(PAID, CANCELLED),
            PAID,        EnumSet.of(FINISHED, REFUNDING),
            REFUNDING,   EnumSet.of(REFUNDED, PAID),   // 退款被拒回到已支付
            CANCELLED,   EnumSet.noneOf(OrderStatus.class),
            FINISHED,    EnumSet.of(REFUNDING),
            REFUNDED,    EnumSet.noneOf(OrderStatus.class));

    public static void assertTransfer(OrderStatus from, OrderStatus to) {
        if (!ALLOWED.getOrDefault(from, Set.of()).contains(to)) {
            throw new BizException(ErrorCode.ORDER_STATUS_ILLEGAL,
                    "非法状态流转 " + from + " → " + to);
        }
    }
}
```

**但状态机断言只是防御性编程，不是并发正确性的来源。**
真正保证并发安全的是所有状态变更都用带旧状态条件的 UPDATE：

```xml
<update id="updateStatus">
    UPDATE t_order
       SET status = #{to}, ${extraSet}
     WHERE order_no = #{orderNo}
       AND status = #{from}
</update>
```

影响行数 0 → 说明别人抢先改了状态，读最新状态重新决策。

## 5. Redis 调用结果不确定时怎么办

`redis.execute` 抛出 `QueryTimeoutException` 时，脚本可能已执行（命令到了服务端，
响应丢在网络上），也可能没执行。此时：

- **不能当成功**：可能库存没扣，却给用户返回了排队中，最终没订单。
- **不能当失败后直接回补**：可能脚本根本没执行，回补会凭空增加库存。

处理：把 `requestNo` 记入"待确认"集合，返回 `SYSTEM_BUSY` 让用户重试。
定时任务用 `EXISTS seckill:req:{a:s}:<requestNo>` 判定真实结果：

```java
@Scheduled(fixedDelay = 10_000)
@DistributedLock(key = "job:uncertain-check", waitTime = 0, leaseTime = 30)
public void checkUncertain() {
    for (UncertainRecord rec : uncertainRecorder.take(500)) {
        String reqKey = "seckill:req:{" + rec.tag() + "}:" + rec.requestNo();
        if (Boolean.TRUE.equals(redis.hasKey(reqKey))) {
            // 脚本确实执行了且成功预扣 → 补发消息
            producer.sendReliable(TOPIC_ORDER_CREATE, rec.requestNo(), rec.toMessage(), null);
        }
        // key 不存在 → 脚本没执行，库存没动，什么都不用做
        uncertainRecorder.remove(rec.requestNo());
    }
}
```

`UncertainRecord` 存在 Redis List（`seckill:uncertain`）里，而不是内存队列——
应用崩溃后这些记录必须还在。

**注意这里为什么安全**：Lua 脚本的原子性保证"预扣库存"和"写 req key"要么都发生
要么都不发生。因此 `req key` 存在 ⟺ 库存已扣。这条等价关系是整个不确定性处理的
基石，也是脚本 A 里必须把 `HSET reqKey` 放在同一脚本内的原因。

## 6. 支付与取消的并发

两个操作同时到达同一订单：

```java
// 支付
@Transactional
public void paySuccess(String payNo, String orderNo, BigDecimal amount) {
    Payment pay = paymentMapper.selectByPayNo(payNo);
    if (pay.getStatus() == PayStatus.SUCCESS.code()) return;   // 回调重复，幂等

    Order order = orderMapper.selectByOrderNo(orderNo);
    require(order.getPayAmount().compareTo(amount) == 0, ErrorCode.PAY_AMOUNT_MISMATCH);

    int rows = orderMapper.updateStatus(orderNo,
            OrderStatus.PENDING_PAY.code(), OrderStatus.PAID.code(), "pay_time = NOW(3)");
    if (rows == 0) {
        // 抢输了：订单已被取消或已支付
        Order latest = orderMapper.selectByOrderNo(orderNo);
        if (latest.getStatus() == OrderStatus.CANCELLED.code()) {
            // 真实资金已收但订单已关 → 转退款流程 + 告警
            paymentMapper.updateStatus(payNo, PayStatus.SUCCESS.code());
            refundService.createRefund(orderNo, payNo, "订单已关闭，自动退款");
            alarm.send("支付与关单竞态", orderNo);
            return;
        }
        if (latest.getStatus() == OrderStatus.PAID.code()) return;   // 并发双支付，幂等
        throw new BizException(ErrorCode.ORDER_STATUS_ILLEGAL);
    }
    paymentMapper.updateStatus(payNo, PayStatus.SUCCESS.code());
    goodsMapper.moveLockedToSold(order.getActivityId(), order.getSkuId(), order.getQuantity());
}
```

```java
// 关单
@Transactional
public boolean closeOrder(String orderNo, String reason) {
    int rows = orderMapper.updateStatus(orderNo,
            OrderStatus.PENDING_PAY.code(), OrderStatus.CANCELLED.code(),
            "cancel_time = NOW(3), cancel_reason = '" + reason + "'");
    if (rows == 0) return false;    // 已支付或已取消，什么都不做

    // 关单成功才发库存释放消息
    producer.registerAfterCommit(TOPIC_STOCK_RELEASE, orderNo,
            new StockReleaseMessage(orderNo, ...), null);
    return true;
}
```

两者都用 `WHERE status = PENDING_PAY` 竞争同一行，MySQL 行锁保证只有一个
`rows == 1`。输的一方读最新状态走补救分支。

## 7. 超时关单

主：RocketMQ 5.x 定时消息，创建订单时按 `expire_time` 投递。

```java
Message<OrderCloseMessage> m = MessageBuilder.withPayload(payload)
        .setHeader(RocketMQHeaders.KEYS, orderNo)
        .build();
rocketMQTemplate.syncSendDeliverTimeMills(topic, m, expireTimeMillis);
```

辅：定时扫描，处理定时消息丢失、消费失败。

```java
@Scheduled(cron = "0 */2 * * * ?")
@DistributedLock(key = "job:close-expired", waitTime = 0, leaseTime = 100)
public void closeExpiredOrders() {
    LocalDateTime deadline = LocalDateTime.now().minus(props.getOrder().getCloseScanDelay());
    // 分页游标，避免一次捞太多
    long lastId = 0;
    while (true) {
        List<Order> batch = orderMapper.selectExpiredPendingPay(deadline, lastId, 200);
        if (batch.isEmpty()) break;
        for (Order o : batch) {
            try { orderService.closeOrder(o.getOrderNo(), "超时未支付(扫描)"); }
            catch (Exception e) { log.error("关单失败 {}", o.getOrderNo(), e); }
        }
        lastId = batch.get(batch.size() - 1).getId();
    }
}
```

扫描比定时消息晚 `close-scan-delay`（默认 2 分钟）触发，避免和定时消息抢同一批订单
造成大量无效竞争。即使抢到同一单，条件更新也保证只有一方成功。

## 8. 库存释放（取消回补）

```java
@Transactional
public void release(StockReleaseMessage msg) {
    // 幂等 1：订单级标记的条件更新，把自己变成唯一执行者
    int rows = orderMapper.markStockReleased(msg.getOrderNo());
    //  UPDATE t_order SET stock_released = 1 WHERE order_no = ? AND stock_released = 0
    if (rows == 0) {
        log.info("库存已释放过，跳过 orderNo={}", msg.getOrderNo());
        return;
    }
    Order order = orderMapper.selectByOrderNo(msg.getOrderNo());

    // 幂等 2：流水唯一键
    try {
        stockLogMapper.insert(StockLog.of(order.getOrderNo(),
                StockChangeType.CANCEL_RELEASE, order.getQuantity(), null));
    } catch (DuplicateKeyException e) {
        log.warn("库存流水已存在 orderNo={}", order.getOrderNo());
        return;
    }

    // DB 回补
    goodsMapper.restoreStock(order.getActivityId(), order.getSkuId(), order.getQuantity());
    //  UPDATE t_seckill_goods
    //     SET available_stock = available_stock + #{qty},
    //         released_stock  = released_stock + #{qty},
    //         status = CASE WHEN status = 2 THEN 1 ELSE status END
    //   WHERE activity_id = ? AND sku_id = ?

    // Redis 回补，提交后执行（脚本 C，SADD 幂等，不动 bought）
    registerAfterCommit(() -> executor.release(
            order.getActivityId(), order.getSkuId(), order.getOrderNo(), order.getQuantity()));
}
```

三层幂等：`stock_released` 条件更新 → `t_stock_log` 唯一键 → Redis `released` Set。
任意一层单独都够用，叠加是因为它们的失效场景不同（前两层防 DB 侧重复，
第三层防"DB 事务提交了但 Redis 回补重试"）。

## 9. 活动状态推进

活动状态不靠人工点击，由定时任务按时间推进，并写审计。

```java
@Scheduled(cron = "0 * * * * ?")
@DistributedLock(key = "job:activity-state", waitTime = 0, leaseTime = 50)
public void advanceState() {
    LocalDateTime now = LocalDateTime.now();
    // READY → RUNNING：已预热完成且到了开始时间
    activityMapper.startReadyActivities(now);
    //  UPDATE t_seckill_activity SET status = 2
    //   WHERE status = 1 AND warmup_state = 2 AND start_time <= #{now}

    // RUNNING → ENDED
    List<Long> ended = activityMapper.selectRunningEnded(now);
    for (Long id : ended) {
        if (activityMapper.endActivity(id, now) > 0) {
            // 停售所有 Redis 商品，让后续请求走 -2 快速失败
            warmupService.stopSelling(id);
        }
    }
}
```

**预热未完成的活动不会进入 RUNNING**，这防止了"到点开抢但 Redis 没数据"导致
所有请求返回 `-1 未预热`。此时用户看到的是"活动即将开始"，比看到系统错误好。
同时预热失败会告警，留出 5 分钟人工介入窗口。
