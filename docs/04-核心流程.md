# 04 核心流程

## 1. 提交秒杀请求（主链路）

### 时序

```
Client        Nginx       Web实例          Redis          MySQL         RocketMQ
  │             │            │               │              │              │
  ├─POST /seckill──────────► │               │              │              │
  │             ├─limit_req──►               │              │              │
  │             │            ├─JWT 解析 + 白名单校验 ────────►│              │
  │             │            ├─令牌桶(ip/user/activity)─────►│              │
  │             │            ├─降级开关（读本地 volatile，零往返）           │
  │             │            ├─Sentinel 入口（QPS + 慢调用熔断）            │
  │             │            ├─秒杀令牌 GETDEL ─────────────►│              │
  │             │            ├─生成 requestNo                │              │
  │             │            ├─EVALSHA seckill.lua ─────────►│              │
  │             │            │   活动/时间/一人一单/库存/写 req key          │

  │             │            ├─syncSend ORDER_CREATE ──────────────────────►│
  │             │            ├─UPDATE t_mq_message(已发送)─►│              │

```

### 代码骨架

```java
@Service
@RequiredArgsConstructor
public class SeckillServiceImpl implements SeckillService {

    private final SeckillExecutor          executor;
    private final SeckillTokenService      tokenService;
    private final SeckillCompensateService compensateService;
    private final UncertainRecorder        uncertainRecorder;
    private final ReliableMqProducer       producer;
    private final DegradeSwitch            degradeSwitch;
    private final SeckillMetrics           metrics;
    private final AlarmService             alarm;

    @Override
    @SentinelResource(value = SentinelConfig.RES_SECKILL_SUBMIT,
            blockHandler = "onSubmitBlocked",
            fallback = "onSubmitFallback",
            exceptionsToIgnore = BizException.class)   // ← 见下，最关键的一行
    public SeckillSubmitVO submit(SeckillCmd cmd, long userId) {
        // 1. 降级开关。放在最前面：降级的目的就是不消耗后面的资源。
        //    读的是本地 volatile（每秒从 Redis 刷一次），这条最热的路径上零网络往返
        if (!degradeSwitch.seckillEnabled()) {
            throw new BizException(ErrorCode.SERVICE_DEGRADED);
        }
        int quantity = cmd.getQuantity() == null ? 1 : cmd.getQuantity();
        Assert.require(quantity == 1, ErrorCode.PARAM_INVALID, "当前版本仅支持单件购买");

        // 2. 令牌校验（携带才校验，固定路径入口不带）。GETDEL 一次性消费
        if (cmd.getToken() != null && !cmd.getToken().isBlank()) {
            tokenService.verifyAndConsume(cmd.getToken(), userId, activityId, skuId);
        }

        String requestNo = IdGenerator.requestNo();
        OrderCreateMessage msg = OrderCreateMessage.builder()
                .requestNo(requestNo).userId(userId)
                .activityId(activityId).skuId(skuId).quantity(quantity)
                .requestTime(LocalDateTime.now()).traceId(TraceContext.get())
                .version(OrderCreateMessage.CURRENT_VERSION)
                .build();

        // 3. Lua 原子判定：活动校验、时间校验（Redis 时钟）、一人一单、库存预扣、
        //    写请求记录，五件事一次完成。这是整个系统唯一的资格分配入口
        SeckillOutcome outcome;
        try {
            outcome = executor.trySeckill(activityId, skuId, userId, quantity, requestNo, traceId);
        } catch (SeckillExecutor.UncertainResultException e) {
            // 结果不确定：既不能放行也不能回补，登记后交给定时任务判定，见 §5
            boolean recorded = uncertainRecorder.record(msg);
            alarm.p2(AlarmService.Event.REDIS_UNCERTAIN, requestNo,
                    recorded ? "已登记待确认" : "登记失败，只能靠库存对账发现");
            throw new BizException(ErrorCode.SYSTEM_BUSY, "系统繁忙，请稍后重试");
        }

        if (!outcome.qualified()) {
            ErrorCode ec = outcome.errorCode();
            // Lua 在时间/库存校验阶段直接返回，没有创建 req key。
            // 这里补一条结论进去（脚本 D）：客户端可能已经在轮询，
            // 给它明确答案比让它等超时好。注意这不是"回补"——这些请求没扣过库存
            executor.writeResult(activityId, skuId, requestNo, userId,
                    rejectStatusOf(ec), null, ec.getMessage());
            recordRejection(msg, ec);          // 落一条 t_seckill_request，供查询与对账
            throw new BizException(ec);
        }

        // 4. 投递创建订单消息。先落本地消息表，再 send；send 失败由重发任务兜住
        try {
            producer.sendReliable(MqTopics.ORDER_CREATE, requestNo, msg, null);
        } catch (Exception e) {
            // 走到这里说明连本地消息表都写不进去（send 失败不会抛到这里，
            // ReliableMqProducer 内部吞掉并转交重发任务）。投递意图彻底没能落盘，
            // 没有任何后续机制会为这个用户建订单 → 必须就地回补
            compensateService.rollback(msg, ErrorCode.SYSTEM_BUSY, "消息登记失败，已退回");
            throw new BizException(ErrorCode.SYSTEM_BUSY);
        }

        // 5. 立即返回排队中。remainStock 报 Redis 的值而不是 DB 的：
        //    Redis 才是资格分配的权威，两者的差值正是"排队中"的量。
        //    pollAfterMs 由降级开关下发，Level 2 起从 300ms 拉到 2000ms，不用发版
        return SeckillSubmitVO.queueing(requestNo, (int) outcome.remainStock(),
                degradeSwitch.pollIntervalMs());
    }
}
```

### `exceptionsToIgnore = BizException.class` 是这段 Sentinel 集成里最关键的一行

不写它的话，"库存不足"会被计入异常比例，几秒钟就把熔断器打开——**活动一售罄
整个接口就熔断了**。同时 `fallback` 会接住这个异常，把"库存不足"改写成"系统繁忙"，
用户以为是系统问题于是不停重试，反而放大流量。

业务失败不是故障，不能进故障统计。`fallback` 里还显式把 `BizException` 原样抛出
做双重保险：成本是三行代码，而漏掉它的后果是所有业务错误码被吞成"系统繁忙"——
接口不报错、监控不报警，只有用户在抱怨。

### 三条失败路径的处置各不相同

| 失败点 | Redis 状态 | 处置 | 为什么 |
| --- | --- | --- | --- |
| Lua 判定拒绝 | 没扣库存、没建 req key | 写结论（脚本 D）+ 落 `t_seckill_request` | 没扣过，不需要回补，只需要一个结论 |
| Redis 调用超时 | **不知道扣没扣** | 登记待确认 + 报 `SYSTEM_BUSY` | 猜错任一边都是资损或少卖，见 §5 |
| 本地消息表写失败 | 已扣库存、已记标记 | 立即回补（脚本 B） | 没有任何机制会为这个用户建订单 |

`send` 失败**不在**这张表里：那时投递意图已经落盘，重发任务会接管。

### 消息体中不带价格

`OrderCreateMessage` 只有 `activityId / skuId / quantity`，**没有 price**。
消费端从 `t_seckill_goods.seckill_price` 读取。原因：消息体一旦包含金额，
就成了客户端到订单金额之间的一条可篡改路径（消息可被伪造重放）。价格必须由
服务端在落库时刻从权威数据源读取。

消息体带 `version`：消费端在处理前先比对，收到比自己新的版本直接抛异常进死信。
新版本消息里字段含义可能变了，用旧代码解析出来的可能是一张金额为 0 的订单——
那比不处理危险得多。

## 2. 异步创建订单（消费端）

```java
@Profile("consumer")
@Component
@RocketMQMessageListener(
        topic = MqTopics.ORDER_CREATE,
        consumerGroup = MqTopics.GID_ORDER_CREATE,
        consumeMode = ConsumeMode.CONCURRENTLY,
        consumeThreadNumber = 12,          // 与 Hikari 池对齐，见 01 §3
        maxReconsumeTimes = 5)
public class OrderCreateListener implements RocketMQListener<MessageExt> {

    @Override
    public void onMessage(MessageExt ext) {
        // 收 MessageExt 而不是直接收 OrderCreateMessage：需要 getReconsumeTimes()
        // 判断第几次重试、需要 getKeys() 回写本地消息表
        OrderCreateMessage msg;
        try {
            msg = JsonUtil.parse(new String(ext.getBody(), UTF_8), OrderCreateMessage.class);
        } catch (Exception e) {
            // 解析不了的消息重试一万次也解析不了，直接 ACK 并告警。
            // 抛出去只会让它在队列里转 5 圈再进死信，中间刷 5 遍同样的错误日志
            log.error("stage=ORDER_CREATE result=UNPARSEABLE keys={}", ext.getKeys(), e);
            return;
        }
        TraceContext.set(msg.getTraceId());   // 不 put 的话消费端日志全都没有 traceId
        try {
            consume(msg, ext);
        } finally {
            TraceContext.clear();
        }
    }

    private void consume(OrderCreateMessage msg, MessageExt ext) {
        if (msg.getVersion() == null || msg.getVersion() > OrderCreateMessage.CURRENT_VERSION) {
            throw new IllegalStateException("未知消息版本: " + msg.getVersion());   // → 死信
        }
        try {
            OrderCreateService.Created created = orderCreateService.handle(msg);

            // 埋点放在回写结论之前：回写是"让外部看到成功"的那一刻，
            // 之后指标才出现的话，观察者会有一个窗口看到"订单已成功"而计数还没动
            if (!created.duplicate()) {
                metrics.orderCreated(msg.getActivityId(), msg.getSkuId());
            }
            writeSuccessAfterCommit(msg, created.order());   // 脚本 D，事务提交后
            markConsumed(ext);                               // 本地消息表标记已消费

        } catch (BizException e) {
            ErrorCode ec = e.getErrorCode();
            if (ec == ErrorCode.REQUEST_DUPLICATED) {
                // 同一 requestNo 被并发处理，另一方已建单。当前事务在 REPEATABLE READ
                // 下看不到对方的提交，查也查不到那张订单——但它确实存在，
                // 结论会由赢家写进 Redis。直接 ACK，绝不回补
                markConsumed(ext);
                return;
            }
            if (ec.isDeterministic()) {
                // 库存真没了 / uk_activity_sku_user 冲突 → 重试 5 次也不会成功，
                // 白占几分钟库存。立即回补并 ACK
                compensateService.rollback(msg, ec, ec.getMessage());
                markConsumed(ext);
                return;
            }
            throw e;                          // 非确定性业务异常 → 触发 MQ 重试

        } catch (Exception e) {
            // DB 连不上、超时、死锁 —— 下一次可能就成了。抛出触发重试；
            // 5 次耗尽后进死信，由 OrderCreateDlqListener 回补，不会永久占着库存
            throw new IllegalStateException("落库失败，待重试: " + msg.getRequestNo(), e);
        }
    }
}
```

**RocketMQ 的重试语义**：`onMessage` 正常返回即 ACK；抛异常则 `RECONSUME_LATER`，
按 `maxReconsumeTimes` 重试后进 `%DLQ%GID_xxx`。因此"确定性失败"必须
自己处理完并正常返回，否则会白重试 5 次再进死信——中间那几分钟库存一直被占着，
纯亏。

**这个类里没有任何业务规则**，唯一的判断就是上面那张"抛出还是回补"的分流。
落库逻辑一行都没搬过来，阶段一二写的落库用例仍然覆盖着同一段代码。

`ConsumeMode.CONCURRENTLY`：秒杀订单之间没有顺序依赖。用顺序消费会把并发度锁死到
队列数，且单条卡住会拖垮整个队列，而幂等设计已经让乱序无害。

`markConsumed` 失败只记 debug：它只是让本地消息表能被安全归档（状态 2 的记录 7 天后
可删），**不影响正确性**。为一条归档标记去重试整条消息，会让一条已经成功落库的请求
被重复处理——幂等能挡住，但纯属白费。

### 落库事务

```java
@Service
@RequiredArgsConstructor
public class OrderCreateService {

    /** @return 落库结果；L1 幂等命中时 duplicate = true 且携带已存在的那张订单 */
    @Transactional(rollbackFor = Exception.class)
    public Created handle(OrderCreateMessage msg) {
        // ---- 幂等层 1：请求号已处理？ ----
        Order exist = orderMapper.selectByRequestNo(msg.getRequestNo());
        if (exist != null) {
            return new Created(exist, -1, true);      // 不做任何写操作，调用方可直接 ACK
        }
        // ---- 幂等层 2 的前置查询：该用户在该活动该 SKU 上已有订单？ ----
        // 注意不带 status 条件：已取消的订单同样占用 uk_activity_sku_user（决策 1）
        Order dup = orderMapper.selectByActivitySkuUser(
                msg.getActivityId(), msg.getSkuId(), msg.getUserId());
        if (dup != null) {
            throw new BizException(ErrorCode.ALREADY_BOUGHT);   // 确定性失败 → 补偿
        }

        SeckillGoods goods = goodsMapper.selectByActivitySku(msg.getActivityId(), msg.getSkuId());
        Assert.requireFound(goods, ErrorCode.GOODS_NOT_FOUND);
        assertSellable(goods, msg.getQuantity());     // 与时间无关的校验，见下

        // ---- 条件扣减，一条语句完成判断 + 扣减 ----
        int rows = goodsMapper.deductStock(goods.getId(), msg.getQuantity());
        if (rows == 0) {
            throw new BizException(ErrorCode.STOCK_NOT_ENOUGH);  // 确定性失败 → 补偿
        }

        // ---- 建订单。价格来自 DB，绝不采信消息体 ----
        BigDecimal unitPrice = goods.getSeckillPrice();
        BigDecimal payAmount = unitPrice.multiply(BigDecimal.valueOf(msg.getQuantity()));
        ProductService.SkuSnapshot snap = productService.getSnapshot(msg.getSkuId());
        // total_amount 是 SKU 原价合计，pay_amount 是秒杀价合计，前端据此显示优惠
        BigDecimal originAmount = snap.sku().getPrice()
                .multiply(BigDecimal.valueOf(msg.getQuantity()));
        LocalDateTime expireTime = LocalDateTime.now().plus(props.getOrder().getPayTimeout());

        Order order = Order.builder()
                .orderNo(IdGenerator.orderNo()).requestNo(msg.getRequestNo())
                .userId(msg.getUserId()).activityId(msg.getActivityId()).skuId(msg.getSkuId())
                .status(OrderStatus.PENDING_PAY.code())
                .totalAmount(originAmount).payAmount(payAmount)
                .quantity(msg.getQuantity()).stockReleased(0)
                .expireTime(expireTime).build();
        insertOrder(order);                    // 唯一键冲突要分开处理，见下

        // ---- 明细快照 ----
        orderItemMapper.insert(OrderItem.builder()
                .orderNo(order.getOrderNo()).skuId(snap.sku().getId())
                .productId(snap.product().getId()).productTitle(snap.product().getTitle())
                .specSnapshot(snap.sku().getSpec()).imageSnapshot(snap.product().getMainImage())
                .unitPrice(unitPrice).quantity(msg.getQuantity()).build());

        // ---- 库存流水（uk_biz_type 保证同一请求的确认扣减只记一条） ----
        stockLogMapper.insert(StockLog.of(msg.getRequestNo(), StockChangeType.CONFIRM_DEDUCT,
                -msg.getQuantity(), msg.getActivityId(), msg.getSkuId(),
                goods.getAvailableStock(), goods.getAvailableStock() - msg.getQuantity(),
                "user:" + msg.getUserId(), "秒杀下单"));

        // ---- 请求记录落库，供对账与长期审计 ----
        upsertRequest(msg, order.getOrderNo());

        // ---- 登记关单定时消息。与订单行同事务，提交后才真正投递 ----
        producer.registerAfterCommit(MqTopics.ORDER_CLOSE, order.getOrderNo(),
                OrderCloseMessage.builder().orderNo(order.getOrderNo())
                        .userId(order.getUserId()).traceId(msg.getTraceId())
                        .version(OrderCloseMessage.CURRENT_VERSION).build(),
                order.getExpireTime());

        return new Created(order, goods.getAvailableStock() - msg.getQuantity(), false);
    }
}
```

### 唯一键冲突必须分开处理

```java
private void insertOrder(Order order) {
    try {
        orderMapper.insert(order);
    } catch (DuplicateKeyException e) {
        String m = String.valueOf(e.getMessage());
        if (m.contains("uk_request_no"))        throw new BizException(REQUEST_DUPLICATED);
        if (m.contains("uk_activity_sku_user")) throw new BizException(ALREADY_BOUGHT);
        if (m.contains("uk_order_no"))          throw new BizException(SYSTEM_BUSY, "订单号冲突");
        throw e;
    }
}
```

**把两者统一当成"重复消息 → ACK"会让 `uk_activity_sku_user` 冲突的请求既没订单
也不回补库存，库存永久泄漏。** `uk_request_no` 冲突意味着另一方正在建同一张单
（ACK 就好），`uk_activity_sku_user` 冲突意味着这个用户已经买过（必须回补）——
方向正好相反。

靠字符串匹配索引名不优雅，但这里只是并发兜底：正常路径由上面两次查询分流，
走到这个 catch 说明是真正的并发撞车。

### 落库时**不再**判定活动时间窗口

阶段一 `assertSellable` 里有时间判定，用应用侧时钟；阶段二把它挪进了 Lua，
用 Redis `TIME`。**这里必须真的删掉而不是留着当"双重保险"**：

- 多实例时钟漂移（故障用例 F14）：一台 web 实例时钟快 5 分钟，Lua 用 Redis 时钟
  判定为"未开始"正确拒绝，而这里用本机时钟判定为"进行中"。两个时钟只要有一个是错的，
  留着的那个就是错的那个。
- 活动结束那一瞬间：Lua 判定通过、请求进入落库，此处再用本机时钟判一次就可能判成
  "已结束"，于是 Redis 扣了库存、订单没建成，白白触发一次补偿回补。

时间判定**只有一个权威时钟**，这是这条改动的全部意义。保留下来的是与时间无关的
校验：数量、限购、商品停售、活动被管理员关闭——它们不依赖时钟，不会出现两个数据源
互相矛盾的情况。

### 为什么 Redis 回写要放在事务提交之后

如果在事务内就把 Redis 请求状态改成 SUCCESS，而事务随后回滚，客户端会查到
"成功 + 订单号"，但订单并不存在——它拿着一个不存在的订单号。
`TxSupport.afterCommit` 封装了 `TransactionSynchronizationManager` 的注册：

```java
public static void afterCommit(String name, Runnable action) {
    // TraceContext.wrap 把当前 traceId 抓进闭包：afterCommit 回调由事务同步机制
    // 触发，此时业务方法已经返回、MDC 可能已被清掉，不 wrap 的话回调日志没有 traceId
    Runnable traced = TraceContext.wrap(action);
    if (!TransactionSynchronizationManager.isSynchronizationActive()) {
        run(name, traced);                 // 不在事务中，直接执行
        return;
    }
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override public void afterCommit() { run(name, traced); }
    });
}

private static void run(String name, Runnable action) {
    try {
        action.run();
    } catch (Exception e) {
        // 抛出也无处可去（事务已提交），只记日志
        log.error("提交后回调执行失败 action={}，依赖兜底路径收敛", name, e);
    }
}
```

提交后回写失败（Redis 抖动）不影响正确性：客户端查不到结果会继续轮询，
`queryResult()` 在 Redis 未命中时**回查数据库** `t_order` + `t_seckill_request`，
能拿到真实结论。

**关单消息为什么反而要放在事务里**：消息行与订单行同一个事务，所以"订单已创建"和
"关单消息已登记"不可能只发生一半。少了这个原子性，一次事务回滚就能造出一张永远
不会被关闭的订单——它会一直占着库存。定时扫描能兜住，但那是 2 分钟一轮的兜底，
不该是主路径。投递时刻取 `expire_time` 而不是"现在 + 15 分钟"：两者在这一刻是同一个
值，但 `expire_time` 是写进 DB 的那个，消费端也会读它，用同一个来源可以避免
"消息在 14:59 触发而 DB 说 15:01 才过期"。

## 3. 查询秒杀结果

```java
public SeckillResultVO queryResult(String requestNo, Long activityId, Long skuId, long userId) {
    // 1. 先查 Redis。需要 activityId + skuId 才能定位 key——req key 带着
    //    {activityId:skuId} hash tag，而这个 tag 是必需的（它要和 stock / bought
    //    落在同一个 Cluster 槽，才能被同一段 Lua 原子操作）
    if (activityId != null && skuId != null) {
        SeckillExecutor.RequestResult r = executor.readResult(activityId, skuId, requestNo);
        if (r != null) {
            assertOwner(r.userId(), userId);
            return SeckillResultVO.of(SeckillRequestStatus.of(r.status()),
                    requestNo, r.orderNo(), r.reason());
        }
    }
    // 2. 回查数据库。这条路径不是冗余：Redis 结果 TTL 只有 30 分钟，
    //    而且回写可能失败。数据库才是结论的权威来源
    Order order = orderMapper.selectByRequestNo(requestNo);
    if (order != null) {
        assertOwner(order.getUserId(), userId);
        return SeckillResultVO.of(SUCCESS, requestNo, order.getOrderNo(), null);
    }
    SeckillRequest req = requestMapper.selectByRequestNo(requestNo);
    if (req != null) {
        assertOwner(req.getUserId(), userId);
        return SeckillResultVO.of(SeckillRequestStatus.of(req.getStatus()),
                requestNo, req.getOrderNo(), req.getFailReason());
    }
    // 3. 三处都没有 → 请求号不存在
    throw new BizException(ErrorCode.REQUEST_NOT_FOUND);
}

private void assertOwner(Object ownerId, long userId) {
    if (ownerId == null || !String.valueOf(ownerId).equals(String.valueOf(userId))) {
        // 与"不存在"返回同一个码，不泄漏请求号的有效性
        throw new BizException(ErrorCode.REQUEST_NOT_FOUND);
    }
}
```

**Redis 命中即返回，即使还是"排队中"**：排队中就是当前的真实结论，回查数据库也只会
查不到订单。多查两次 DB 只是把轮询的压力从 Redis 挪到 MySQL——而轮询恰好是
QPS 最高的那类请求。

客户端轮询策略（退避）：

```
第 1 次   300 ms          ← 首次间隔由服务端 pollAfterMs 下发
第 2 次   500 ms
第 3 次   800 ms
第 4 次  1300 ms
第 5 次  2000 ms
之后固定 2000 ms，累计 20 s 未出结论 → 提示"请稍后在订单列表查看"
```

服务端下发的 `pollAfterMs` 是起点：降级 Level 2 起直接给 2000ms，客户端从第一次就
慢下来。服务端对结果查询接口也单独限流（`fss.ratelimit.result-qps`，默认 5 QPS），
防止客户端 bug 打成 DDoS。

## 4. 订单状态机

```text
                    ┌──────────────┐
                    │  PENDING_PAY │ 0
                    └──┬────────┬──┘
             支付成功   │        │  超时/用户取消
                       ▼        ▼
                  ┌────────┐  ┌───────────┐
                  │  PAID  │1 │ CANCELLED │2
                  └───┬─┬──┘  └───────────┘
            发货完成   │ │  申请退款
                      ▼ ▼
        ┌──────────┐  ┌───────────┐
        │ FINISHED │3 │ REFUNDING │4
        └──────────┘  └─────┬─────┘
                            ▼
                      ┌──────────┐
                      │ REFUNDED │5
                      └──────────┘
```

允许的迁移，集中定义并在每次变更前断言：

```java
public final class OrderStateMachine {

    private static final Map<OrderStatus, Set<OrderStatus>> ALLOWED =
            new EnumMap<>(OrderStatus.class);
    static {
        ALLOWED.put(PENDING_PAY, EnumSet.of(PAID, CANCELLED));
        ALLOWED.put(PAID,        EnumSet.of(FINISHED, REFUNDING));
        ALLOWED.put(REFUNDING,   EnumSet.of(REFUNDED, PAID));   // 退款被拒回到已支付
        ALLOWED.put(FINISHED,    EnumSet.of(REFUNDING));
        ALLOWED.put(CANCELLED,   EnumSet.noneOf(OrderStatus.class));
        ALLOWED.put(REFUNDED,    EnumSet.noneOf(OrderStatus.class));
    }

    public static void assertTransfer(OrderStatus from, OrderStatus to) {
        if (!canTransfer(from, to)) {
            throw new BizException(ErrorCode.ORDER_STATUS_ILLEGAL,
                    "非法状态流转 " + from + " → " + to);
        }
    }

    /** 出边为空即终态。终态集合不单独维护一份，否则加状态时会漏改 */
    public static boolean isTerminal(OrderStatus s) {
        return ALLOWED.getOrDefault(s, Set.of()).isEmpty();
    }
}
```

**每个状态都显式列出，包括终态的空集合。** 用 `getOrDefault(from, Set.of())` 兜底
是必要的，但如果依赖它来表达"终态没有出边"，新加一个状态时忘了登记就会静默变成
终态——而这类缺陷只在那条路径被走到时才暴露。

对应状态机图：[docs/uml/png/06-订单状态机.png](uml/png/06-订单状态机.png)。

**但状态机断言只是防御性编程，不是并发正确性的来源。**
真正保证并发安全的是所有状态变更都用带旧状态条件的 UPDATE：

```sql
UPDATE t_order
   SET status = #{to}, /* 附带的时间戳等字段 */
 WHERE order_no = #{orderNo}
   AND status = #{from}
```

影响行数 0 → 说明别人抢先改了状态，读最新状态重新决策。

## 5. Redis 调用结果不确定时怎么办

`redis.execute` 抛出 `QueryTimeoutException` 时，脚本可能已执行（命令到了服务端，
响应丢在网络上），也可能没执行。此时：

- **不能当成功**：可能库存没扣，却给用户返回了排队中，最终没订单。
- **不能当失败后直接回补**：可能脚本根本没执行，回补会凭空增加库存 → 直接超卖。

处理：把整条 `OrderCreateMessage` 记入"待确认"登记簿，返回 `SYSTEM_BUSY` 让用户重试
（重试用的是新 `requestNo`，即使这一条最终判定为"已扣"，一人一单的 `bought` 标记
也会拦住第二次）。定时任务用 `EXISTS seckill:req:{a:s}:<requestNo>` 判定真实结果：

```java
@Scheduled(fixedDelayString = "${fss.job.uncertain-check-delay-ms:10000}")
@DistributedLock(key = "uncertain-check", leaseSeconds = 60)
public void checkUncertain() {
    var cfg = props.getReconcile();
    // settle 是静置窗口：超时那一刻脚本可能正在执行，立刻判定必然判错
    for (var rec : recorder.take(cfg.getBatchSize(), cfg.getUncertainSettle())) {
        OrderCreateMessage msg = rec.msg();
        try {
            if (executor.requestExists(msg.getActivityId(), msg.getSkuId(), msg.getRequestNo())) {
                // 脚本执行过、库存已扣 → 补发消息。用同一个 requestNo，
                // 所以哪怕原来那条其实也发出去了，L1/L2 幂等会挡住第二张订单
                producer.sendReliable(MqTopics.ORDER_CREATE, msg.getRequestNo(), msg, null);
            }
            // key 不存在 → 脚本没执行，库存没动，什么都不用做
            recorder.remove(rec.raw());
        } catch (Exception e) {
            // 判定或补发失败：记录必须留着——删掉就丢了"库存可能已扣"的唯一线索。
            // 但不能无限留，超过 uncertain-retention 转人工
            if (isExpired(rec.recordedAt(), cfg.getUncertainRetention())) {
                toManual(msg, e);
                recorder.remove(rec.raw());
            }
        }
    }
}
```

### 登记簿用 ZSet 而不是 List

`seckill:uncertain` 是一个 ZSet，member 是消息的 JSON、score 是登记时刻。
最初设计给的是 List，三个问题：

1. **`LPOP` 取出即出队**，处理过程崩了记录就消失——而它正是"不知道库存扣没扣"的
   唯一线索。改用 `LRANGE` 不删则要 `LREM` 按值删，O(N)。
2. **没有时间维度**，做不了那个必需的静置窗口。
3. 同一 `requestNo` 重复登记会堆成多条。

ZSet 用 score 存时刻，天然支持"只取 5 秒前的"（`ZRANGEBYSCORE 0 now-settle`）、
天然按 member 去重、删除是 `ZREM` 的 O(log N)。

**静置窗口 `uncertain-settle` 不能是 0**：Redis 超时的那一刻，脚本可能**正在**执行。
立刻判定"没执行"会把一份已扣的库存留成永久泄漏。

### 转人工时不自动回补

这里的处境恰好是"不知道库存扣没扣"，而回补一份根本没扣过的库存就是凭空增加
库存 → 直接超卖。**少卖一份可以靠人工修，超卖要赔钱。** 所以宁可留着差额等库存
对账，也不做方向未知的自动修正。

### 注意这里为什么安全

Lua 脚本的原子性保证"预扣库存"和"写 req key"要么都发生要么都不发生。因此
`req key` 存在 ⟺ 库存已扣。这条等价关系是整个不确定性处理的基石，
也是脚本 A 里必须把 `HSET reqKey` 放在同一脚本内的原因。

> 故障演练 F1 意外验证了这一段：`docker pause` 不是"断网"而是冻结进程，
> 命令在 `unpause` 之后照样执行，客户端却早已超时——于是造出了 3 次真实的
> "不确定结果"，全部判定"已执行"并补发，5 单全部成功。见
> [10 §2](10-故障演练报告.md)。

## 6. 支付与取消的并发

两个操作同时到达同一订单：

```java
// 支付成功落账（验签、时间戳、金额校验都在这之前完成）
private void paySuccess(Payment pay, PayNotifyCmd cmd, String rawBody) {
    String orderNo = pay.getOrderNo();

    int rows = orderMapper.markPaid(orderNo,
            OrderStatus.PENDING_PAY.code(), OrderStatus.PAID.code());
    if (rows == 0) {
        // 抢输了，读最新状态重新决策——不能直接报错了事
        Order latest = orderMapper.selectByOrderNo(orderNo);
        int status = latest == null ? -1 : latest.getStatus();

        if (status == OrderStatus.PAID.code()) {
            markPaymentSuccess(cmd, rawBody);      // 并发双回调，另一方已处理完
            return;
        }
        if (status == OrderStatus.CANCELLED.code()) {
            // 钱收到了但订单已关闭 → 先如实记成成功流水（钱确实收了，账不能不认），
            // 再走退款。顺序反了的话 refund 的 "from = SUCCESS" 条件更新
            // 会一行都改不到，退款静默失败
            markPaymentSuccess(cmd, rawBody);
            refundService.refund(cmd.getPayNo(), orderNo,
                    "支付与关单竞态：订单已关闭，库存已回补给其他用户");
            log.error("stage=PAY_CANCEL_RACE orderNo={} action=REFUND", orderNo);
            return;
        }
        throw new BizException(ErrorCode.ORDER_STATUS_ILLEGAL, "订单状态不允许支付: " + status);
    }

    markPaymentSuccess(cmd, rawBody);

    Order order = orderMapper.selectByOrderNo(orderNo);
    // locked → sold：此时库存真正卖出，不再可回补
    int moved = goodsMapper.moveLockedToSold(
            order.getActivityId(), order.getSkuId(), order.getQuantity());
    if (moved == 0) {
        log.error("stage=PAY_SUCCESS orderNo={} warn=LOCKED_STOCK_INSUFFICIENT "
                + "库存账目异常，需对账介入", orderNo);
    }
}

private void markPaymentSuccess(PayNotifyCmd cmd, String rawBody) {
    try {
        paymentMapper.markSuccess(cmd.getPayNo(), cmd.getOutTradeNo(), rawBody);
    } catch (DuplicateKeyException e) {
        // uk_out_trade_no：同一渠道流水号重复回调，幂等
    }
}
```

```java
// 关单。cancel（用户主动）与 closeOrder（超时）都走这个私有方法
private boolean doClose(String orderNo, String reason) {
    int rows = orderMapper.markCancelled(orderNo, reason);
    //  UPDATE t_order SET status = 2, cancel_time = NOW(3), cancel_reason = #{reason}
    //   WHERE order_no = #{orderNo} AND status = 0
    if (rows == 0) return false;    // 已支付或已取消，什么都不做

    // 关单成功才回补库存。顺序反了会出现"库存回补了但订单还是待支付"，
    // 用户仍能支付，等于超卖
    stockReleaseService.release(orderNo, reason);
    return true;
}
```

**抽成私有方法而不是让 `cancel` 直接调 `closeOrder`**：后者是自调用，绕过 Spring
代理，事务语义取决于外层方法有没有 `@Transactional`——这种"看着对、改一行就错"的
写法不值得留在关键路径上。

两者都用 `WHERE status = PENDING_PAY` 竞争同一行，MySQL 行锁保证只有一个
`rows == 1`。输的一方读最新状态走补救分支。

**`moveLockedToSold` 影响行数 0 只告警不抛异常**：此时钱已经收了、订单已是 PAID，
抛异常会回滚这两件事，把一个"库存账目对不上"的问题升级成"用户付了钱订单还是待支付"。
库存等式的偏差交给库存对账收敛。

## 7. 超时关单

主：RocketMQ 5.x 定时消息，创建订单时按 `expire_time` 投递（决策 3）。
所有发送都经过 `MqSender`，即时与定时只差一个分支：

```java
Message<String> m = MessageBuilder.withPayload(body)
        // KEYS 让 RocketMQ 控制台能按 orderNo / requestNo 反查这条消息
        .setHeader(RocketMQHeaders.KEYS, bizKey)
        .build();
SendResult sr = (deliverTime == null)
        ? template.syncSend(topic, m, props.getMq().getSendTimeout())
        : template.syncSendDeliverTimeMills(topic, m, toMillis(deliverTime));
```

**消息体是已序列化的 JSON 字符串而不是对象**：本地消息表里存的就是这个字符串，
发送时原样发出。让 `RocketMQTemplate` 自己序列化的话，落库那份和发出去那份是两次
独立序列化的结果，重发任务发出去的字节可能和第一次不同——消费端解析失败时
你无法从表里那份 JSON 复现问题。

辅：定时扫描，处理定时消息丢失、消费失败。

```java
@Scheduled(cron = "${fss.job.close-expired-cron:0 */2 * * * ?}")
@DistributedLock(key = "close-expired", leaseSeconds = 300)
public void closeExpiredOrders() {
    LocalDateTime deadline = LocalDateTime.now().minus(props.getOrder().getCloseScanDelay());
    int batchSize = props.getOrder().getCloseScanBatch();
    long lastId = 0;
    while (true) {
        // 主键游标分页，避免 OFFSET 越翻越慢，也避免一次捞太多
        List<Order> batch = orderMapper.selectExpiredPendingPay(deadline, lastId, batchSize);
        if (batch.isEmpty()) break;
        for (Order o : batch) {
            try {
                orderService.closeOrder(o.getOrderNo(), "超时未支付(扫描)");
            } catch (Exception e) {
                // 单张订单失败不能中断整批：否则一张脏数据会让后面所有订单永远关不掉
                log.error("stage=ORDER_CLOSE orderNo={} result=ERROR", o.getOrderNo(), e);
            }
        }
        lastId = batch.get(batch.size() - 1).getId();
    }
}
```

扫描比定时消息晚 `close-scan-delay`（默认 2 分钟）触发，避免和定时消息抢同一批订单
造成大量无效竞争。即使抢到同一单，条件更新也保证只有一方成功。

`leaseSeconds = 300` 明显长于其他任务：这一轮可能要关几万张订单。锁租期短于实际
执行时间的话，第二个实例会在第一个还在跑的时候拿到锁——虽然条件更新兜得住，
但两个实例会互相撞行锁，白白拖慢整批。

## 8. 库存释放（取消回补）

```java
/**
 * 用默认的 REQUIRED 传播级别，与关单同事务。
 * 曾考虑过 REQUIRES_NEW（"回补失败不该把已关的订单回滚"），但那是错的：
 * 回补先独立提交、外层关单随后回滚，就会出现 stock_released = 1 且库存已归还、
 * 而订单还是待支付——用户仍能支付这张单，等于超卖。
 */
@Transactional(rollbackFor = Exception.class)
public boolean release(String orderNo, String reason) {
    // 幂等 1：订单级标记的条件更新，把自己变成唯一执行者
    int rows = orderMapper.markStockReleased(orderNo);
    //  UPDATE t_order SET stock_released = 1 WHERE order_no = ? AND stock_released = 0
    if (rows == 0) return false;

    Order order = orderMapper.selectByOrderNo(orderNo);
    SeckillGoods goods = goodsMapper.selectByActivitySku(
            order.getActivityId(), order.getSkuId());

    // 幂等 2：流水唯一键 uk_biz_type (biz_no, change_type)
    try {
        stockLogMapper.insert(StockLog.of(orderNo, StockChangeType.CANCEL_RELEASE,
                order.getQuantity(), order.getActivityId(), order.getSkuId(),
                goods.getAvailableStock(), goods.getAvailableStock() + order.getQuantity(),
                "system", reason));
    } catch (DuplicateKeyException e) {
        return false;
    }

    // DB 回补
    int restored = goodsMapper.restoreStock(
            order.getActivityId(), order.getSkuId(), order.getQuantity());
    //  UPDATE t_seckill_goods
    //     SET available_stock = available_stock + #{qty},
    //         locked_stock    = locked_stock - #{qty},
    //         released_stock  = released_stock + #{qty},
    //         status = CASE WHEN status = 2 THEN 1 ELSE status END
    //   WHERE activity_id = ? AND sku_id = ? AND locked_stock >= #{qty}
    if (restored == 0) {
        // locked_stock 不足 —— 库存账目已经错乱。必须让事务回滚并告警，
        // 而不是"回补失败但订单已标记 released"，那会永久少一份库存
        throw new IllegalStateException("库存回补失败，locked_stock 不足: " + orderNo);
    }

    // Redis 回补：登记一条 FSS_STOCK_RELEASE，事务提交后投递（幂等 3 在消费端）
    releaseRedisAfterCommit(order, reason);
    return true;
}
```

三层幂等：`stock_released` 条件更新 → `t_stock_log` 唯一键 → Redis `released` Set。
任意一层单独都够用，叠加是因为它们的失效场景不同（前两层防 DB 侧重复，
第三层防"DB 事务提交了但 Redis 回补重试"）。

### 为什么 DB 那半留在事务里、Redis 这半走消息

这里与 [05](05-消息与一致性.md) 有一处刻意偏差：文档把整个取消回补都改成消息，
实现只把 Redis 那半挪了出来。两半的性质完全不同：

- DB 回补**能**和关单同事务，所以必须同事务。同一个库、两条 UPDATE，原子性是免费的。
  拆成消息反而引入新的失败模式：消费端永久失败时，订单已是 CANCELLED 却永远拿不回
  库存，而"已取消"没法回滚成"待支付"。
- Redis 回补**没法**加入 DB 事务，所以必须可重试。阶段二是提交后直接 `INCRBY`、
  失败只打日志等对账——那期间 Redis 少一份库存，是实打实的少卖。登记成消息之后它有了
  5 次退避重试与死信兜底。

顺序仍然是"提交之后"才投递。反了（事务内先投递、消费端抢先 `INCRBY`）会有一段时间：
Redis 库存已经加回、别人已经能抢到这一份，而 DB 事务还没提交甚至可能回滚——回滚之后
订单还是待支付、DB 库存没还，Redis 却多放出去一个资格，就是超卖。
`registerAfterCommit` 把消息行写在同一事务里、send 放在提交后，两个方向都占住了。

### 消费端要能区分"回补失败"与"早就回补过了"

脚本 C 对两者都返回非 0。分不开的话，重复投递会被当成失败无限重试，最后整批进死信——
一个纯粹由"把幂等命中误判成失败"造出来的故障。`StockReleaseListener` 多查一次
`SISMEMBER seckill:released:{a:s} <orderNo>` 把两者分开。

## 9. 活动状态推进

活动状态不靠人工点击，由定时任务按时间推进。

```java
@Scheduled(cron = "${fss.job.activity-state-cron:0 * * * * ?}")
@DistributedLock(key = "activity-state", leaseSeconds = 60)
@Transactional(rollbackFor = Exception.class)
public void advanceState() {
    LocalDateTime now = LocalDateTime.now();

    // READY → RUNNING：已预热完成且到了开始时间
    activityMapper.startReadyActivities(now);
    //  UPDATE t_seckill_activity SET status = 2
    //   WHERE status = 1 AND warmup_state = 2 AND start_time <= #{now}

    // RUNNING → ENDED
    for (Long id : activityMapper.selectRunningEnded(now)) {
        if (activityMapper.endActivity(id) > 0) {
            // 停售该活动的全部商品，让后续请求快速失败而不是走完整校验链
            goodsMapper.updateStatusByActivity(id, SeckillGoods.STATUS_OFF_SALE);
        }
    }
}
```

**预热未完成的活动不会进入 RUNNING**，这防止了"到点开抢但 Redis 没数据"导致
所有请求返回 `GOODS_NOT_WARMED`。此时用户看到的是"活动即将开始"，比看到系统错误好。
预热失败会告警，`warmup-ahead`（默认 5 分钟）留出了人工介入窗口。故障用例 F13
验证的就是这条保护。

**这个任务只改 DB，不动 Redis。** 活动结束后 Redis 侧的快速失败由预热时写入的
`endTime` 字段完成——Lua 每次都用 Redis `TIME` 与它比较，不需要谁来"通知"Redis
活动结束了。少一次跨存储的状态同步，就少一类"两边不一致"的故障。

**用户看到的活动状态不等于库里这一列**：详情接口会用 `serverTime` 现算
（见 [06 §4.2](06-接口契约.md)）——状态推进是每分钟一轮的，而活动开始那一刻
用户就在刷页面。库里这一列服务的是任务与对账，不是展示。
